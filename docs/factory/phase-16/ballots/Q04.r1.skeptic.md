| A  | Any image failure fails run | 3 | 3 | 5 | 3 | 4 |
| B  | Drop unusable image + RunFailure(step describe); transient gateway/deadline errors still fail run (retryable); all-images-failed fails run | 4 | 5 | 3 | 4 | 4 |

## Reasoning
- Pipeline already allows partial success with counted omissions (architecture.md Idempotency; ai_agents.md "omission is counted on the run"; RunFailure.ofItem/dropped).
- Failure modes of A: a decorative/blank image yields empty or refused output, deterministically, so every retry fails; one bad logo blocks the document permanently (not retryable in effect).
- Failure modes of pure B: a transient provider outage silently drops images and the run completes; no retry re-describes them, so content is lost permanently. Hence the split: transient errors (gateway unavailable, deadline) fail the run as retryable (matches IngestRunFailedException handling); only per-image deterministic failures (blank or unusable output) are dropped and counted.
- Guard: if the document had IMAGE blocks and none produced text and no text blocks exist, fail with a retryable/clear error instead of falling through to "document has no text".
- Observability: record count and block position in RunFailure with fixed text only (no provider message); add `describe` to FAILURE_STEPS in frontend/src/app/shared/labels.ts.
## What would change my mind
Evidence that blank/unusable output is rare and mostly transient (then A is simpler), or that the UI cannot surface RunFailure omissions.

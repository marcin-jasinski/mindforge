## Reasoning
- D01 puts image bytes in documents.content_blocks (JSONB, eager-loaded); an unbounded image count means unbounded row size, memory and retry cost (each retry re-pays every VISION call). A bound is a safety need, not a nicety.
- ai_agents.md:91: over a cap the run fails, like the claim cap; B copies that existing pattern and needs no schema change (B2 needs a new run counter).
- Filter (min dimension ~64 px) and content-hash dedupe are not omissions of content; they drop decorative/repeated items. Log the dropped count at INFO.
- Format: raster only; PNG/JPEG pass through, other decodable raster re-encoded to PNG via ImageIO (JDK, no new dependency); EMF/WMF/SVG skipped and logged. Failure to decode one image must not fail the upload.
- Per-image byte cap (e.g. 5 MB after re-encode): fail the image loudly is too harsh for an upload; skip it with a WARN log naming document and page. Residual silent-loss risk; accept and document.
- Cap enforced at parse time bounds stored bytes; if parse-time failure is chosen it rejects the upload (400) with a clear message, before any row is stored. Prefer enforcing after filter+dedupe so logos do not count.
- Opt-out: one switch `mindforge.ingest.images.enabled` (default true, since completion expects descriptions); when false parsers emit no IMAGE blocks. Document in deployment.md. Do not put it in ProcessingSettings (per-KB, speculative).
## What would change my mind
Evidence that real documents routinely exceed a sane cap (then counted omission B2 is better than failing).
## Implementation notes
Constants/config in `dev.mindforge.infrastructure.parsing` (shared helper `ImageExtractor`: min-dimension, SHA-256 dedupe per document, ImageIO re-encode, byte cap). Default cap e.g. 50 images/document, from `mindforge.ingest.images.max-per-document`; exceed => domain exception mapped to 4xx at upload. Tests: tiny image skipped, duplicate once, EMF skipped, over-cap fails, switch off emits none.

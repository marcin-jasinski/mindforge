## Reasoning
- Architecture.md: partial success is legal, a run fails only when nothing succeeded; RunFailure already models dropped items (RunFailure.ofItem / dropped).
- ai_agents.md:91 allows counted omission where omission is acceptable; one decorative image in a text document is such a case. D01 note says "a loud IngestRunFailedException or a counted omission on the run; never dropped silently", so B is consistent.
- A makes one bad image block a whole document; with retry re-describing every image (D01), cost multiplies.
- B must keep the loud edge: provider unavailable / circuit open / deadline is infrastructure, not per-image, so fail the run retryable (same as other model steps). Only per-image unusable output (blank/empty) is dropped. If all text and all images are gone, the run fails retryably (describe failures), not "no text, not retryable".
- Recorded reason is fixed text, never provider message. Add `describe` to FAILURE_STEPS in labels.ts.

## What would change my mind
Evidence that dropped images silently degrade quiz/flashcard quality enough that users prefer a hard failure; or that distinguishing per-image from gateway errors is not feasible via AIGateway exceptions.

## Implementation notes
- ImageDescriber returns a result record (blocks plus List<RunFailure>); per image blank output -> RunFailure.ofItem("describe", "block " + position, null, "empty description").
- Gateway/deadline exceptions propagate as IngestRunFailedException (retryable) from IngestPipeline.generateAndCommit.
- If all IMAGE blocks failed and no TEXT blocks remain, throw retryable IngestRunFailedException.
- Add "describe" to frontend/src/app/shared/labels.ts FAILURE_STEPS; tests with StubAIGateway(VISION): blank output dropped and recorded, gateway error fails run, image-only all-fail is retryable.

## Options
| id | option | correct | fit | simple | risk | reversible |
|----|--------|---------|-----|--------|------|------------|
| A  | Describe in the run as first step; IMAGE blocks with bytes stored in `content_blocks` JSONB | 5 | 4 | 4 | 3 | 4 |
| B  | Describe at upload in `IngestionService`, before the tx; store only TEXT blocks | 3 | 2 | 4 | 2 | 3 |
| C  | Describe in the run, commit 1 rewrites the document's blocks (bytes dropped) | 3 | 2 | 2 | 2 | 2 |
| D  | A, plus bytes in a separate `document_images` table read only by the run | 5 | 3 | 2 | 4 | 3 |

## Reasoning
Failure modes, per option:
- B: N vision calls hold the HTTP request/CLI (upload is 202 today, plan 4.5); a provider outage makes uploads fail with the file lost, with no retry path (retry needs a FAILED run, `IngestionService.retry`). Calls run before the dedup check (`findByContentHash` is inside the tx, line 90), so a duplicate upload pays again. No permit, no `step_versions`, no cost on a run: the description is invisible in operations. That is the worst observability of all options.
- C: the run writes to `documents` in commit 1, which breaks `Document` ("Immutable", `Document.java:9`). A crash between describe and commit, or a run that fails after commit 1, leaves the input in a mixed state. A retry then sees different input and does not record `ImageDescriber` in `step_versions`. Data integrity and audit trail both get worse.
- A: correct by design. The calls are on the run worker, behind the permit pool, outside any transaction (before commit 1 at `IngestPipeline.java:~234`), versioned via `RunState.version`, and a failure becomes a FAILED run that the user can retry. The real risks are size and read amplification. `DocumentEntity.contentBlocks` is an eagerly mapped JSONB column (`DocumentEntity.java:63`), and `listByKnowledgeBase` (`IngestionService.documents`, line 154) loads every document's blocks on each document-list GET. With bytes, this becomes MBs to tens of MBs for each request. `findByContentHash` also loads the full row. A retry re-pays the vision calls, but it is visible and counted. These risks have mitigations without a new concept (see notes). The tech-stack "original bytes not retained" line is about the upload file. Extracted image blocks are derived content blocks, and no ADR forbids them (ADR 0014 amendment covers text only).
- D removes the read amplification fully but adds a table, a port and a migration. That is speculative before the size problem is measured. If A's list query fix is not enough, D can be added later (reversible).

## What would change my mind
Evidence that a JSONB row of ~67 MB (50 MB upload, base64) breaks Hibernate/JDBC memory limits in the deployment target (Railway), or that the list projection cannot be done without a large refactor. Then D.

## Implementation notes
- `IngestPipeline.generateAndCommit`: call `describeImages(state, document.contentBlocks())` before `Preprocessor.clean`. Skip it for CONVERSATION. Add `step(state, "describe", ...)` and `state.version(ImageDescriber.class, ImageDescriber.VERSION, ImageDescriber.TIER)` only when at least one IMAGE block exists.
- Replace the block in place with `ContentBlock.text(description, sameposition)`. A failed or blank description is a counted omission or a loud `IngestRunFailedException(…, true)`. Never drop it silently.
- Bound the cost in code: a cap on the image count per document (setting in `ProcessingSettings`, documented in deployment.md) and a minimum pixel size to skip icons/bullets in the parsers. Above the cap, fail loudly or count the omitted images on the run. Do not truncate silently.
- Read amplification: make `listByKnowledgeBase` (and `findByContentHash`, which needs only the id) not load `content_blocks`. Use a JPQL projection or `@Basic(fetch = LAZY)`, or document the cost if this is deferred. Add an integration test that asserts the list does not return blocks.
- Bytes must never be serialized to a DTO: keep `DocumentResponse` without blocks, and add a test that the JSON of a document with an image has no base64 bytes.

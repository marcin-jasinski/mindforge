## Options
| id | option | correct | fit | simple | risk | reversible |
|----|--------|---------|-----|--------|------|------------|
| A  | Describe in the run as the first step (before `Preprocessor.clean`); IMAGE blocks with bytes stored in `content_blocks` JSONB | 5 | 4 | 5 | 3 | 5 |
| B  | Describe at upload in `IngestionService`, after parse, before the transaction; store only TEXT blocks | 3 | 2 | 3 | 2 | 3 |

## Reasoning
- A reuses everything that exists: the run worker already reads `document.contentBlocks()` (`IngestPipeline.java:162`) outside a transaction; `PipelineConfig.background` already gives the permit; `RunState.version(...)` and `ProcessingSettings.withModels` already record VISION. The new code is one call before `Preprocessor.clean`. No new concept.
- A matches plan 16.2 literally ("before `RelevanceGuard`") and scope ("describe images before commit 1, outside any transaction").
- B needs a model call in the upload path with no run: no permit, no `step_versions`, no cost meter, and the 202 upload (plan 4.5) becomes a slow call that can fail on the model. It adds new concepts (upload-time model use) to the closed pipeline design.
- C breaks `Document` immutability (`Document.java:9`: "Immutable") and makes retries non-deterministic in input; it also needs a new write path for documents.
- D is speculative: retries are rare (max three attempts) and re-describe is the honest cost, recorded on the run. Add only if cost data says so (minimal-implementation.md).
- Cost of A: JSONB grows (base64, ~33 %), bounded by the existing 50 MB upload cap. `tech-stack.md:94` says "the original bytes are not retained" — extracted image bytes are not the original file, but update that sentence to say extracted image bytes are kept in content blocks. Bytes stay out of the API (`DocumentResponse.java:7` excludes `contentBlocks`) and the export (exporter does not read `ContentBlock`).
- A is fully reversible: changing to B later is a move of one call; stored blocks remain valid.

## What would change my mind
Evidence that document list/read paths load `content_blocks` on hot API paths so large JSONB causes real latency or memory problems, or that a mandatory image-byte retention rule exists in an ADR.

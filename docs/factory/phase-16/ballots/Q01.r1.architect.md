## Options
| id | option | correct | fit | simple | risk | reversible |
|----|--------|---------|-----|--------|------|------------|
| A  | Describe in the run as its first step (before Preprocess); IMAGE blocks with bytes stored in `documents.content_blocks` JSONB | 5 | 5 | 4 | 3 | 4 |
| B  | Describe at upload in `IngestionService` after parse, before the transaction; store only TEXT blocks | 3 | 1 | 3 | 2 | 3 |
| C  | Describe in the run, then the run's commit rewrites the document's blocks (images -> descriptions) | 3 | 1 | 2 | 2 | 2 |
| D  | Describe in the run, bytes stored in a separate `document_images` table (not in `content_blocks`) | 5 | 3 | 2 | 3 | 3 |

## Reasoning
- ADR 0013 defines ingest as a fixed sequence of single-shot model calls inside a run; the plan (16.2) puts the describer in that sequence "before RelevanceGuard". A is the only option that keeps every model call of ingest inside the run, so it inherits the permit pool, deadline, cost meter and `step_versions` (ai_agents.md:33, :49) with no new mechanism.
- B moves a model call into the upload adapter path (`IngestionService.java:84` parses, then `:88` transaction). It is the first and only model call outside a run in ingest; its VERSION cannot be recorded (no run exists), and the upload stops being a fast 202. That is an architectural exception a maintainer would have to explain forever.
- C mutates `Document`, which is declared immutable source of truth (`Document.java:8-9`; CONTEXT.md:70 "exactly as received"); ADR 0015 relies on a retry being a new run of the same source.
- "Original bytes are not retained" (tech-stack.md:95) refers to the uploaded file; the image bytes are extracted content blocks, which the same sentence says are stored in PostgreSQL. ADR 0014 amendment "Uploaded text is retained" does not forbid it. A is consistent with both; it should be stated in the ADR 0013 amendment and tech-stack.md so the deviation from "text only" is explicit.
- Retries re-describing images is correct under ADR 0015: re-runs are new runs; a new VISION model or prompt VERSION should apply. Cost is visible on each run.
- D is cleaner on storage size but adds a table, a port and a migration the plan does not ask for; JSONB is already the block store (minimal-implementation.md). Defer until size is a measured problem.
- Size risk (50 MB cap, base64 +33 %) is bounded by the existing upload limit; record it as a known consequence.

## What would change my mind
Evidence that JSONB rows of tens of MB break the document read path (e.g. `DocumentRepository` list queries load `content_blocks`) - then D. A requirement that upload-time cost must be refused before queueing would favour B.

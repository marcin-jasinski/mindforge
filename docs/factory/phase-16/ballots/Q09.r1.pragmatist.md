## Options
| id | option | correct | fit | simple | risk | reversible |
|----|--------|---------|-----|--------|------|------------|
| A  | PDF: images after page text block; DOCX: right after holding paragraph/table | 4 | 5 | 5 | 4 | 5 |
| B  | PDF: split page text at image y-position | 5 | 3 | 1 | 2 | 3 |
| C  | All images at end | 2 | 1 | 5 | 3 | 5 |

## Reasoning
- PdfParser emits one TEXT block per page, so a page is the finest existing unit. Option A keeps image and its page text adjacent, so the same chunk and the same claim block range see both.
- DOCX already has one block per body element, so "right after the holding paragraph" is exact at the existing granularity.
- B needs custom PDFTextStripper and PDFStreamEngine code and changes the one-block-per-page contract. It is speculative precision for an impact-low question.
- C breaks locality and the plan's "in document order" wording.
- A is reversible: positions are assigned consecutively by the parser, so B can be added later in the parser only.

## What would change my mind
Evidence that real PDFs have many images per page where mid-page order changes chunk or claim attribution.

## Implementation notes
PdfParser: after each page's TEXT block, emit that page's IMAGE blocks in content-stream order. DocxParser: emit IMAGE block(s) immediately after the paragraph or table that holds the picture. Assign consecutive positions as the blocks are emitted.

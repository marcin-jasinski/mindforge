- id: C1
  severity: major
  confidence: 0.7
  location: src/main/java/dev/mindforge/infrastructure/parsing/ImageExtractor.java:58
  claim: The pass-through decision trusts the declared MIME type, not the decoded format, so bytes of another format are emitted unchanged with a wrong `image/png` / `image/jpeg` label.
  evidence: `accept(bytes, "image/png")` with GIF or JPEG bytes (a DOCX part named `.png` whose content is JPEG is common; the DOCX content type comes from the file extension in `[Content_Types].xml`) -> `ImageIO.read` decodes it with whatever reader matches the magic bytes -> line 58 sees `PNG.equals(mimeType)` -> `emit(bytes, "image/png", ...)` returns `ImageInput(<JPEG/GIF bytes>, "image/png")`. Downstream the VISION call sends a media type that does not match the bytes (providers reject or misread such an image), and a GIF labelled PNG is not "re-encoded to PNG" as D05 requires.
  fix: Decide pass-through from the actual format: open an `ImageInputStream`, take `ImageIO.getImageReaders(iis).next().getFormatName()`, and keep the bytes only when it is `png` (emit `image/png`) or `jpeg` (emit `image/jpeg`); re-encode everything else to PNG. Add a test with JPEG bytes declared as `image/png`.

- id: C2
  severity: major
  confidence: 0.5
  location: src/main/java/dev/mindforge/infrastructure/parsing/ImageExtractor.java:49
  claim: The full decode runs before any dimension check, so a small, highly compressed image with huge declared dimensions decodes into a multi-GB raster and throws `OutOfMemoryError`, which the `IOException | RuntimeException` catch does not handle.
  evidence: Upload limit is 50 MB (`application.yml:11`). A PNG of one colour at 40000x40000 compresses to a few MB; `ImageIO.read` allocates a 40000*40000*3-4 byte raster (about 5-6 GB) -> `OutOfMemoryError` (an `Error`) escapes `accept`, fails the upload with a 500 rather than a skip, and can starve other requests in the same JVM. The ticket notes say "Dimension check uses ... before decoding" for PDF; the byte path has no pre-decode check at all.
  fix: Read width/height with `ImageReader.getWidth(0)/getHeight(0)` from the `ImageInputStream` before `reader.read(0)`, and skip (WARN) an image whose pixel count exceeds a fixed bound (for example the area that could fit within `MAX_IMAGE_BYTES` at a reasonable ratio) - or at least skip above a hard pixel ceiling, before decoding.

- id: C3
  severity: minor
  confidence: 0.6
  location: src/main/java/dev/mindforge/infrastructure/parsing/ImageExtractor.java:43
  claim: A null `mimeType` throws `NullPointerException` instead of a skip, because `Set.of(...).contains(null)` throws.
  evidence: `NON_RASTER` is an immutable `Set.of` set; `ImmutableCollections.SetN.contains(null)` throws NPE. A caller that passes a missing content type (for example a picture part without a declared type) crashes the parse, against AC5 "skipped without an exception".
  fix: Guard with `mimeType == null ||` (treat as unknown, decode and re-encode) or `mimeType != null && NON_RASTER.contains(mimeType)`.

- id: C1
  severity: major
  confidence: 0.7
  location: src/main/java/dev/mindforge/infrastructure/parsing/PdfParser.java:65
  claim: The same image XObject is fully decoded and re-encoded again on every `Do` that draws it, and the 100-image limit is checked only after all pages, so a small PDF can make one upload do an unbounded amount of decode/PNG work.
  evidence: Dedup happens only inside `ImageExtractor.emit` (SHA-256 of the output bytes), after `extract` has called `image.getImage()` and `ImageIO.write(..., "png")`. Nothing remembers which PDImageXObject (COSStream) was already handled. The MAX_PIXELS guard (50M px) still allows a ~7000x7000 Flate image, which compresses to roughly 150 KB when uniform and decodes to a ~196 MB raster. Input: a 50 MB PDF (the upload limit in application.yml) with that one XObject and content streams of `/Im1 Do` repeated (about 8 bytes each), so millions of draws across the pages. Each draw decodes 49M pixels and PNG-encodes them; only the first is kept. The parse runs for hours on a request thread. Also, `extractor.checkCount(images)` runs only after the loop (line 73). So a PDF with many distinct large images is decoded in full before the >100 rejection. A rejection after image 101 would stop this.
  fix: Keep a `Set<COSBase>` of `drawn.getCOSObject()` per parse and skip an XObject that is already in it before `extract`. Call `extractor.checkCount(images)` after each accepted image (or test `images > MAX_IMAGES_PER_DOCUMENT` there), so the parse stops at image 101 rather than after the last page.

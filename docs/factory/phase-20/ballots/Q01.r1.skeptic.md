## Options
| id | option | correct | fit | simple | risk | reversible |
|----|--------|---------|-----|--------|------|------------|
| A  | Per client address only (login + register) | 3 | 4 | 5 | 2 | 5 |
| B  | Per address on both + per-normalised-email bucket on login (refuse when either is spent) | 4 | 4 | 3 | 4 | 4 |
| C  | Per email on login, per address on register | 2 | 3 | 3 | 2 | 4 |
| D  | Per address on both + per-email on login counting only failed sign-ins (in AccountService) | 4 | 2 | 3 | 3 | 4 |

## Reasoning
- The plan names no key (implementation-plan.md 20.3: "Caffeine-backed limiter on `/api/auth/login` and `/api/auth/register`"), so the threats in the question decide. Each option fails differently:
- A fails silently against a distributed guesser on one account. It also depends fully on Q02: if the client address is wrong (proxy address, Q02 option C), A is one global bucket, so ten failures anywhere lock out all sign-ins. Or, if forwarded headers are trusted too widely, an attacker can rotate addresses and A does nothing. We find out only after an incident.
- C does not cap credential stuffing (many emails from one address) on login. That is the most common attack in practice, so C does not meet the stated threat.
- B covers all three threats, and its two keys fail independently: a Q02 misconfiguration still leaves the per-email cap on guessing. The cost is that an attacker can spend a victim's email bucket. This is bounded: give the email bucket a generous limit and a short window (it slows guessing to tens per window, not to zero), and the victim can still sign in with OAuth. 429 + Retry-After tells the victim that the block is temporary.
- D (count only failures) breaks the R09 precedent ("rejected requests count") and puts limiter logic in the application layer. No hard objection, but it has no advantage over B.
- Integrity/operability risks of B and how to control them: (1) attackers can make many email keys, so set `maximumSize` on the email cache, and the address bucket caps growth per address anyway. (2) The email must be normalised as `AccountService.normalise` does (`email.trim().toLowerCase(Locale.ROOT)`, AccountService.java:82-83). If they differ, a case change gets past the bucket, so share one normaliser. (3) Never log the raw body or the password. Log a hash, or nothing, for the email.
- Testability: two MockMvc tests (same address with different emails gives 429; different addresses with one email gives 429) prove each bucket separately.

## What would change my mind
Evidence that reading the login email before the controller needs fragile body caching that affects `@Valid @RequestBody` binding. Then I would take A now and add the email bucket later (A to B is additive).

## Implementation notes
- Make the window logic of `RateLimitInterceptor` (api/config) generic over the key (`Cache<K, Window>`). Or extract a small `FixedWindowLimiter<K>` with `boolean tryAcquire(K key)` / reset seconds, so that R09 and the auth limiter share one implementation.
- Address bucket: a `HandlerInterceptor` on `/api/auth/login` and `/api/auth/register` POST, keyed by `request.getRemoteAddr()` (after the Q02 decision). It throws `RateLimitExceededException`, which reuses the existing 429/`RATE_LIMITED`/`Retry-After` path in `GlobalExceptionHandler`.
- Email bucket: do not cache the raw body. Use a `RequestBodyAdvice` (`afterBodyRead`, `supports` only `LoginRequest`) in api/config, so the `LoginRequest` that Spring already parsed is checked before the controller method runs. Key = the shared normaliser output (expose `AccountService`'s rule as a static in a domain/application helper, for example `Emails.normalise`).
- Settings under `mindforge.rate-limits.auth.*` (address limit/window, email limit/window), documented in deployment.md and env.example. Bound both caches with `maximumSize`.

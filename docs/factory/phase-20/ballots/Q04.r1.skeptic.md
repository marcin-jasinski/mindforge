## Reasoning
- AccountService.authenticate skips matches() for unknown email and null passwordHash: a ~250 ms timing oracle, trivially exploitable.
- register 409 stays an open channel, but closing it needs email verification, and no mail sending exists (minimal-implementation.md). Rate limit (Q01-Q03) bounds it.
- B is a new flow outside plan scope and changes the API contract.
- C leaves a cheap, known leak.
- Failure modes of A: a hard-coded dummy hash of the wrong cost would leave a timing gap, so generate it once via PasswordHasher.hash at construction. Always run exactly one matches() call. Test with a stub hasher counting matches() calls across the three cases (no timing assertions, which are flaky).

## What would change my mind
Mail sending being added in this phase would make B worthwhile.

## Implementation notes
In AccountService: a final String dummyHash = hasher.hash("dummy") set in the constructor. In authenticate: find the user; hash = user with a non-null passwordHash ? that hash : dummyHash; boolean ok = hasher.matches(password, hash); throw invalidCredentials unless the user is present, has a hash and ok. Remove the ponytail comment. Add a unit test that matches() is called once in all three cases.

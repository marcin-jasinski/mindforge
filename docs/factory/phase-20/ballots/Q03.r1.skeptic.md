## Options
| id | option | correct | fit | simple | risk | reversible |
|----|--------|---------|-----|--------|------|------------|
| A  | New mindforge.rate-limits.auth.requests/window, 10 per PT1M, one bucket per address shared by login+register | 4 | 5 | 5 | 4 | 5 |
| B  | As A, but separate login (10/min) and register (5/hour) allowances | 4 | 4 | 3 | 3 | 4 |
| C  | Reuse mindforge.rate-limits | 2 | 3 | 5 | 2 | 4 |

## Reasoning
- D01 keys by client address only, so every bucket is per address. The main failure is NAT lock-out. A hourly register cap (B) makes that worse: a classroom or household behind one address cannot sign up more than 5 users per hour, and the failure is hard to diagnose (a long Retry-After).
- Registration cost is bounded by BCrypt cost 12; 10 per minute per address is a CPU cost that the server tolerates. B's tighter register cap helps only against mass sign-up, which D01 already limits.
- A needs one counter and one setting pair. B needs a path-aware key and two setting pairs, and the second pair brings more tests and docs.
- A to B is additive later (key = path + address), so A is reversible. A cap that is too tight at launch is not easy to find without metrics.
- C is rejected: the shared 30/min is too loose, and the two limits would be coupled.
- Test risk: ApiFlowTest registers many users from localhost, so it must set a high value, as RateLimitTest does with @TestPropertySource. Verify the default does not break other ITs; a failure shows as unexpected 429.
- Shared bucket weakness: register spam from an address exhausts that address's login allowance. Acceptable, because it only affects the same address.

## What would change my mind
Evidence of abusive mass registration (open signup with no email verification), which would justify a separate hourly register cap.

## Implementation notes
- AppProperties: add nested `Auth` class inside `RateLimits` (`@Valid private Auth auth = new Auth();`) with `@Positive int requests = 10` and `@NotNull Duration window = Duration.ofMinutes(1)`. Binds to `mindforge.rate-limits.auth.requests` and `.window`.
- Env: `AUTH_RATE_LIMIT_REQUESTS`, `AUTH_RATE_LIMIT_WINDOW` in application.yml, with defaults.
- One `AuthRateLimitInterceptor(int, Duration)` instance, registered in `RateLimitConfig.addInterceptors` for the two paths, with one shared bucket per address.
- Document in `docs/standards/.../deployment.md` and `env.example`. Raise the values in ApiFlowTest and other ITs that register many users.
- Retry-After and the RateLimit-* headers come from `RateLimitExceededException` and the existing handler.

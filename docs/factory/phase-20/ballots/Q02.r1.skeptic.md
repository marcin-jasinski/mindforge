## Reasoning
- Spoofing under A: RemoteIpValve honours XFF only when the direct peer matches internal-proxies, then walks the list right to left and takes the first untrusted entry. The PaaS proxy appends the real peer, so a forged left-hand value is skipped. A public client cannot reach the app from a private address on Railway/Render, so it cannot get its own header trusted.
- A fails toward the global bucket, not toward a bypass. If the proxy address is outside the default ranges, Tomcat ignores the header and the limit is per proxy. That is the DoS case, and it is visible if the limiter logs the key on refusal.
- B fails worse in both directions. Leave `TRUSTED_PROXIES` unset on Railway and it gives exactly that DoS on the primary deployment: anyone can send ten bad logins and block all sign-ins. Worse, the obvious implementation `internal-proxies: ${TRUSTED_PROXIES:}` fails OPEN. In Spring Boot, an empty internal-proxies regex means "trust all proxies". The Spring Boot how-to says "do not do so in production". So "default empty = trust none" is the opposite of the real semantics, and a reviewer may miss it.
- C: hard objection (see above). D: we would re-implement RemoteIpValve badly, it misses X-Forwarded-Proto, and a wrong N trusts client data.
- The scheme change is wanted. `OAuthLoginSuccessHandler` and the OAuth2 `{baseUrl}` redirect URIs get https behind the proxy, where today they see http.
- Residual risk for A: a self-hosted Docker setup whose peer is a private gateway (userland-proxy) trusts a client XFF. Document it in deployment.md. B' closes it only if the operator acts, so it is not worth the extra code now. Reversible: one yml line.

## What would change my mind
Evidence that Railway or Render ingress connects from a non-RFC1918/ULA/CGNAT address, or overwrites rather than appends XFF. Also a reviewer who requires an operator override now: then I take B', never B with an empty default.

## Implementation notes
- `src/main/resources/application.yml`: under `server:` add `forward-headers-strategy: native`. Do not set `tomcat.remoteip.internal-proxies`. Never set it to empty, because empty means trust all.
- The limiter key is `request.getRemoteAddr()` only. No code reads `X-Forwarded-For`.
- Test (integration, real Tomcat, `RANDOM_PORT`): the test client is on loopback, which is trusted. Use a test property `server.tomcat.remoteip.internal-proxies=^$` (matches nothing, so not the empty-string trap) to show that a forged XFF does not change the bucket. With the default config, show that XFF from loopback does change the key.
- Log the refused key at INFO on a 429, so a global-bucket misconfiguration shows up in the logs.
- ADR (newest format): "Client address comes from Tomcat RemoteIpValve with default internal proxies". deployment.md § Railway: note the trust model and the self-hosted Docker caveat.

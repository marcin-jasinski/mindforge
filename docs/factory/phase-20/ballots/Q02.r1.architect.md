## Options
| id | option | correct | fit | simple | risk | reversible |
|----|--------|---------|-----|--------|------|------------|
| A  | `forward-headers-strategy=native`, Tomcat default private ranges, limiter uses `getRemoteAddr()` | 4 | 3 | 5 | 3 | 5 |
| B  | Native RemoteIpValve, trusted proxies from `TRUSTED_PROXIES` (allowlist); blank = no valve, peer address only (fail closed) | 4 | 5 | 4 | 4 | 5 |
| C  | No forwarded headers; document that the limit is global behind a proxy | 1 | 2 | 5 | 2 | 5 |
| D  | Limiter parses rightmost XFF itself with a configured hop count | 3 | 1 | 2 | 3 | 4 |
| E  | As A, but `TRUSTED_PROXIES` overrides the Tomcat private-range default (open by default, narrowable) | 4 | 4 | 4 | 3 | 5 |

## Reasoning
- B matches the house pattern for operator trust: ADR 0028 admits callers by a fail-closed allowlist from config; the
  question's constraints cite `validation.md` "allowlists over blocklists" and env vars documented in `deployment.md`/`env.example`.
- B and A use the framework's own valve, so `getRemoteAddr()`, `isSecure()` and the OAuth redirect scheme agree on one
  idea of "the client". D makes the limiter the only code that knows the proxy shape (hidden second source of truth).
- A relies on an undocumented property of Railway/Render (question Context: "not documented as a guarantee") and
  trusts any private peer, including the docker bridge in local compose. A maintainer cannot see from config that XFF is trusted.
- TRAP (load-bearing for B): Spring Boot docs say an EMPTY `server.tomcat.remoteip.internal-proxies` trusts ALL proxies
  ("You can trust all proxies by setting the internal-proxies to empty (but do not do so in production)").
  So `internal-proxies: ${TRUSTED_PROXIES:}` would be fail-OPEN. B must not install the valve when the setting is blank.
- Cost of B: a production deploy that forgets `TRUSTED_PROXIES` falls back to one global bucket (availability fault,
  not a bypass). Mitigate: Railway step 3 lists it, `env.example` shows the value, startup logs which mode is on.
- The OAuth scheme change happens only when the operator turns trust on, which is the deployment that needs it.
- Load-bearing: needs a new ADR (next number) in the 0028/0037 format, "Considered Options" listing A, D, C.

## What would change my mind
Evidence that Railway/Render document their proxy egress as private ranges (A/E become safe-by-default), or a team
rule that a missing env var must never degrade production behaviour (then E).

## Implementation notes
- `AppProperties.Security` (`src/main/java/dev/mindforge/infrastructure/config/AppProperties.java`): add
  `String trustedProxies` bound from `mindforge.security.trusted-proxies: ${TRUSTED_PROXIES:}` (a Tomcat regex of peer IPs).
- New `@Configuration` (e.g. `infrastructure/config/ForwardedHeadersConfig.java`): a
  `WebServerFactoryCustomizer<TomcatServletWebServerFactory>` that, only when `trustedProxies` is non-blank, adds a
  `RemoteIpValve` with `setInternalProxies(trustedProxies)`, `setTrustedProxies(null)`, `setRemoteIpHeader("X-Forwarded-For")`,
  `setProtocolHeader("X-Forwarded-Proto")`; validate the regex at startup (`Pattern.compile`, fail start on error).
  Log `log.info` once: "forwarded headers trusted from {}" or "forwarded headers ignored". Keep
  `server.forward-headers-strategy` unset (NONE) so Boot does not add a second valve.
- Limiter key (Q01/W02) reads `request.getRemoteAddr()` only; never reads `X-Forwarded-For` directly.
- `deployment.md` env table + § Railway step 3: `TRUSTED_PROXIES` with the private-range regex for Railway/Render;
  `env.example` commented. Tests: spring-free test of the customizer (blank -> no valve; set -> valve with pattern),
  and an integration test that a forged XFF from an untrusted peer does not change the bucket.
- New ADR `docs/adr/00NN-client-address-from-forwarded-headers-only-from-configured-proxies.md`.

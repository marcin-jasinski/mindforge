## Reasoning
- A is one YAML line in `src/main/resources/application.yml` (`server:` block, line 75) and zero Java. Tomcat's
  `RemoteIpValve` honours `X-Forwarded-For` only when the direct peer matches `internal-proxies`, and walks the header
  right-to-left, stopping at the first untrusted address. A forged left-hand value from a client is never reached, and a
  client that connects directly from a public address gets its header ignored. This meets "never trust client data
  without a check" with an allowlist the framework already enforces.
- The override already exists without new code: Spring relaxed binding maps `SERVER_TOMCAT_REMOTEIP_INTERNAL_PROXIES`
  to `server.tomcat.remoteip.internal-proxies`. We document it in `deployment.md` (env table near line 42) and
  `env.example`, which satisfies the `conventions.md` env-var rule. A new `TRUSTED_PROXIES` alias (B2) adds a concept
  for no gain.
- B fails closed by default, but in production that "safe" default reproduces the exact bug C has (one bucket for all
  users, global lockout). The operator also cannot fill it correctly: Railway/Render do not publish their proxy IPs
  (question Context bullet 3). A footgun default is worse than a documented, overridable one.
- D re-implements the valve by hand (parsing, IPv6, N-hop counting) in the limiter, and only the limiter benefits;
  `isSecure()`/scheme stay wrong for OAuth redirects. More code, more bugs, less fit.
- Residual risk of A: a co-tenant on the same private network could spoof the header. With one instance on a managed
  PaaS this is low, and the override narrows it. The `isSecure()`/scheme change is a fix for OAuth redirect URIs behind
  TLS-terminating proxies; local compose and tests connect directly, so nothing changes there.

## What would change my mind
Evidence that Railway or Render connect from a public (non-private) address, or that the app port is reachable from
other tenants on the same private range, would push me to B2 with a documented required value.

## Implementation notes
- `application.yml`, under `server:`: `forward-headers-strategy: native` (comment: trusts X-Forwarded-* only from
  `server.tomcat.remoteip.internal-proxies`, Spring's private-range default).
- Limiter key (W02): `request.getRemoteAddr()`; no header parsing anywhere in app code.
- `deployment.md` § Railway + env table and `env.example`: document optional `SERVER_TOMCAT_REMOTEIP_INTERNAL_PROXIES`
  (Java regex) to narrow or widen the trusted proxy set.
- Test: a `@SpringBootTest` (integration) or MockMvc test with `RemoteAddr=10.0.0.1` + `X-Forwarded-For: 1.2.3.4, 5.6.7.8`
  resolves to `5.6.7.8`; with `RemoteAddr=8.8.8.8` the header is ignored. Note MockMvc bypasses the Tomcat valve, so
  this needs a real-server test (`webEnvironment = RANDOM_PORT`) or a unit test of the valve config.
- ADR 0038 (newest format, cf. `docs/adr/0037-*.md`): "Client address comes from Tomcat's RemoteIpValve trusting
  private-range proxies".

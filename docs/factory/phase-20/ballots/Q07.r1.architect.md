## Reasoning
- Constraints in Q07: no secrets in the repo, the checklist item must be achievable without a key, and new env vars go in deployment.md and env.example.
- B fails the run because no key can be obtained (hard objection).
- Only the Maven analyzers are in scope (Q12); frontend/ is not scanned, so Node, RetireJS and Yarn stay off.
- A and C differ only by an optional, env-gated OSS Index analyzer. A is the smaller change. C adds a concept (two more env vars, a conditional property) that nothing in this run can test.
- Risk to flag for A: without a key the first NVD download can fail with 403/429. Set a generous `nvdApiDelay` and retry settings, and let the data directory persist between runs.
- I pick C by a small margin: the cost is a few lines, enabling is purely opt-in, and it gives the human an upgrade path without a design change. If the panel prefers minimal-implementation, A is acceptable. Both disable OSS Index by default.

## What would change my mind
Evidence that a keyless NVD update cannot complete reliably in this run would make me want a fallback (for example a cached data directory) and push toward A for simplicity. Reading minimal-implementation.md as strict would also push me to A.

## Implementation notes
- pom.xml, dependency-check-maven `<configuration>`: `<nvdApiKey>${env.NVD_API_KEY}</nvdApiKey>`, `<ossindexAnalyzerEnabled>${ossindex.enabled}</ossindexAnalyzerEnabled>` with the property defaulting to false, and `<nodeAnalyzerEnabled>`, `<nodeAuditAnalyzerEnabled>`, `<retireJsAnalyzerEnabled>`, `<yarnAuditAnalyzerEnabled>` and `<assemblyAnalyzerEnabled>` all false.
- Pass the OSS Index credentials through `~/.m2/settings.xml` server ids or env vars, never the pom.
- Document `NVD_API_KEY`, `OSSINDEX_USERNAME` and `OSSINDEX_TOKEN` in deployment.md and env.example, commented out and empty.

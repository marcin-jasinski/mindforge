## Reasoning
- Q10 is answered and binding: "a foreign resource id under one's own kb -> 404", and its constraints say new tests add
  "run report by id and revert". B re-litigates an answered decision.
- Precedent: `RunReportService.java:47` already does `runs.findById(kbId, runId).orElseThrow(() -> new NotFoundException("Run"))`.
  A copies that exact pattern; `NotFoundException` javadoc says "does not exist where the caller looked for it", and
  `GlobalExceptionHandler` already maps it to 404. No new concept.
- Domain semantics: `RevertNotAllowedException` means "the run exists but revert is not offered". Folding "no such run"
  into it (current `isRevertible`) conflates two states; A separates them, which a maintainer will agree with in a year.
- Tenancy is structural (CLAUDE.md): the kbId-scoped port finding nothing IS "not found" in this kb; the API should say so
  consistently across report, revisions and revert.
- C puts a lookup/business decision in the controller (violates thin-controller rule); rejected.
- Risk of A is small: a user-visible 409->404 only for ids that do not exist in the kb; the UI only offers revert for
  listed runs, so no real client relies on 409 for an unknown id.
- Scope: the ticket says test-only, but plan task 20.1 "Fix any gaps found" authorizes a minimal fix; record it in the ticket Notes.

## What would change my mind
Evidence that a client (frontend `run-api.ts`/labels) branches on `REVERT_NOT_ALLOWED` for unknown ids, or an ADR that
fixes revert's error contract to 409 for all failures.

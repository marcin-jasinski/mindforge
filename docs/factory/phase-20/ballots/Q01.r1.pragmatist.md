## Options
| id | option | correct | fit | simple | risk | reversible |
|----|--------|---------|-----|--------|------|------------|
| A  | Per client address only (login + register), no body read | 4 | 5 | 5 | 3 | 5 |
| B  | Per address on both + per-normalised-email bucket on login | 4 | 3 | 2 | 3 | 4 |
| C  | Per email on login, per address on register | 3 | 3 | 3 | 2 | 4 |
| D  | Per (address, normalised email) pair on login, per address on register | 3 | 3 | 2 | 3 | 4 |

## Reasoning
- Plan 20.3 (`docs/project/implementation-plan.md:1720-1721`) asks only for "Caffeine-backed limiter on `/api/auth/login` and `/api/auth/register`; 429 with `Retry-After`". A per-address key meets that in full, and 20.4 "Rate limit triggers" is testable with it.
- A reuses the exact window logic of `api/config/RateLimitInterceptor.java` (a `Cache<K, Window>` + `compute`), only with a `String` address key. No request-body caching, no JSON parse before the controller, no second copy of `AccountService.normalise` in the api layer (B/C/D need all three; a `ContentCachingRequestWrapper` or a filter that reads the body is a new concept in this codebase).
- A covers credential stuffing (many accounts, one address) and mass registration (fresh emails, one address). The email key adds nothing for register (Q01 context says so).
- The per-email bucket (B, C) opens a new failure mode: anyone can lock a victim out of password sign-in by spending the victim's bucket. C has no address limit on login at all, so stuffing across many accounts is not slowed: weaker than A.
- The gap in A (distributed guessing against one account) is real but slow: BCrypt cost >= 12 (CLAUDE.md § Security) and the residual risk can be logged as a follow-up. Adding a per-email bucket later is additive and reversible; removing state and body parsing is not as cheap.
- A depends on Q02 giving a correct client address; that is a separate question and does not change the key choice.

## What would change my mind
A standard or ADR that requires per-account brute-force protection (none in `web-security.md` today), or evidence that Q02 cannot give a trustworthy address, so that a per-address key is useless in production.

## Implementation notes
- New `api/config/AuthRateLimitInterceptor` (or generalise `RateLimitInterceptor` with a key function `Function<HttpServletRequest, String>`; prefer a small separate class to keep R09 untouched), `Cache<String, Window>` keyed by `request.getRemoteAddr()` (after Q02's forwarded-header setup).
- Register in `RateLimitConfig.addInterceptors` with `.addPathPatterns("/api/auth/login", "/api/auth/register")`, POST only; rejected attempts count (R09 precedent).
- Throw the existing `RateLimitExceededException(limit, resetSeconds)` so `GlobalExceptionHandler` answers 429 + `Retry-After` + `RATE_LIMITED`.
- Settings under `mindforge.rate-limits.auth` (budget per Q03). Never log the request body.

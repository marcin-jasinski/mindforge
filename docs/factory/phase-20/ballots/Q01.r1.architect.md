## Options
| id | option | correct | fit | simple | risk | reversible |
|----|--------|---------|-----|--------|------|------------|
| A  | Per client address only, path-scoped interceptor on login + register (reuse R09 fixed-window logic, key = address) | 4 | 5 | 5 | 3 | 5 |
| B  | A, plus a per-normalised-email bucket on login (body cached by a filter, or read in a `RequestBodyAdvice`) | 4 | 3 | 2 | 3 | 4 |
| C  | Per normalised email on login, per address on register | 3 | 3 | 3 | 2 | 4 |
| D  | Per-address in the interceptor, per-email throttle in `AccountService.login` behind a new port | 4 | 2 | 2 | 3 | 3 |

## Reasoning
- Existing pattern: `api/config/RateLimitInterceptor.java` is a `HandlerInterceptor` with a Caffeine fixed window, wired by path in `RateLimitConfig.addInterceptors`. A only changes the key (`String` address instead of `UUID` userId) and adds the two auth paths. No new concept, no new library; matches plan 20.3 wording ("limiter on `/api/auth/login` and `/api/auth/register`").
- B/C need the JSON email before the controller. A `HandlerInterceptor` cannot see it without a body-caching filter (`ContentCachingRequestWrapper` only caches after the body is read, so a custom re-readable wrapper is needed) or a `RequestBodyAdvice` that knows `LoginRequest`. Both add a second mechanism next to the one R09 set; duplicate normalisation (`AccountService.normalise` is `private static`: `email.trim().toLowerCase(Locale.ROOT)`) must then be exposed or copied, which drifts.
- Per-email bucket counts all attempts (R09 precedent), so anyone can lock a victim out of password sign-in by sending the victim's email; that is a new availability defect that A does not have.
- C drops address limiting on login, so credential stuffing from one address is unthrottled; weakest.
- D moves a transport concern (throttling) into the application layer and needs a new port + adapter for Caffeine (hexagonal.md: application imports domain/agent/tx/slf4j only); too much for 20.3.
- Distributed guessing against one account stays open under A; BCrypt cost >= 12 (CLAUDE.md Security) slows each attempt. A per-email bucket can be added later in a `RequestBodyAdvice` without changing A, so A is reversible.
- A depends on Q02 for a correct address; that dependency is the same for B and C on register.

## What would change my mind
Evidence that web-security.md or an ADR asks for per-account throttling, or a skeptic case that distributed guessing is a likely threat here that BCrypt cost does not cover.

## Implementation notes
- New `api/config/AuthRateLimitInterceptor` (or generalise the window logic into a small package-private `FixedWindowCounter<K>` shared by both interceptors; keep `RateLimitInterceptor` behaviour unchanged).
- Key: `request.getRemoteAddr()` (after Q02 forwarded-header handling). Count every POST (rejected ones too), throw `RateLimitExceededException(limit, resetSeconds)` so `GlobalExceptionHandler` answers 429 + `Retry-After` + `RATE_LIMITED`; set `RateLimit-*` headers.
- Register in `RateLimitConfig.addInterceptors` with `.addPathPatterns("/api/v1/auth/login", "/api/v1/auth/register")` (controller is `@RequestMapping("/api/v1/auth")`; plan text says `/api/auth`, see Q08). Settings per Q03.
- Never log the body; log only the address at debug, if at all.

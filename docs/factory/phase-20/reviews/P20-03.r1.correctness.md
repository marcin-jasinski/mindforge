No findings.

Checked:
- `AccountService.authenticate` calls `hasher.matches` exactly once on every path (unknown email, `passwordHash == null`, wrong password, success) and does not return or throw before it. The throw condition `found.isEmpty() || hash == null || !matches` cannot accept the dummy hash, so a password that matches the dummy hash still fails.
- `dummyHash` is made once in the constructor through the port. The only production construction (`AccountConfig.accountService`) uses `BCryptPasswordHasher`, which returns a non-null cost-12 hash. All test constructions use `makeHasher()`, which now stubs `hash` to a non-null value (AC5).
- Null or blank passwords cannot reach the newly added `matches` call on the unknown-email path, because `LoginRequest` has `@NotBlank` on `password`.
- Tests: `anyString()` does not match null, so `verify(hasher, times(1)).matches(eq(pw), anyString())` together with the exact `matches(pw, "dummy-hash")` check proves that the dummy hash is passed and a null hash is not. `recordLogin` is checked as `never()` on every failure, and the success case is kept.

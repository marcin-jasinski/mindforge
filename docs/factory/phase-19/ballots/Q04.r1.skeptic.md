## Reasoning
- Privacy first (ADR 0032: "Knowledge bases are private"; Q09 "The upload path (Q04) must reply privately too"). A DM file
  is seen only by the uploader and the bot, and the DM itself is the private reply channel: no `postEphemeral`, no
  `not_in_channel` failure, no `response_url` expiry. B and E nudge users to post private material into a channel
  (cannot be recalled) and need `channels:history`, so the bot reads every channel message: a wide data surface.
- C lets a user ingest *another user's* file from any channel; the bot token can only fetch files it can see, so a
  shortcut in a channel without the bot fails late, after the modal (a confusing failure that tests will not catch).
- D is private and typed, but adds a slash command the plan does not name ("file upload handler"; scope.md "Commands
  outside the plan" are out), and needs a two-phase flow: `trigger_id` within 3 s, `view_submission` ack within 3 s,
  then download+ingest async and a reply via a `response_url` carried in `private_metadata`. The Java SDK's support
  for `file_input` values in `view.state` is unverified (Slack docs only show Bolt-JS adding it); raw JSON parsing risk.
- A's risks are known and testable as pure units: ignore `bot_id`/own messages and edit/delete subtypes; Socket Mode
  re-delivers unacked events, so ack first and work async; a re-delivery is absorbed by IngestionService's
  "identical upload -> existing id" check. Free-text `lesson_id`/`new_version` parse errors map to fixed refusals,
  same texts as `discord/UploadCommand.java:37-44`. Gate order (allowlist -> rate limit -> resolve -> download) holds.
- Main weakness: A cannot open a modal (message events have no `trigger_id`), so it needs Q03 = implicit/provisioned
  KB (Q03 B/D) - which matches the fact that a Slack user owns exactly one KB until #43 (scope.md "Accounts").

## What would change my mind
Q03 choosing a Block Kit modal KB select for every command (then D unifies the flow), or Q02 rejecting DMs; proof that
the Java SDK exposes `file_input` files in `view_submission` state would lower D's risk.

## Implementation notes
- `dev.mindforge.slack.UploadHandler` registered as `app.event(MessageEvent.class, ...)` (plus `file_share` subtype
  routing); act only when `channel_type == "im"`, `files` non-empty, no `bot_id`; exactly one file, else fixed refusal.
- Scopes: `im:history`, `files:read`, `chat:write`; App Home "Messages tab" on; event subscription `message.im`.
- Text grammar: `lesson_id=<id>` and `new_version` tokens only; anything else -> fixed `LESSON_IDENTITY`-style refusal.
- Order: allowlist (team + `user_team`, per Q02) -> rate limit (one count per upload, D11) -> `ExternalIdentityService.resolve`
  -> KB (Q03, then `requireOwner`) -> size check from `file.size` before download -> capped download (Q08) ->
  `IngestionService.ingest(new DocumentUpload(kbId, userId, UploadSource.SLACK, ...))` -> one DM reply "queued".
- Unit tests: channel file ignored, bot message ignored, multi-file refused, bad text refused, re-delivery idempotent.

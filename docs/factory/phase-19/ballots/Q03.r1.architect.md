## Reasoning
- Today a Slack user can own exactly one KB: ADR 0027 (no web sign-in), no bot command creates one, and the CLI does
  not create KBs (`cli/PipelineCommandRunner.java:134`, `QuizCommandRunner.java:95` only call `requireOwner`). A
  selector (A/B) would select from a list of one: speculative generality (`minimal-implementation.md`).
- ADR 0030 rejected "only or oldest, implicitly" because a user with several KBs "gets uploads ... in a knowledge base
  they did not pick, or is locked out". E never picks for the user: with more than one it refuses, so no wrong-KB writes.
  The lock-out case cannot occur until #43, which then owns the selection design (likely A, value = id).
- ADR 0030 itself names "an optional `kb` option that defaults to the only knowledge base" as a compatible later
  addition; E is the Slack form of that rule with the UI deferred. It keeps the id discipline: every downstream call
  gets a `kbId` from `KnowledgeBaseService.list`, then `requireOwner(kbId, userId)` (same path as `DiscordKnowledgeBases.java:85`).
- A costs a `view_submission` route, private metadata to carry the command, and does not fit file upload (a
  `file_shared`/message event has no `trigger_id`, so Q04 would need a button then a modal). breakdown.md notes W06/W07 grow to M/L.
- C/D rely on names (non-unique) or a stored pointer, both explicitly rejected in ADR 0030 for reasons that are not
  Discord-specific.
- Needs its own ADR (Slack scope) stating: why implicit is safe here (one KB by construction), the fixed refusal for
  0 or >1, and that #43 must add a selection (Block Kit select, value = id) before it can give a user a second KB.

## What would change my mind
Evidence that a Slack user can own more than one KB in Phase 19 (a CLI or bot path that creates one), or a human rule
that every Slack command must show the KB explicitly; then A.

## Implementation notes
- `dev.mindforge.slack.SlackKnowledgeBases` with `Optional<UUID> resolveKnowledgeBase(UUID userId, SlackReply reply)`:
  `knowledgeBases.list(userId)`; size == 1 -> `kbId = only.id()`, `knowledgeBases.requireOwner(kbId, userId)`, return;
  else reply one fixed text (e.g. "This command needs exactly one knowledge base. Selection is not available in Slack yet.")
  and return empty. Never look up by name; never store a selection.
- Called by `SlackCommandHandler` after identity resolution, before `/mf-ask`, `/mf-quiz start`, and the upload handler.
  Quiz answers use the KB stored with the quiz session (as ADR 0030 Consequences).
- Tests (`unit/slack/SlackKnowledgeBasesTest`): one KB -> its id and `requireOwner` called; two KBs -> fixed refusal,
  no service call; zero -> fixed refusal; `requireOwner` throws -> fixed refusal.
- ADR `0033-slack-commands-act-on-the-users-only-knowledge-base.md` (format of newest ADR); link #43 in its Consequences.

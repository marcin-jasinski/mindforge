## Reasoning
- pom.xml has no websocket or tyrus dependency today, so any choice adds a new WebSocket stack (grep of pom.xml found none).
- A brings javax.websocket-api next to Boot's Jakarta namespace and a second container-style client; avoidable conflict risk.
- C matches the namespace but Tyrus 2.x pulls the Jakarta websocket API and Tyrus modules (more jars, possible clash with Boot's embedded server's websocket API if on classpath).
- B is one small jar (org.java-websocket:Java-WebSocket, with slf4j), no javax/jakarta API, no OkHttp involvement, so the okhttp-jvm 5 ordering (pom.xml:103-109, ADR 0025) is untouched.
- Slack types stay in dev.mindforge.slack; the backend is a one-line choice (SocketModeClient.Backend.JavaWebSocket), so reversible to A or C.
- Verify with mvn dependency:tree that Java-WebSocket's slf4j matches Boot's, and run OutboundHttpGuardTest.
## What would change my mind
Dependency tree shows a conflict from Java-WebSocket, or Bolt's JavaWebSocket backend proves unreliable on reconnect in a test.

## Reasoning
- ADR 0028 (`docs/adr/0028-...md`) is the precedent: fail-closed list, pure value, check before resolution, fixed reply. B keeps all four and carries its *intent* (only members of admitted orgs get an account and model spend) to Slack's two-team payload shape.
- Slack docs say slash commands run only for members of the installing workspace, but external members can interact with messages the app posts, and shared-channel message/file events carry `user_team` != `team`. The upload handler (Q04) and quiz interactions (Q05/Q12) are event/interaction paths, so A leaks there. B closes it with one more set lookup on the same set.
- C copies ADR 0028's DM rule without its reason. ADR 0028 rejects DMs because a DM "has no guild and no roles" and a stored link "proves a past check, not current membership". A Slack DM command carries `team_id` and the caller's team on every call, so membership is checked on every call. ADR 0028 § Consequences asks that DM use get "a new decision with its own explicit allowlist"; the Slack team allowlist is that allowlist, and the new ADR records it.
- D and E are speculative generality (`docs/standards/global/minimal-implementation.md`): no requirement names channel scoping or Grid org-wide installs; both can be added later without changing B's rules (ADR 0028 makes the same "add later" argument for leave-on-join).
- Grid: ignore `enterprise_id`; an org-wide install event with null `team_id` is rejected (fail closed). Grid users in an allowed workspace pass because both team ids are that workspace.
- Fits Q01 option A: if both teams must be in a small allowed set, the user id alone is unique in practice.

## What would change my mind
Evidence that the caller's team is absent from a payload type we must handle (no `user_team`/`user.team_id`) and a `users.info` call is needed before the gate, which would move the check after an API call; I would then accept C/rejecting that payload type instead.

## Implementation notes
- `dev.mindforge.slack.SlackAllowlist` record: `record SlackAllowlist(Set<String> teamIds)` with `boolean admits(String payloadTeamIdOrNull, String callerTeamIdOrNull)`; false when either is null/blank or not in `teamIds`. Javadoc cites the new ADR.
- `AppProperties.Slack.allowedTeamIds` (`mindforge.slack.allowed-team-ids`, env `SLACK_ALLOWED_TEAM_IDS`); `@AssertTrue` "allowed-team-ids must not be empty when the bot token is set", mirroring `AppProperties.Discord`.
- Slash command: payload team = `team_id`; caller team = `user_team` if present, else `team_id` (Slack restricts slash commands to installing-workspace members). Events: `team` / `user_team` (fallback `user_profile.team`); block actions: `team.id` / `user.team_id`. Missing caller team on events/actions -> reject.
- Gate order in `SlackCommandHandler`: allowlist -> rate limit -> ack -> resolve. Fixed reply text names no workspace.
- New ADR `docs/adr/0033-slack-commands-admitted-when-workspace-and-caller-team-are-allowed.md` (newest format, like 0028): Considered options A, C, D, E with the reasons above.
- Tests (`src/test/java/dev/mindforge/unit/slack/SlackAllowlistTest`): allowed/allowed admits; foreign caller team in allowed workspace rejected; null team rejected; DM (same team) admitted; empty list fails `AppProperties` validation.

## Reasoning
- Today a Slack user owns exactly one KB: `ExternalIdentityService.resolve` inserts one (line ~52), the web is closed to bot accounts (ADR 0027), and no CLI path creates a KB (`cli/PipelineCommandRunner.java:134` only calls `requireOwner`). So any modal path (A, B) is code no real user can reach in Phase 19.
- A breaks in operable ways: `trigger_id` expires after 3 s, and first contact runs a provisioning transaction plus `list` before `views.open`; a slow DB gives `expired_trigger_id` and the user sees nothing. The file upload (Q04) is an event with no `trigger_id`, so A needs an extra button round trip there. Each `view_submission` adds a payload parser (state values, `private_metadata`) whose user id must come from the payload, not from metadata - more untrusted input to get right.
- B ships both paths; the modal branch is dead in practice, so its bugs will be found in production after #43, not in tests.
- ADR 0030 rejected the implicit default because "a user with several gets uploads ... in a knowledge base they did not pick, or is locked out". E never picks for a user with several: it refuses loudly ("Several knowledge bases; selection in Slack is not available yet."), so no wrong-KB writes. Lock-out is impossible today and visible if it happens.
- E keeps the security boundary uniform: the id still goes through `requireOwner(kbId, userId)` and `kbId` first on every port call; a KB deleted between `list` and use gives `NotFoundException` -> the same fixed reply.
- E is fully reversible: adding A's modal for the several-KB case later is additive (same as ADR 0030's note that a required option can become optional).
- Testability: E is one pure branch on `list(userId).size()`, unit-testable with plain Mockito (0, 1, 2 KBs; foreign/deleted id).
- E needs its own ADR (constraint in the question): reason = Slack has no typed options and a Slack user cannot own a second KB before #43.

## What would change my mind
Evidence that a Slack user can own more than one KB in Phase 19 (an operator CLI create, or #43 scheduled into this phase) -> A, with the modal opened before provisioning-heavy work.

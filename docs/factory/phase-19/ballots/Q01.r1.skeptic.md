## Options
| id | option | correct | fit | simple | risk | reversible |
|----|--------|---------|-----|--------|------|------------|
| A  | `user_id` alone (`U0123ABCD`) | 3 | 5 | 5 | 2 | 2 |
| B  | `team_id`+`user_id` concatenated (`T0123U0456`) | 4 | 4 | 5 | 3 | 3 |
| C  | `team_id-user_id` with `-`, `ExternalAccounts` admits one `-` for SLACK only | 5 | 4 | 4 | 4 | 3 |
| D  | `enterprise_id` if present else `team_id`, plus `user_id` | 3 | 3 | 2 | 2 | 2 |
| E  | store `team_id:user_id` in `external_id`, email from concatenation without separator | 4 | 3 | 3 | 4 | 3 |

## Reasoning
- Failure of A is silent and is a security failure: `ExternalIdentityService.resolve` (lines 41-44) returns whatever
  user owns `(platform, external_id)`. If two admitted workspaces (or a Slack Connect guest that Q02 does not block)
  ever share a `U…` id, the second person gets the first person's account and knowledge bases. Nothing logs it; no test
  can find it. Its safety depends fully on Q02 and on the allowlist never listing two teams. A key that is correct only
  while another decision holds is a trap for a later config change.
- A also hurts operability: with no team in the key, an operator cannot tell which workspace an account came from, so
  removing a team from the allowlist cannot be followed by `WHERE external_id LIKE 'T…-%'` cleanup or audit.
- D breaks on a real event: when a workspace joins an Enterprise Grid, `enterprise_id` appears and the key flips from
  `T…` to `E…`; every existing user is silently re-provisioned as a new empty account (data "loss"). Org-wide installs
  are also out of scope for a single-bot-token Socket Mode app (Q02 context).
- B is unique only by convention (`T0U1`+`U2` vs `T0`+`U1U2`): improbable, but it cannot be split back, so a later
  Slack reminder DM (`ReminderService` sends `identity.externalId()` as the DM target, line 46) could not recover the
  user id. C keeps both parts recoverable with a trivial `split("-", 2)`.
- ':' (and the plain colon form of C) is rejected: `syntheticEmail` puts the id in the local part
  (`ExternalAccounts.java` line 29); ':' is not legal there unquoted. '-' is legal and the platform prefix is a fixed
  enum name without '-', so `slack-t0123-u0456@users.invalid` stays unambiguous.
- Cost of C: `ExternalAccountsTest.shouldRefuseABlankIdAndAnIdOutsideLettersAndDigits` pins `"12-34"` as rejected for
  DISCORD. Keep that by making the hyphen form SLACK-only, so the Discord rule and its test do not change.
- Length: `T` id (~11) + 1 + `U/W` id (~11) is far under `VARCHAR(64)` (V8) and 255 for the email. No migration.
- Use the caller's own team (`user_team` / `user.team_id`), not the channel `team_id`, so a key always names the home
  workspace of the person; this must agree with Q02's check.

## What would change my mind
Evidence that Q02 picks a single fixed team id (one-element allowlist enforced by config validation) and that Slack
guarantees global user-id uniqueness would make A acceptable; a ruling that the domain rule must not change favours B.

## Implementation notes
- `ExternalAccounts`: add `private static final Pattern SLACK_ID = Pattern.compile("[A-Za-z0-9]+-[A-Za-z0-9]+");`
  and choose the pattern by platform (`platform == ExternalPlatform.SLACK ? SLACK_ID : EXTERNAL_ID`). Add a static
  `slackExternalId(String teamId, String userId)` in the domain that validates each part is `[A-Za-z0-9]+` and returns
  `teamId + "-" + userId` (no lowercasing in the stored value; Slack ids are upper case, email is lowercased).
- `ExternalAccountsTest`: add `shouldDeriveTheSyntheticEmailOfASlackUser` (`"T0123-U0456"` ->
  `slack-t0123-u0456@users.invalid`), reject `"T0123-"`, `"-U1"`, `"T1-U2-U3"`, `"T1:U2"` for SLACK; keep `"12-34"`
  rejected for DISCORD.
- Slack adapter (`dev.mindforge.slack`): `externalIdentityService.resolve(ExternalPlatform.SLACK,
  ExternalAccounts.slackExternalId(callerTeamId, userId), displayName)` after the allowlist check.
- Record in the Slack ADR: key = caller home team + user id; Grid users get one account per workspace (accepted cost).

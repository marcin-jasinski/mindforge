## Options
| id | option | correct | fit | simple | risk | reversible |
|----|--------|---------|-----|--------|------|------------|
| A  | bolt-socket-mode + Tyrus 1.x (javax) | 3 | 2 | 3 | 3 | 4 |
| B  | bolt-socket-mode + Java-WebSocket backend | 4 | 4 | 5 | 3 | 5 |
| C  | bolt-jakarta-socket-mode + Tyrus 2.x | 4 | 4 | 3 | 3 | 4 |
## Reasoning
- pom.xml has no websocket dependency today, so any choice is new; fewest jars matches tech-stack.md minimalism and docs/standards/global/minimal-implementation.md.
- A pulls javax.websocket-api into a Jakarta (Boot 4) app: namespace split, a concept a maintainer questions.
- C is namespace-correct but adds Tyrus 2 (container, server-side SPI jars) for a client-only need.
- B is one small jar with no javax/jakarta API, no OkHttp interaction (JDA okhttp-jvm 5 first, ADR 0025). The backend sits behind Bolt, so swapping to C later is a pom and one-line change.
- Slack types stay in dev.mindforge.slack in all options.
## What would change my mind
Dependency tree or a spike showing Java-WebSocket reconnect or ping instability, or Bolt marking it unsupported.
## Implementation notes
Add com.slack.api:bolt, bolt-socket-mode, org.java-websocket:Java-WebSocket; set SocketModeClient.Backend.JavaWebSocket in dev.mindforge.slack config; verify `mvn dependency:tree` and okhttp order; add a row to tech-stack.md "Key Dependencies Summary".

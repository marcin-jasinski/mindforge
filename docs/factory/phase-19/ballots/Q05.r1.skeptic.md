## Options
| id | option | correct | fit | simple | risk | reversible |
|----|--------|---------|-----|--------|------|------------|
| A  | `/mf-quiz start`, `/mf-quiz answer <text>` | 4 | 5 | 5 | 4 | 5 |
| B  | Buttons + modal, interaction handlers | 4 | 3 | 2 | 2 | 3 |
| C  | `/mf-quiz` start, `/mf-quiz <text>` answers | 2 | 3 | 4 | 2 | 4 |

## Reasoning
- A mirrors Discord `/quiz start` and `/quiz answer` (QuizCommand.java), so one parse and one QuizService path; the explicit verb makes intent unambiguous.
- C is ambiguous: an answer text equal to "start" or empty text is mistaken for a command. A mistaken start could drop the current session and lose a graded answer. Hard to test all edges.
- B adds `block_actions` and `view_submission` handlers, trigger_id 3 s expiry, and modal state that must carry the session id. Each is an ownership-check surface (plan 19.3: user A must not reach user B's session). Ephemeral messages cannot be reliably updated long after posting. More failure modes, and Q05 is only medium impact.
- Both A and C must ack in 3 s and post the LLM-graded result via response_url (never call a model in a transaction). Same risk for all; not a differentiator.
- Long answers: Slack allows long slash text (multi-line via shift+enter), so the A limit is usability, not correctness. B can be added later without breaking A (reversible).
- Ownership: every subcommand goes through QuizService.next/answer owned(...); output only NextQuestion and Graded text.

## What would change my mind
Evidence that Slack slash text truncates or blocks multi-line answers in practice, making answering unusable.

## Implementation notes
Slack adapter `SlackQuizCommand`: split text on first whitespace; verb `start` or `answer`; unknown or empty verb returns an ephemeral usage line; empty answer text rejected. Session pointer per Q12/D05 keyed on internal user id. Ephemeral replies via one reply helper.

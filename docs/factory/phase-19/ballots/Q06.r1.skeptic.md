## Reasoning
- pom.xml has no tyrus or websocket dependency today; only the JDA okhttp ordering rule (pom.xml:103-109, ADR 0025) is a classpath constraint.
- A adds a javax.websocket API jar and Tyrus 1.x on a Jakarta Boot 4.1 app: dead namespace, stale line, extra transitive jars.
- C puts a second jakarta.websocket API on the classpath next to the embedded server's own websocket classes. This risks duplicate or mismatched classes and Boot BOM clashes, and the failure shows only at runtime.
- B adds one small jar (org.java-websocket:Java-WebSocket), with no javax/jakarta API and no service-loader discovery. Bolt supports it officially as a Backend enum value. The risk is less field use than Tyrus; mitigate with a reconnect test.
- Skeptic checks, all to run in W02: mvn dependency:tree for duplicates, OutboundHttpGuardTest green, okhttp-jvm 5 still first, and a startup smoke test.
## What would change my mind
Dependency tree showing Java-WebSocket pulls conflicting jars, or Slack reconnect failures with it (known issues) favouring Tyrus 2.x.

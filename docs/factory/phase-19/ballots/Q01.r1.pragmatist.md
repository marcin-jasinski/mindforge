## Options
| id | option | correct | fit | simple | risk | reversible |
|----|--------|---------|-----|--------|------|------------|
| A  | `user_id` alone (`U0123ABCD`) | 3 | 5 | 5 | 3 | 2 |
| B  | `team_id`+`user_id` concatenated, no separator (`T0123U0456`) | 5 | 4 | 5 | 4 | 2 |
| C  | `team_id:user_id`, widen `ExternalAccounts` regex for `:` | 5 | 2 | 3 | 4 | 2 |
| D  | `enterprise_id` or `team_id`, plus `user_id` | 4 | 3 | 3 | 3 | 2 |

## Reasoning
- Every option is equally hard to reverse: the key is persisted in `external_identities` (PK `(platform, external_id)`,
  `V8__create_external_identities.sql` line 8) and in `users.email`. So pick the one that is correct by design now.
- A is correct only while exactly one workspace is ever admitted. `mindforge.slack.allowed-team-ids` (Q02) is a list,
  and Slack Connect guests from listed partner teams can reach the bot; Slack documents user ids as unique per
  workspace only. A collision gives one person another person's account and knowledge bases - a silent tenancy bug
  that no test would catch. Correctness beats the one-line saving.
- B costs one string concatenation in the Slack adapter and no change to anything else: it passes the existing
  `[A-Za-z0-9]+` rule in `domain/model/ExternalAccounts.java`, fits VARCHAR(64) (~22 chars), and keeps ADR 0027's
  `slack-<externalId>@users.invalid` shape ("Phase 19 reuses the same rule with its own platform prefix").
  We never need to split the value back - it is an opaque key - so "split only by convention" does not matter.
- C adds a domain rule change plus a test change for a separator nobody reads. Not needed.
- D adds a branch on `enterprise_id` for Grid, a deployment shape this project does not target; a Grid user getting
  one account per workspace under B is an acceptable, safe outcome (no shared data across workspaces by accident).
- Use the caller's own team (`user.team_id` / `user_team`), not the channel's `team_id`, so a Connect guest keys
  under their home team; this aligns with Q02 option B.

## What would change my mind
A ruling in Q02 that only one workspace can ever be admitted and Connect guests are always rejected would make A
correct in practice and I would accept it as the simpler, Discord-shaped choice.

## Implementation notes
- In the Slack adapter (`dev.mindforge.slack`), a private static helper, e.g.
  `static String externalId(String userTeamId, String userId) { return userTeamId + userId; }`, used for every
  `ExternalIdentityRepository` lookup/link with `ExternalPlatform.SLACK`.
- Team id source: `user_team` (slash command payload) / `user.team_id` (events), falling back to `team_id` only when
  absent. Unit test: same user id under two team ids resolves to two different identities.
- No migration, no change to `ExternalAccounts` or `ExternalAccountsTest`. Record the key shape in the Slack ADR.

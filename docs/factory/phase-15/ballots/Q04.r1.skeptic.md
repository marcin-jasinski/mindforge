## Options
| id | option | correct | fit | simple | risk | reversible |
|----|--------|---------|-----|--------|------|------------|
| A  | Act as `KnowledgeBase.ownerId`; no user argument; ownership check is by construction | 4 | 3 | 5 | 2 | 4 |
| B  | `--user <email>`; application service resolves the user (NotFoundException), then `requireOwner(kbId, user)`; no password | 5 | 4 | 4 | 4 | 5 |
| C  | `--user <email>` + password prompt via `AccountService.authenticate` | 4 | 3 | 2 | 3 | 4 |
| D  | Fixed operator/system user from config (e.g. `mindforge.cli.user`) | 3 | 2 | 3 | 2 | 4 |

## Reasoning
- Trust boundary is the DB credentials (question Context), so the check protects against operator error, not attackers. Its value is to catch the wrong KB, not to authenticate.
- A: `requireOwner(kbId, kb.ownerId())` can never fail (`KnowledgeBaseService.java:35-47` compares `ownerId` to the same `ownerId`). A copy-paste of the wrong `--kb` silently ingests into another user's KB, sets `uploaded_by` to that user, and in the quiz CLI writes quiz scores into that user's study progress (`study.recordQuizScore`). Nothing reports the error. That is a data-integrity failure that nobody detects. It is not a hard objection: scope only says "act as a definite user that owns the KB", and A does that.
- B: the operator states who they act as. A KB mismatch fails with the existing typed `NotOwnerException`, and an unknown email fails with `NotFoundException`, so the negative paths are easy to test with plain Mockito. Emails must be normalised the same way as `AccountService.normalise` (lowercase/trim), or the lookup fails for mixed-case input. OAuth-only users can use it.
- C: `authenticate` filters out `passwordHash() == null` (`AccountService.java:40-46`), so OAuth-only users are locked out. A prompt breaks "scripted ingestion" (scope Goal) unless the password comes from an env var or stdin, which adds a new secret-handling surface. It also has a side effect: `users.recordLogin` changes last-login on every CLI run. And it adds no protection, because DB credentials bypass it.
- D: a synthetic user owns no KB, so it fails `requireOwner` or needs a bypass. It also needs a seed row (migration). Rejected.
- Rate limit absence (`RateLimitInterceptor`, API adapter) is the same for all options. The operator pays the cost directly. Accept it, and note it in deployment.md.

## What would change my mind
Evidence that KBs are single-tenant in practice (one user per deployment) would make B's mismatch guard worthless, and then A wins on simplicity. A plan or ADR text that forbids extra CLI arguments would have the same effect.

## Implementation notes
- `AccountService.byEmail(String email): User`: normalise, then `users.findByEmail(...)`, else throw `new NotFoundException("User")`. Put this in the application layer, not in the runner. Do not call `recordLogin`.
- Runners: `PipelineCommand` takes `--file --kb --user`, and `QuizCommand` takes `--kb --user`. Then `User u = accounts.byEmail(user); knowledgeBases.requireOwner(kbId, u.userId());` before `IngestionService.ingest(new DocumentUpload(..., u.userId(), UploadSource.CLI?...))`. Check the `UploadSource` enum for a CLI value. Q07/W03 owns that.
- On a missing `--user`, unknown email or `NotOwnerException`, print one line to stderr and exit non-zero. Do not print whether the KB exists for another user beyond "not found or not yours".
- Tests (unit, Mockito): unknown email gives a non-zero exit and no ingest. KB owned by another user gives `NotOwnerException`, no ingest and no quiz session. A mixed-case email resolves.

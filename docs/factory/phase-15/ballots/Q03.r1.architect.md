## Reasoning
- The checklist entry point (implementation-plan.md line 1455) is `java -jar mindforge.jar --spring.profiles.active=cli`. A selects the runner by argument, so the same command works for both runners.
- C changes the entry point to `cli,pipeline` / `cli,quiz`. This contradicts the checklist wording.
- D adds scripts that do not exist and that deployment.md does not mention. This is speculative (minimal-implementation).
- B selects implicitly. A missing `--file` would silently start the quiz.
- A fits thin adapters. Each runner checks `args.getNonOptionArgs()` and returns if the command is not its own. No command framework is added.
- `mindforge-pipeline` and `mindforge-quiz` stay as plan labels. The concrete subcommands are `pipeline` and `quiz`.
- Unknown or missing command: print usage and exit non-zero.
## What would change my mind
- A requirement for distributable wrapper scripts, or a need to run both runners in one process.
## Implementation notes
- `dev.mindforge.cli.PipelineCommandRunner` and `QuizCommandRunner`, both `ApplicationRunner` beans (not `CommandLineRunner`) in a `@Configuration` with `@Profile("cli")`. They take `ApplicationArguments`, which parses `--file` and `--kb`.
- A shared small `CliCommand` helper, or one `CliDispatcher`, owns the unknown-command usage and exit code. Use `SpringApplication.exit` or an `ExitCodeGenerator`.
- With the `cli` profile, set `spring.main.web-application-type=none` in application-cli.yml.

## Reasoning
- PipelineConfig.java injects the concrete SseProgressNotifier into IngestPipeline, LintService and RunWorker (lines 125, 136, 144). The port ProgressNotifier (domain/port) already exists, so these three parameters should take the port: this fixes a small hexagonal leak and is what A needs.
- Only RunController needs the concrete type (to subscribe). Under D02 it is not loaded in the non-web cli context, so the SSE bean can be `@Profile("!cli")` with the console one `@Profile("cli")`.
- D01 runs the pipeline in the CLI JVM, so A fits and step progress is available. C drops the steps that plan 15.1 requires. B adds a registry with a single user.
- Port stays JDK-only and best-effort; the console notifier must not throw and should filter by the CLI's run id (D01).

## What would change my mind
If a second in-process consumer of progress appears (B becomes justified), or Q01 changes to enqueue-only (then C is forced).

## Implementation notes
- PipelineConfig: change the three `SseProgressNotifier progressNotifier` params to `ProgressNotifier`. Keep the `SseProgressNotifier progressNotifier()` bean but add `@Profile("!cli")`. RunController keeps the concrete type.
- `dev.mindforge.cli.ConsoleProgressNotifier implements ProgressNotifier` (print `step done/total` to stdout, only for a configured runId, catch all exceptions); bean in the `@Profile("cli")` CliConfig. Because the run id is known only after ingest, make the filter a settable/`kbId`-scoped check, or print every RunProgress for the kb (simplest).
- Test: plain unit test for output and no-throw; the cli context-load test (D02) asserts the bean type.

## Reasoning
- The danger is the sweep, not the worker. `RunWorker.sweep` fails every RUNNING run not in this JVM's `active` set (RunWorker.java `sweep()`/`settle()`), and `RunWorkerTriggers.onReady` runs it at startup. Any CLI profile that keeps `RunWorkerTriggers` (incl. the quiz CLI) fails a live server's in-flight runs on start. So the `cli` profile must drop the whole `RunWorkerTriggers` bean (PipelineConfig.java:153), not only the periodic part.
- A transient CLI that never sweeps is not "a second permanent worker": deployment.md:62-63 already accepts brief overlap because commits are fenced (ADR-0015 Amendment: "Each commit updates the run only from its expected status while it holds the lease; 0 rows aborts"). The `active_run_id` lease still serializes writers per KB across processes, so wiki integrity holds even if an operator ignores the doc.
- Remaining failure if a server IS live: the server's sweep fails the CLI's run within PT1M, re-queues it, and the server regenerates it (double cost, CLI reports FAILED "interrupted"). Detectable (CLI prints the reason), not corrupting. Document it in deployment.md#one-live-instance.
- B: step progress is not persisted (scope.md "Step progress is not persisted on `ingest_runs`"), so 15.1 is unmet; with no server the run stays QUEUED forever. Hard objection.
- C: a DB "is someone else working" check is a lease in disguise; out of scope (scope.md Out of scope). A2's RUNNING-row check gives false safety (an idle server has no RUNNING row) and a crashed server's stale RUNNING row would block the CLI until a server restart. Not worth it.
- Edge cases A must handle (testable): dedup returns an existing document id and queues NO run -> the CLI must not wait forever (check `latestForDocument` run was created by this call / is not terminal-old; print "already ingested", exit 0); `drain` claims the OLDEST queued run of the KB, which may not be the CLI's -> wait on the CLI's own run (`latestForDocument(kbId, docId)`), not the first one claimed; `drain`'s finally re-drains the KB, so a further queued run may be claimed just before exit and left RUNNING -> the next server startup sweep re-queues it (acceptable, document it).
- Exit code: 0 on COMPLETED, non-zero on FAILED or timeout; no model call inside a transaction is unchanged since the pipeline itself is reused.

## What would change my mind
Evidence that the `active_run_id` lease does not fence a cross-process writer, or a plan change that drops "prints step progress" (then B).

## Implementation notes
- `PipelineConfig.runWorkerTriggers`: add `@Profile("!cli")` (Spring `@Profile` on the `@Bean` method; configuration stays in `@Configuration`). Keep `RunWorker` bean in all profiles.
- `dev.mindforge.cli.PipelineCommand implements CommandLineRunner`, `@Profile("cli")` bean in a `CliConfig` `@Configuration`: `UUID docId = ingestionService.ingest(upload); runWorker.drain(kbId);` then poll `ingestRunRepository.latestForDocument(kbId, docId)` every ~1 s until COMPLETED/FAILED, with a timeout property `mindforge.cli.run-timeout` (default e.g. PT30M).
- Quiz CLI gets no worker side effects: with the triggers bean gone, starting it touches no runs. Integration test: start a `cli`-profile context with a RUNNING run row from "another process" and assert it is still RUNNING after context ready.
- deployment.md: "Stop the server before `--spring.profiles.active=cli` for the pipeline; otherwise its sweep fails the CLI's run within one sweep interval and re-queues it."

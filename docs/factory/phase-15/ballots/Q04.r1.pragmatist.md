## Reasoning
- A KB has exactly one owner (`domain/model/KnowledgeBase.java:12 UUID ownerId`); there is no sharing. Only the owner
  can pass `requireOwner` (`KnowledgeBaseService.java:34-46`). So with `--kb` alone the acting user is already fully
  determined: B can only add an error path ("wrong user"), not a new capability.
- A matches the plan's argument list exactly (`--file <path> --kb <id>`; 15.2 none), so no plan change and no new flag.
- A still does a real check: the KB must exist (`NotFoundException`), and `uploadedBy`, the quiz session `userId` and
  `recordQuizScore` all get a definite user that owns the KB (scope: "the CLI must act as a definite user that owns the KB").
- The trust boundary is DB credentials (question Context); a `--user` without password (B) authenticates nothing more
  than A. C adds a terminal password prompt, blocks OAuth-only users, and adds console-I/O code for zero real protection.
- D needs a migration and a fake user that does not own the KB — fails ownership; incorrect.
- Cost of A: one application-service method (`KnowledgeBaseService.owner(kbId)`) — thin adapter rule kept.
- Reversible: adding `--user` later (B) is additive, nothing to undo.
- No hard objection on A: ownership is satisfied by construction, not skipped; the "every controller method checks"
  rule exists to stop a caller acting on another user's data, and here there is no other caller identity to check.

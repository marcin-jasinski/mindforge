## Options
| id | option | correct | fit | simple | risk | reversible |
|----|--------|---------|-----|--------|------|------------|
| A  | web-application-type none in application-cli.yml + @Profile("!cli") on web-only beans | 4 | 4 | 3 | 4 | 4 |
| B  | keep web stack, server.port 0 | 3 | 3 | 5 | 2 | 4 |
| C  | main() picks web type from args | 2 | 2 | 2 | 3 | 3 |
## Reasoning
- B: a short-lived CLI process still serves the full API (and auth endpoints, OAuth config) on a random port; unneeded attack surface and wasted startup. Failure is silent.
- C: hidden logic in main(), not covered by profile; args parsing duplicates Spring's own profile handling; still needs the bean exclusions.
- A: no server, no exposure. Risk: @RestController/@ControllerAdvice classes in dev.mindforge.api are component-scanned regardless of web type and may depend on beans from the excluded configs (SecurityConfig, RateLimitConfig). Only infra SseProgressNotifier uses SseEmitter outside api (it is a plain object; fine).
- Mitigation: a no-Spring-web context-load test with profile cli (Testcontainers) so a missing @Profile fails at build, not at runtime.
## What would change my mind
Evidence that controllers/advice cannot be cleanly excluded (e.g. many cross-deps), making B cheaper.
## Implementation notes
src/main/resources/application-cli.yml: spring.main.web-application-type: none. @Profile("!cli") on SecurityConfig, SpaConfig, RateLimitConfig, ApiDocsConfig, JwtFilter, and api controllers/advice/interceptor (or one marker). Add CLI context-load integration test.

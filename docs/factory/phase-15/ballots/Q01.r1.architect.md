## Reasoning
- ADR-0015 Amendment (lines 45-54) and deployment.md:57-64 make the sweep a per-instance duty that assumes one live
  instance. Any CLI profile that keeps the startup/periodic sweep (A2) sweeps a live server's runs: a blocker.
- Plan 15.1 ("prints step progress") needs the run to execute in the CLI process, where `ProgressNotifier` callbacks
  are visible; step progress is not persisted on `ingest_runs` (scope.md). That rules out B as incorrect.
- C is the heartbeat lease the scope puts out of scope; it would need an ADR-0015 amendment.
- Between A and D: `IngestionService.ingest` commits through `TransactionOperations` before it returns
  (IngestionService.java:88), so a direct `runWorker.drain(kbId)` after `ingest` returns is outside any transaction
  ("never call a model inside a DB transaction" holds) and uses the exact same `RunWorker.drain -> IngestPipeline.run`
  path as an upload. D keeps `RunWorkerTriggers` one class with one meaning ("the server instance's wake-ups") instead
  of splitting it into two trigger classes or adding profile flags to methods (A). Nothing in the cli profile wakes the
  worker on its own, so the quiz CLI touches no runs at all.
- The KB lease (`claim` with `active_run_id IS NULL`) and fenced commits still protect the wiki if a user ignores the
  documented rule; the residual hazard is the server's periodic sweep failing the CLI's run, which the doc states.
- Reversible: once a heartbeat lease exists, the profile guard can be removed with no other change.

## What would change my mind
Evidence that the plan expects the CLI to coexist with a live server (then only B is honest, with status-only output
and an explicit plan change), or that other ballots show the AFTER_COMMIT path is required for the dedup case.

## Implementation notes
- `infrastructure/config/PipelineConfig.java`: add `@Profile("!cli")` to `runWorkerTriggers(...)` (bean method).
  `@EnableScheduling` stays; with no `@Scheduled` bean nothing fires.
- `cli/PipelineCommand` (`CommandLineRunner`, `@Profile("cli")`, wired in a `cli/CliConfig` `@Configuration`):
  `UUID documentId = ingestion.ingest(upload); IngestRun run = runs.latestForDocument(kbId, documentId)...;`
  if the run is already terminal (identical document dedup), print and exit; else `worker.drain(kbId)` and poll
  `runs.findById(kbId, run.runId())` until `COMPLETED`/`FAILED` (bounded wait; exit code 0/1). Note drain may first
  execute an older `QUEUED` run of the same KB - that is correct ordering; keep waiting for our run id.
- Step progress: a CLI `ProgressNotifier` (see Q05) prints `RunProgress(step, done, total)` for the run id.
- On exit call `worker.stop()` (the `ContextClosedEvent` hook lived in `RunWorkerTriggers`).
- `deployment.md`: new "CLI" section - the CLI is a live instance; stop the server (or use a separate database)
  before `java -jar mindforge.jar --spring.profiles.active=cli`; it runs no sweep.

## Reasoning
- D01 fixes that the CLI runs the ingest in-process, drains the worker, waits for COMPLETED or FAILED, prints step progress and then calls stop(). C would drop the run at exit, so C is out.
- Without --new-version, a second version of a lesson can never be ingested from the CLI (Q08 context). The flags map straight onto the existing DocumentUpload.lessonId/newVersion fields (scope.md:48). They are two optional args with no new logic.
- Exit codes:
  - 0: COMPLETED, including per-page failures or supersession_skipped (print a warning); an identical upload (print the existing document id and its latest run state).
  - 1: run FAILED.
  - 2: refused upload (LessonAlreadyExists, UnknownLesson, LessonIdentity, UploadRejected), a usage error, or an unknown user or KB. The message goes to stderr; for LessonAlreadyExists it says "pass --new-version or another --lesson-id".
- The runner only maps outcomes to messages and codes. Typed exceptions are caught in the runner. Exit goes through SpringApplication.exit / ExitCodeGenerator.

## What would change my mind
Evidence that the flags are unwanted scope, or that the identical-upload case must not exit 0.

## Options
| id | option | correct | fit | simple | risk | reversible |
|----|--------|---------|-----|--------|------|------------|
| A  | Act as `KnowledgeBase.ownerId`; no user argument | 4 | 2 | 5 | 3 | 4 |
| B  | `--user <email>`, lookup in an application service, then `requireOwner(kbId, userId)`; no password | 5 | 5 | 4 | 4 | 4 |
| C  | `--user <email>` + password prompt via `AccountService.authenticate` | 4 | 3 | 2 | 3 | 3 |

## Reasoning
- The scope says the CLI "must act as a definite user that owns the KB (see Q04)" and every access verifies
  ownership (CLAUDE.md Security). With A the acting user is derived from the KB, so `requireOwner` becomes a
  tautology: the check exists in name only. Not a hard violation, but it erodes the one ownership rule.
- A also bakes in "a KB has exactly one owner". `docs/adr/0018` line 33 and `roadmap.md:143` list shared knowledge
  bases as a known future direction; B keeps the CLI correct then, A would silently pick the owner for a member.
- B reuses the existing pattern exactly: the web adapter resolves a principal, then calls
  `KnowledgeBaseService.requireOwner(kbId, userId)` (`KnowledgeBaseService.java:45`) and passes `userId` to
  `QuizService.next/answer` (which `owned` re-checks). The CLI only swaps the principal source.
- Trust boundary: the operator holds `DATABASE_*`, so a password (C) adds ceremony, not protection, and locks out
  OAuth-only users (`AccountService.signInWithProvider` users have no password). C also needs console password
  handling — more code and concepts for no real gain (minimal-implementation.md).
- D (raw UUID) is minimal but users do not know their UUID; email is the domain identifier `UserRepository.findByEmail`
  already supports.
- Cost of B vs. plan: one extra argument beyond plan 15.1's `--file --kb`; acceptable and should be recorded in the
  plan/deployment docs as an "as built" note.

## What would change my mind
A decision (ADR or plan note) that the CLI is a single-operator admin tool which deliberately bypasses per-user
ownership; then A, documented as such, is simpler.

## Implementation notes
- Application: add `AccountService.byEmail(String email) -> User` (throws `NotFoundException("User")`), using
  `UserRepository.findByEmail`; the runner must not call the repository directly (thin adapter).
- Both runners take `--user <email>` (quiz also `--kb <id>`); resolve user, then
  `knowledgeBaseService.requireOwner(kbId, user.id())` before any work; map `NotFoundException`/`NotOwnerException`
  to a clear stderr message and non-zero exit.
- Pipeline: `new DocumentUpload(user.id(), UploadSource.<CLI or existing value>, ...)`; quiz: pass `user.id()` to
  `QuizService.begin/next/answer` so scores record against that user.
- Docs: `deployment.md` states the CLI trusts the operator (DB credentials are the boundary), no password, and the
  per-user rate limit does not apply.

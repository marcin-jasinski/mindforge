## Reasoning
- Plan 15.1 requires "same `IngestionService` and pipeline; prints step progress". Only an in-process run sees
  `ProgressNotifier` events (steps are not persisted), so B fails the requirement.
- `RunWorker.sweep` fails every RUNNING run not in this process's `active` set (RunWorker.java `sweep`/`settle`). A CLI
  that sweeps (E) breaks a live server at startup; so the CLI must not have the sweep. The quiz CLI also must not sweep.
- Least code: put `@Profile("!cli")` on the `runWorkerTriggers` bean (PipelineConfig.java:153) and have the pipeline
  runner call `runWorker.drain(kbId)` itself after `ingest` returns (its transaction has committed). No new trigger
  class, no new concept. `RunWorker` already claims under the lease and fences commits, so no model call enters a tx.
- The CLI is a short-lived process, the same class of event as deploy overlap that deployment.md:62-63 already
  accepts. Document the rule "stop the server first" in deployment.md; do not build detection (C = lease, out of scope).
- D duplicates `RunWorker` claim/fail/cost logic in the adapter (business logic in an adapter; hexagonal.md).
- Fully reversible: removing the profile guard restores today's behaviour.

## What would change my mind
Evidence that `IngestionService.ingest` does not commit before return (then `drain` would see no QUEUED run), or a
requirement that the CLI must run beside a live server.

## Implementation notes
- `infrastructure/config/PipelineConfig.java`: `@Profile("!cli")` on `RunWorkerTriggers runWorkerTriggers(...)`.
  `@EnableScheduling` stays (no scheduled beans under `cli` is harmless).
- `cli/PipelineCliRunner implements CommandLineRunner` (`@Profile("cli")`, wired in a `cli/CliConfig` `@Configuration`):
  `UUID docId = ingestion.ingest(upload); runWorker.drain(kbId);` then wait until the run for `docId` is terminal
  (COMPLETED/FAILED) — via a `ProgressNotifier` latch or polling `IngestRunRepository` (see Q05), print steps, exit
  code 0/1. If `ingest` returns an existing identical document (dedup), print that and exit 0 without waiting.
- After the run ends, `drain` may pick the next QUEUED run of the KB; the runner waits only for its own run, and
  `worker.stop()` must be called on exit (move a `ContextClosedEvent` stop into the CLI config, or call it in the runner).
- `docs/project/deployment.md#one-live-instance`: add "The CLI is a second instance: stop the server before you run
  `--spring.profiles.active=cli` against the same database."

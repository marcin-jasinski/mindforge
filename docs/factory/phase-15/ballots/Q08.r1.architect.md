## Reasoning
- D01 already binds wait-for-own-run, dedup exit 0 without waiting, non-zero on FAILED/timeout; A and B both satisfy that. C contradicts D01.
- Without --new-version, a second lesson version can never be ingested from the CLI (question context), and LessonAlreadyExistsException says "send newVersion or another lessonId". A CLI that must print that hint but cannot act on it is a design gap.
- B only maps two flags to DocumentUpload.lessonId/newVersion (fields already exist, scope.md); no logic, thin adapter. Parity with web form.
- Exit codes: 0 = COMPLETED or identical upload (already ingested); 1 = FAILED run, timeout, or refused upload (UploadRejected, LessonAlreadyExists, UnknownLesson, LessonIdentity); 2 = usage error (D03). Typed domain exceptions caught in the runner, one-line stderr message. Keep COMPLETED-with-page-failures/supersession_skipped as exit 0 but print a warning line.
## What would change my mind
Evidence that lesson identity handling in the CLI needs extra validation beyond what IngestionService already does.
## Implementation notes
PipelineCommandRunner: optional --lesson-id <id>, boolean --new-version -> DocumentUpload(kbId, user.userId(), UploadSource.CLI, name, mimeTypeOf(file), bytes, lessonId, newVersion). Map exceptions to exit codes via one small mapper in dev.mindforge.cli; --new-version without --lesson-id: let IngestionService decide (no CLI business rule). Tests: refused upload non-zero, LessonAlreadyExists message mentions --new-version.

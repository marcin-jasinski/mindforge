## Reasoning
- C is incorrect under D01: with `@Profile("!cli")` on the triggers there is no sweep or drain, so a run queued and abandoned stays QUEUED forever, and exit 0 reports success for work that never ran.
- A has a dead end: a lesson that already exists gives LessonAlreadyExistsException ("send newVersion or another lessonId"), and the CLI has no way to follow that advice. For a scripted ingest this is a silent permanent failure.
- B maps two flags straight onto the existing DocumentUpload.lessonId/newVersion. It adds no logic, and the service still owns validation.
- Exit codes must be stable and tell failure types apart. Proposed: 0 = COMPLETED, or an identical upload (print the existing document id and the latest run state; if that run is FAILED, exit 1, not 0). 1 = run FAILED. 2 = usage error or refused upload (Unknown/Identity/AlreadyExists/UploadRejected, with a clear stderr message). COMPLETED with per-page failures or supersession_skipped: exit 0 with a warning line on stderr, because the run is terminal and the web treats it the same.
- Failure modes to test: a run stuck RUNNING (wait must have a bounded timeout or must end if the worker stops); the JVM exit code must come from SpringApplication.exit(ExitCodeGenerator), not System.exit inside the runner, so the context closes and RunWorker.stop() runs.
- Identical upload with a prior FAILED run: do not silently exit 0.

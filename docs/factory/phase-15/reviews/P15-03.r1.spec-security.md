  location: src/main/java/dev/mindforge/cli/CliUsageRunner.java:17
  claim: The usage text documents space-separated option values (`--file <path> --kb <id>`), but Spring's `ApplicationArguments` only takes an option value from the `--name=value` form, so a script that follows the usage gives the runners options with no value, and the values become extra non-option arguments.
  evidence: SimpleCommandLineArgsParser (behind DefaultApplicationArguments) splits an option arg only on '='; `pipeline --file notes.md` gives getOptionValues("file") = [] and nonOptionArgs = [pipeline, notes.md] (CliCommandTest line 15 uses this exact shape). AC5 requires this literal text, and D03 uses the same form, so the text matches this ticket. But P15-05..07 will print the same `USAGE` constant, and a runner that reads `getOptionValues` will refuse input that follows the usage text exactly.
  fix: No change in this ticket. In the runner tickets, parse `getSourceArgs()` for `--flag value` pairs, or change D03/AC5 and the usage text to the `--flag=value` form.

- id: C1
  severity: minor
  confidence: 0.85
  location: docs/project/deployment.md:80
  claim: The deployment guide says an identical file means "no run is queued ... and does not wait", but when the latest run of the identical document is still QUEUED, the command drains the queue and waits for that run.
  evidence: IngestionService.ingest (IngestionService.java:90-92) returns the existing documentId with no new run. PipelineCommandRunner.report (PipelineCommandRunner.java:170-174) then reads runs.latestForDocument and on `case QUEUED -> drainAndAwait(...)` it drains and polls for up to run-timeout. Example: the server stops after an upload but before it claims the run. The operator then runs the CLI with the same file. The CLI executes and waits for the old QUEUED run, which goes against the documented "does not wait".
  fix: Change the sentence to say that if the latest run of the document is still QUEUED, the command runs it and waits. In all other cases it prints the state of that run and does not wait (exit 1 if that run FAILED).

- id: C2
  severity: minor
  confidence: 0.8
  location: docs/project/deployment.md:99
  claim: The exit-code table leaves out two code paths that return 2. The pipeline returns 2 when it cannot read the file, and the quiz returns 2 when the knowledge base has nothing to quiz. The table also says "before a run was queued" for the quiz, which never queues a run.
  evidence: PipelineCommandRunner.java:137-139 returns refuse("cannot read file: ...") (REFUSED=2). QuizCommandRunner.java:104-108 returns refuse("nothing to quiz: ...") when QuizService.start throws NotFoundException. Neither path is listed under "a usage error, an unknown user or knowledge base, a user who is not the owner, or a refused upload". A script that runs the quiz on an empty knowledge base gets exit 2, and no documented cause matches it.
  fix: Add "a file that cannot be read" and "a knowledge base with nothing to quiz" to the list for code 2. Change the wording to "refused before any work started".

- id: C3
  severity: minor
  confidence: 0.7
  location: docs/project/deployment.md:126
  claim: The guide says "the next server start re-queues it" for a run that the CLI claimed and left RUNNING. This is not always true. The sweep re-queues only INGEST runs with attempt < 3, and the CLI drain can also claim a QUEUED LINT run. The guide also does not tell the operator that the CLI's own run stays RUNNING after a timeout (exit 1). The server later fails that run and runs it again.
  evidence: RunWorker.drain (RunWorker.java:66-96) claims `runs.oldestQueued(kbId)` of any kind. RunWorker.settle (RunWorker.java:150-161) fails a RUNNING run as "interrupted" and enqueues a retry only when `run.kind() == INGEST && run.attempt() < MAX_ATTEMPTS`. A LINT run, or an ingest on its third attempt, only goes to FAILED. On timeout, PipelineCommandRunner.drainAndAwait calls runWorker.stop() and returns RUN_FAILED. The run that is still executing is not stopped, so after the process exits it stays RUNNING until a server sweeps it.
  fix: Change the text to "the next server start fails it as interrupted and re-queues an ingest run (up to three attempts)". Also add one sentence: after a timeout the CLI's own run stays RUNNING, and the next server start settles it the same way.

- id: C1
  severity: major
  confidence: 0.7
  location: src/main/java/dev/mindforge/cli/CliUsageRunner.java:17
  claim: The usage text (the script contract) tells users to pass options space-separated (`--file <path> --kb <id> --user <email>`), but Spring's `ApplicationArguments` parser only binds a value written as `--name=value`; the space form gives an option with no value and turns the value into a non-option argument.
  evidence: Checked against spring-core 7.0.8 / spring-boot 4.1.0 on this machine. `new DefaultApplicationArguments("--spring.profiles.active=cli","pipeline","--file","notes.md","--kb","7")` gives `getNonOptionArgs()=[pipeline, notes.md, 7]`, `getOptionValues("file")=[]` and `getOptionValues("kb")=[]`. The runners (P15-05..07) will read `getOptionValues("file"/"kb"/"user")`, so a user who follows the printed usage gets empty values, so "missing option" and exit 2. The command is still selected correctly because it is first, which is why the tests here pass. AC5 and D03 copy the same space-separated syntax, so this is a defect in the contract that this ticket prints and documents, not only a code slip.
  fix: Print the syntax the parser accepts: `pipeline --file=<path> --kb=<id> --user=<email> [--lesson-id=<id>] [--new-version]` and `quiz --kb=<id> --user=<email>`. Change AC5 and the CliUsageRunnerTest assertion to match, and record the amendment to D03. The other option is to keep the space form and write a custom parser, but D03 says "no command framework", so `=` is the smallest fix.

- id: C1
  severity: blocker
  confidence: 0.8
  location: src/main/java/dev/mindforge/discord/DiscordListener.java:44
  claim: With the JDA built with no gateway intents, every guild interaction carries a detached Member whose getRoles() throws, so toCall fails before the gate and no slash command or kb autocomplete ever gets a reply.
  evidence: DiscordConfig.jda builds `JDABuilder.createLight(token, EnumSet.noneOf(GatewayIntent.class))`, so without GatewayIntent.GUILDS no GUILD_CREATE arrives and `jda.getGuildById` is null for every guild. In JDA 6.7.0 `InteractionImpl.<init>` then calls `InteractionEntityBuilder.getOrCreateGuild`, which creates a `DetachedGuildImpl` when the guild is not cached, and `InteractionEntityBuilder.createMember` returns a `DetachedMemberImpl` for a detached guild. `DetachedMemberImpl.getRoles()` is bytecode `invokevirtual detachedException(); athrow` (checked with javap on ~/.m2/.../JDA-6.7.0.jar). `DiscordListener.toCall` calls `member.getRoles()` unconditionally (also when the role allowlist is empty), so on a real guild call it throws DetachedEntityException out of onSlashCommandInteraction/onCommandAutoCompleteInteraction: no allowlist check, no reply, Discord shows "The application did not respond". DiscordListenerTest mocks `member.getRoles()`, so the unit tests cannot catch this. The P18-04 note "slash interactions carry the member and roles without privileged intents" is true for the raw payload but JDA does not expose the role ids on a detached member.
  fix: Build JDA with `EnumSet.of(GatewayIntent.GUILDS)` (not privileged) so guilds and their roles are cached and the interaction member is an attached MemberImpl with resolved roles; add a short comment why. Alternatively read role ids without getRoles, but JDA has no public API for that on a detached member.

- id: C2
  severity: minor
  confidence: 0.6
  location: src/main/java/dev/mindforge/discord/DiscordCommandHandler.java:63
  claim: When defer() itself fails (for example the 3 s acknowledgement window has passed or the interaction is unknown), the catch calls reply.send(FAILED), which uses interaction.reply on an unacknowledged interaction and throws again, so the exception escapes the gate and JDA logs it with its message.
  evidence: JdaDiscordReply.defer sets `acknowledged = true` only after `deferReply(true).complete()` returns; if complete() throws (ErrorResponseException UNKNOWN_INTERACTION), send(FAILED) goes to `interaction.reply(part)...complete()`, which fails with the same error outside any catch; JDA's event manager then logs the uncaught exception with its message and stack trace, against the "message is not shown or logged" intent of AC5.
  fix: Wrap the fallback `reply.send(FAILED)` in its own try/catch (RuntimeException) that logs only the exception class at WARN.

  severity: minor
  confidence: 0.55
  location: src/main/java/dev/mindforge/discord/DiscordListener.java:38
  claim: An exception in kb autocomplete (identity resolution conflict, repository failure) escapes the listener uncaught, so JDA logs it with the full message and the user gets no choices reply.
  evidence: `knowledgeBases.suggest` calls `identities.resolve`, which can throw ExternalIdentityConflictException ("A DISCORD identity is already linked, or its account email is taken"); there is no catch in onCommandAutoCompleteInteraction, unlike the command gate which logs only the exception class.

- id: C1
  severity: major
  confidence: 0.7
  location: src/main/java/dev/mindforge/discord/UploadCommand.java:173
  claim: The attachment's raw Discord `content_type` goes to `UploadPolicy.admit`, which matches MIME types exactly, so a text or Markdown upload whose content type has a charset parameter is refused.
  evidence: Discord sets the attachment `content_type` of text files with a charset parameter (for example `text/plain; charset=utf-8`, and `text/markdown; charset=utf-8` for `.md`). `UploadCommand.upload` passes `attachment.getContentType()` unchanged into `DocumentUpload.mimeType`. `IngestionService.ingest` (:88) calls `UploadSanitizer.admit`, which does `!allowedMimeTypes.contains(mimeType)` (UploadSanitizer.java:38). The allowlist is `ParserRegistry.mimeTypes()`, which holds the bare `text/markdown` and `text/plain` (MarkdownParser.MIME_TYPE, PlainTextParser.MIME_TYPE). The parser lookup `parser.parse(upload.mimeType(), ...)` is also by exact key. Result: `/upload file:notes.md` throws `UploadRejectedException`, and the user gets "The file was refused; check its type, name and size." So two of the four supported formats fail from Discord. A null `content_type` (Discord leaves it out when it cannot detect a type) is refused in the same way. UploadCommandTest stubs `getContentType()` as the bare `"text/markdown"`, so this path is not tested.
  fix: In UploadCommand, normalise the type before it builds `DocumentUpload`. Keep the part before the first `;`, then strip it and lower-case it with `Locale.ROOT`. Add a test with the stub `"text/markdown; charset=utf-8"` that expects `mimeType` to be `"text/markdown"`.

- id: C2
  severity: minor
  confidence: 0.6
  location: src/main/java/dev/mindforge/discord/DiscordAttachments.java:50
  claim: When the thread is interrupted, the code does not cancel the download future, so the OkHttp call continues and its response stream is never closed.
  evidence: The `ExecutionException | TimeoutException | IOException` branch calls `download.cancel(true)`. JDA's `FileProxy.download` wires that cancel to `DownloadTask` through `FutureUtil.thenApplyCancellable`, which cancels the OkHttp `Call`. The `InterruptedException` branch only sets the interrupt flag again and throws. The call that `enqueue` started then completes later, and nothing reads or closes its `InputStream`, so its connection stays held until GC.
  fix: In the `InterruptedException` branch, also call `download.cancel(true)`, or call it in a shared `finally` when `content` is still unset.

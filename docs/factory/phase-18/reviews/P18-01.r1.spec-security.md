- id: S1
  severity: major
  confidence: 0.6
  location: src/main/java/dev/mindforge/infrastructure/persistence/adapter/ExternalIdentityRepositoryAdapter.java:47
  claim: createUserAndLink does not guarantee an insert of the users row; for a User whose userId already exists it silently overwrites that existing account and links the external identity to it, which is the "link to an existing account" path D02 forbids.
  evidence: UserEntity (entity/UserEntity.java) has an assigned @Id UUID, no @Version and does not implement Persistable, so SimpleJpaRepository.save/saveAndFlush sees isNew()==false and calls em.merge(). merge SELECTs the existing row and issues UPDATE (display_name, email, password_hash, avatar_url, last_login_at) instead of INSERT; no unique violation occurs, so no ExternalIdentityConflictException. The identity row then inserts with user_id = the existing account. Input: an existing web user U, call createUserAndLink(DISCORD, "x", new User(U.userId(), ..., "other@example.com", hash, ...)) -> U's email and password hash are replaced and Discord "x" now acts as U. Ticket D02: "Phase 18 does not link a Discord user to an existing web account"; port Javadoc says "Inserts the user". Today's planned caller (P18-03) generates a random UUID, so it is a contract hole rather than a live exploit, but the port is the guard the decision relies on.
  fix: Force an insert: check users.existsById(user.userId()) and throw ExternalIdentityConflictException if present, or persist via EntityManager.persist (or make UserEntity Persistable for this path) so a duplicate primary key raises a unique violation that the existing catch translates. Add a test: createUserAndLink with an existing userId throws and leaves the existing user row unchanged.

- id: S2
  severity: minor
  confidence: 0.5
  location: src/main/java/dev/mindforge/infrastructure/persistence/adapter/ExternalIdentityRepositoryAdapter.java:54
  claim: Every DataIntegrityViolationException is reported as an identity/email conflict, not only unique violations as the ticket's lost-race contract specifies.
  evidence: Ticket: "translate a unique violation (on the primary key or on idx_users_email) into a domain exception". Spring maps SQLState class 22/23 (e.g. 22001 value too long for external_id VARCHAR(64), 23502 not-null on a null externalId or displayName) to DataIntegrityViolationException, so invalid input surfaces as ExternalIdentityConflictException; a P18-03 caller that treats the conflict as a lost race and re-reads findUserId will then get empty and misbehave instead of seeing an input error.
  fix: Translate only unique violations (e.g. catch DuplicateKeyException, or inspect the cause's SQLState 23505 / ConstraintViolationException) and let other integrity errors propagate.

- id: S1
  severity: major
  confidence: 0.6
  location: src/main/java/dev/mindforge/discord/UploadCommand.java:91
  claim: The raw Discord `content_type` goes to `IngestionService.ingest` as the MIME type. Discord sends text attachments with a charset parameter (for example `text/plain; charset=utf-8`, `text/markdown; charset=utf-8`), so a Markdown or text upload, the main use of `/upload`, gets the fixed "The file was refused" reply.
  evidence: `UploadSanitizer.admit` (src/main/java/dev/mindforge/infrastructure/security/UploadSanitizer.java:38) does an exact `allowedMimeTypes.contains(mimeType)` against `parserRegistry.mimeTypes()`, which holds `text/markdown` (MarkdownParser.MIME_TYPE) and `text/plain` (PlainTextParser.MIME_TYPE) with no parameters. `parser.parse(upload.mimeType(), ...)` also uses the same string. Input `attachment.getContentType() == "text/markdown; charset=utf-8"` causes UploadRejectedException, then REJECTED. A null content type (Discord omits it for some types) is refused the same way. The Goal and AC2 want a valid CDN attachment to ingest "through the same path as the web and CLI". The CLI gets its MIME from the extension (`PipelineCommandRunner.mimeTypeOf`), so it never meets this case. UploadCommandTest only stubs a bare `text/markdown`, so the tests do not show this path.
  fix: Before the `DocumentUpload` is built, remove the media-type parameters (take the part before `;`, strip it, lower-case it). If the content type is null, use the extension mapping that the CLI uses. Add a UploadCommandTest case with `text/markdown; charset=utf-8`.

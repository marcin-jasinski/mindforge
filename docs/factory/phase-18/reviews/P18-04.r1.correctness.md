- id: C1
  severity: minor
  confidence: 0.6
  location: src/main/java/dev/mindforge/discord/DiscordBot.java:26
  claim: The unbounded `jda.awaitReady()` in an ApplicationRunner holds back `ApplicationReadyEvent`, so a slow or unreachable Discord gateway at boot delays (possibly forever) every ready listener, including the startup run sweep.
  evidence: Spring Boot calls runners before it publishes `ApplicationReadyEvent` (SpringApplication.run: callRunners, then listeners.ready). `RunWorkerTriggers.onReady` (src/main/java/dev/mindforge/infrastructure/event/RunWorkerTriggers.java:34) starts the startup sweep on that event. `awaitReady()` returns only when JDA reaches CONNECTED, and throws only on SHUTDOWN. While JDA retries the gateway connection during a Discord outage, the main thread stays blocked: the ready event never fires and the readiness state never becomes ACCEPTING_TRAFFIC. The scheduled sweep (initial delay `mindforge.runs.sweep-interval`, 1 min) still recovers runs, so the impact is limited to a delay. This is why the severity is minor.
  fix: Use `jda.awaitReady()` with a bounded wait (for example, `awaitStatus` with a timeout, or wait on a JDA ready callback with a timeout). On timeout, log a WARN line without the token and return, so startup continues. Alternatively, write down in the ticket notes that this blocking is accepted.

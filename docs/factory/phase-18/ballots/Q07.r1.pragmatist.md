## Reasoning
- The URL is not typed by the user: Discord's gateway sets it, over the bot's authenticated, operator-configured
  session. ADR 0023 trusts "Endpoints that the operator sets in configuration"; the Discord API and its CDN are that
  platform. The host allowlist turns "trust Discord" into a checked fact, so a forged or odd URL fails closed.
- ADR 0023 § Consequences names "bot links" and says "That change needs a new decision" — A records that decision as
  a new ADR, so no accepted ADR is contradicted. B also fits, but needs no ADR only if it is fully egress-checked.
- B is not reuse: `HttpArticleSource` (219 lines, `infrastructure/web/HttpArticleSource.java`) is HTML-only, returns
  `FetchedArticle`, and is built only for articles in `ArticleFetchConfig`. B means a second redirect loop, watchdog,
  header caps and a new port — about 150+ lines to guard Discord's own public CDN. `minimal-implementation.md`:
  "No Speculative Abstractions". C pays for both and adds nothing over B.
- D is incorrect by design: a string check without DNS pinning and with OkHttp's redirect following is the
  half-guard ADR 0022/0025 reject.
- Size: `Attachment.getSize()` is checked against `AppProperties.Upload.maxSize` before any byte is read; the stream
  is still read with a cap (declared size can lie), and one byte over fails (Phase 17 `readCapped` precedent).
  `UploadSanitizer` then admits name, MIME and size as for web and CLI.
- Guard: `OutboundHttpGuardTest` cannot see OkHttp today; adding the marker keeps it a tripwire for any new download.
- Reversible: if a later review wants B, only the one download method changes behind the same call site.

## What would change my mind
Evidence that JDA's OkHttp follows CDN redirects to arbitrary hosts in practice, or that a user can make the bot
download a URL that is not a Discord-issued attachment URL (then B).

## Implementation notes
- `dev.mindforge.discord.AttachmentDownloader` (package-private or final class; one caller, `/upload` handler):
  `byte[] download(Message.Attachment attachment)`.
  - `static final Set<String> CDN_HOSTS = Set.of("cdn.discordapp.com", "media.discordapp.net")`; parse
    `attachment.getUrl()` with `URI`, require scheme `https`, no userinfo, default port, host in `CDN_HOSTS`
    (lower-case), else reply "attachment refused".
  - `if (attachment.getSize() > maxBytes)` reject with the same message the web upload gives for too large; no download.
  - `attachment.getProxy().download().get(timeout, SECONDS)` then read at most `maxBytes + 1` bytes; more than
    `maxBytes` fails (never truncate); close the stream in try-with-resources. Timeout from a small
    `AppProperties.Discord` setting or a fixed constant (e.g. 60 s) — pick the constant unless Q15 adds a setting.
  - Build `DocumentUpload(kbId, userId, UploadSource.DISCORD, attachment.getFileName(), attachment.getContentType(),
    bytes, null, false)` and pass through `UploadSanitizer` / `IngestionService.ingest` as usual. Download outside any
    transaction.
- `OutboundHttpGuardTest`: add markers `"getProxy().download"`, `"AttachmentProxy"`, `"okhttp3"`; add
  `"dev/mindforge/discord/AttachmentDownloader.java"` to `OPERATOR_ENDPOINT_FILES` with a comment naming the new ADR.
- New ADR `docs/adr/0027-discord-attachments-downloaded-from-a-fixed-cdn-host-list.md` (number after whatever Q01
  takes): Discord API + CDN are an operator platform endpoint under ADR 0023; host list, https-only, size check before
  download, capped read; considered B and C; consequence: a bot feature that takes a free URL from a user still goes
  through `EgressPolicy`.
- Unit test with a fake attachment: off-list host refused, `http` refused, declared size over cap refused without a
  download call, body over cap fails.

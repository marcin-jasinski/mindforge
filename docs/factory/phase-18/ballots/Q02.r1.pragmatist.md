## Reasoning
- Plan 18.1-18.4 (implementation-plan.md:1576-1595) name four commands and three tests; no task, command or test calls `link`. minimal-implementation.md: "Build What You Need", "No Future Stubs". A keeps the port to methods with callers (Q13 already says "`link` only if Q02 gives it a caller").
- D01/ADR 0027 already settled that a bot user is a separate, auto-provisioned account that cannot sign in to the web; A is the direct consequence and needs no new concept, endpoint, table, credential or frontend gate.
- B/C each add a new credential type (hash store, TTL, single use, rate limit — which scope.md puts in Phase 20), an API endpoint with ownership checks, a frontend change (scope.md: "Frontend changes, unless Q02 picks a web-issued link code") and a merge/refuse policy for a provisioned account's data. That is a feature, not a Phase 18 task, and adds the most attack surface of any option.
- D is cheap and secure under ADR 0019's trust model, but it adds a CLI command the plan does not list and only helps a self-hosting operator; still speculative.
- E is account takeover; hard objection.
- Cost of A: a web user gets a second, empty account in Discord (vision.md:64 "ambient learning" is weaker). This is a known, visible gap, not a bug; adding `link` later is additive (new port method + new flow). The only reversibility cost is that provisioned accounts may hold data when linking arrives; that later decision must pick "refuse if the provisioned account owns any knowledge base, else re-point and delete it" — record this so it is not forgotten.
- Phase 19 reuses the same port; it gains nothing from a `link` it also would not call.

## What would change my mind
A human statement that Phase 18 is not done unless an existing web user can study their own wiki from Discord; then B (web-issued code, hashed, single use, short TTL, refuse when the provisioned account owns data).

## Reasoning
- Threat: the invite link is shareable, so any guild can add the bot; each command costs model spend and the first
  contact creates a user row (Q04 Context, scope.md 18.2). The allowlist is the only gate before identity resolution.
- C fails open on a missing env var: a typo in `MINDFORGE_DISCORD_ALLOWED_GUILD_IDS` silently makes the bot public.
  validation.md:15 "Allowlists Over Blocklists" and scope.md "fail closed" rule it out. Hard objection.
- B: a linked identity proves the user passed the check once, not now. Kick/ban or role removal does not revoke DM
  access, and a DM has no member/roles to recheck. Nobody would notice (no signal). Also Q02 may drop linking, making
  "linked" mean "auto-provisioned once", which is weaker still. Hard objection.
- A: the check uses Discord-supplied interaction fields (`isFromGuild()`, `getGuild().getIdLong()`,
  `getMember().getRoles()`), which come over the authenticated gateway, so they are not forgeable by the caller.
  Fail fast fits `AppProperties` `@Validated` + `@AssertTrue` precedent (AppProperties.java:21, :91).
- Role semantics: flat `Set<Long>` is correct because snowflakes are globally unique; D adds config shape without a
  new guarantee. Binding to `Long` makes a non-numeric id a startup error, not a silent never-match.
- A2: leaving guilds is nice hygiene but adds JDA calls and a failure path; ignore+reject is enough. Optional later.
- Testability: A is a pure predicate (guildId, roleIds) -> allowed; 18.4 "non-allowed guild rejected" is a one-line
  unit test, plus DM and missing-role cases. Failure is visible: rejection logged at INFO with guild id (not config).

## What would change my mind
A human statement that the deployment is single-user and DMs are the main use; even then I would want a separate
explicit `allowed-dm-user-ids` allowlist, not B.

## Implementation notes
- `AppProperties.Discord`: `String botToken`; `Set<Long> allowedGuildIds = Set.of()`; `Set<Long> allowedRoleIds = Set.of()`.
  `@AssertTrue(message = "allowed-guild-ids must not be empty when bot-token is set") isGuildAllowlistSetWhenEnabled()`
  returns `botToken == null || botToken.isBlank() || !allowedGuildIds.isEmpty()` (validates only when the bot is on, Q08).
- `dev.mindforge.discord.CommandAccess` (record or small final class), `boolean admits(Long guildIdOrNull, Set<Long> memberRoleIds)`:
  null guild -> false; guild not in set -> false; role set empty -> true; else intersect non-empty.
- In the slash handler, call it first, before `deferReply` work and before identity resolution; on reject reply
  ephemeral fixed text "This command is not available here." and return. Log `log.info("Discord command rejected: guild={}", guildId)`;
  never log the lists or the token.
- Register commands per allowed guild (`guild.updateCommands()`) rather than globally, so DMs and other guilds do not
  see them (defence in depth; the handler check stays authoritative because stale global commands can exist).
- Tests: `CommandAccessTest` — DM rejected, other guild rejected, allowed guild + empty roles admitted, required role
  missing rejected, one matching role admitted; AppProperties validation test for token set + empty guild list.
- deployment.md: `MINDFORGE_DISCORD_ALLOWED_GUILD_IDS` (required with token), `MINDFORGE_DISCORD_ALLOWED_ROLE_IDS` (optional).

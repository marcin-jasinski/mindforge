## Options
| id | option | correct | fit | simple | risk | reversible |
|----|--------|---------|-----|--------|------|------------|
| A  | Synthetic `discord-<id>@users.invalid`, no guard on the reserved domain | 2 | 4 | 5 | 2 | 4 |
| B  | `users.email` nullable (V8), `User.email` optional everywhere | 4 | 3 | 2 | 3 | 2 |
| C  | No provisioning; link first | 1 | 1 | 4 | 4 | 4 |
| D  | A + reserved domain enforced in code: `AccountService.register` and `signInWithProvider` refuse any `@users.invalid` email; provisioning never looks up by email; address built only in the application service | 5 | 4 | 4 | 4 | 4 |

## Reasoning
- Snowflakes are public (anyone can copy a user id in Discord), so a deterministic synthetic address is guessable. `register` checks only `findByEmail` then inserts (AccountService.java:26-31) and the DTO accepts any syntactically valid email (RegisterRequest.java:10), so `.invalid` is accepted today. A without a guard leaves squatting open: victim provisioning hits `idx_users_email` (V1__baseline.sql:14) on every command. D closes this with one check in `AccountService` ("Every rule ... enforced in code").
- `signInWithProvider` matches by email (AccountService.java:54-58). Google/GitHub only hand over verified emails (OAuthLoginSuccessHandler.java:38) and cannot verify a `.invalid` address, but D still refuses the domain there: defence in depth, one line.
- A/D need no migration and keep `User` unchanged; no NPE surface. B makes `email` null in `normalise` (NPE at AccountService.java:79 via byEmail/findByEmail), `UserResponse.email`, JWT/SPA code and the CLI `--user=<email>` (ADR 0019) — many silent break points, each needing a test; and the reverse migration needs a backfill, so B is the least reversible.
- Race: two first-contact commands. With D the synthetic email is deterministic, so the second insert fails on BOTH `idx_users_email` and the `(platform, external_id)` key inside the one transaction; catch the unique violation, roll back, re-read `findUserId`. No orphan `users` row. With B a null email gives only the identity key as backstop (still enough, but one fewer).
- Detection: a test that `register("x","discord-1@users.invalid",...)` throws `AccountException`; a test that two `createUserAndLink` for the same id yield one user; first-contact test asserts the provisioned email equals the synthetic address.
- The account has no password and no provider match, so it cannot sign in to the web; the synthetic address shows only through the CLI or a later link (Q02). Low exposure.

## What would change my mind
Evidence that some other path (admin import, a future email-change endpoint) writes user emails without going through `AccountService`, or a human decision that Discord-only accounts must sign in to the web later without linking.

## Implementation notes
- Application: `AccountService.provisionExternal(String platform, String externalId, String displayName)` is not needed if provisioning lives in an identity service; put the address rule in one place: `static String syntheticEmail(String platform, String externalId)` -> `platform.toLowerCase(ROOT) + "-" + externalId + "@users.invalid"`, platform-neutral so Phase 19 reuses it (Slack ids lowercase injectively).
- `AccountService.register` and `signInWithProvider`: after `normalise`, if `normalised.endsWith("@users.invalid")` throw `AccountException` (new factory, e.g. `AccountException.reservedEmail()` or reuse `emailTaken()` to avoid an oracle). Map to 409/400 like existing account errors.
- `ExternalIdentityRepository.createUserAndLink(platform, externalId, User user)` in one `@Transactional`; the resolver catches the adapter's unique-violation domain exception and returns `findUserId(...)`. Display name via `TextRules.singleLine`, truncated to 255; fall back to the username if global name is null.
- Password hash null, avatar null. Record the choice in a new ADR (account model for bot users), next number after 0026.

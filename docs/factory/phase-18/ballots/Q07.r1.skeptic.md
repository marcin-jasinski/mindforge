## Options
| id | option | correct | fit | simple | risk | reversible |
|----|--------|---------|-----|--------|------|------------|
| A  | Discord CDN is a trusted platform endpoint: https + fixed host list + declared size <= max-size, download with JDA's OkHttp (`getProxy().download()`), byte cap; new ADR amends ADR 0023; JDA-download marker in guard test | 4 | 2 | 4 | 3 | 4 |
| B  | URL untrusted: download through `EgressPolicy` with a pinned HttpClient 5 client in `infrastructure.web`, public-address check, no redirects, size cap | 4 | 4 | 2 | 3 | 4 |
| C  | A's fixed https host allowlist + declared-size check, then fetch through the egress-checked pinned client of B (no redirects, byte cap, deadline) | 5 | 5 | 2 | 4 | 4 |
| D  | Like A but with a JDA `OkHttpClient` set via `JDABuilder.setHttpClient` with redirects off and an OkHttp `Dns` through `EgressPolicy` | 3 | 1 | 3 | 2 | 3 |

## Reasoning
- No option is a hard blocker if an ADR records it, but A sits awkwardly against two accepted texts: ADR 0023
  § Consequences "bot links … that URL is untrusted and must go through `EgressPolicy`", and web-security.md § Untrusted
  Input Handling "All … external URLs … are untrusted … never write ad-hoc … HTTP handling". A must argue a Discord-set
  URL inside user-triggered event data is "operator config"; the spec-security review lens is likely to flag that.
- A's failure modes we would not see: JDA's OkHttp follows redirects by default, so a one-time host check does not cover
  later hops; OkHttp has no markers in `OutboundHttpGuardTest` (MARKERS list), so the guard needs a new, broad marker
  (`.download(`/`getProxy()`) that is easy to bypass (`getUrl()` + any other OkHttp call). Read timeouts restart per byte;
  only the future, not the body read, gets a deadline.
- D is rejected by ADR 0025 "Considered Options": OkHttp `Dns` was refused because `okhttp-4.12.0` and `okhttp-jvm-5.3.2`
  both ship `okhttp3` and jar order picks the SSRF-control class. Adding JDA (OkHttp) makes that worse, not better.
- B alone fits ADR 0022/0023/0025 but makes the bot a fetcher of any public host: if a URL ever reaches the download path
  from a non-attachment field, nothing limits it to Discord. validation.md prefers allowlists, fail closed.
- C costs one `Set.of(...)` over B and gives defense in depth: host allowlist (only Discord CDN), then the existing
  checked-DNS client (no second resolution, ADR 0025), no redirects, deadline watchdog, byte cap that fails instead of
  truncating (`HttpArticleSource.readCapped` precedent). A new class in `infrastructure/web/` passes the guard by
  directory with no guard edit, and a sibling of `shouldHaveTheArticleSourceCallEgressPolicyCheck` proves it calls check.
- Testability: C reuses the ADR 0022 resolver seam, so a test shows a CDN-host name that resolves to loopback is refused
  at connect; A can only be tested by mocking JDA's `Attachment`/`AttachmentProxy`.
- Size: check `attachment.getSize()` against `mindforge.upload.max-size` before any request, also cap read bytes at
  max-size (+1 byte fails), then `UploadPolicy.admit` still runs in `IngestionService` as on web and CLI.
- Operability: Discord host change fails closed with a fixed reply and a `log.warn` of the host (never the full signed
  URL query); observable, fix is one config/constant edit.

## What would change my mind
Evidence that Discord CDN rejects the Apache client (UA/Cloudflare) or needs redirects, or a reviewer-accepted reading
that ADR 0023's "bot links" excludes platform-set attachment URLs and the extra client code is judged not worth it (then A).

## Implementation notes
- New ADR 0027 "Discord attachment bytes are fetched through EgressPolicy from a fixed Discord CDN host list"; it applies
  ADR 0023 § Consequences ("bot links") and ADR 0025, does not amend them.
- `dev.mindforge.infrastructure.web.HttpAttachmentSource` (final, `AutoCloseable`): `static create(EgressPolicy,
  Duration connectTimeout, Duration requestTimeout)`, `byte[] fetch(URI url, long maxBytes)`; field
  `private final EgressPolicy egressPolicy;` and calls `egressPolicy.check(url)`; any 3xx = failure (CDN does not
  redirect), non-2xx = failure, `Content-Length > maxBytes` = TOO_LARGE before reading, read loop fails at maxBytes+1.
  Throws a domain/infra exception (e.g. `AttachmentFetchException` with `Reason {HOST, POLICY, TOO_LARGE, TIMEOUT,
  UNREACHABLE, HTTP_STATUS}`), never echoes the URL or provider message to the user.
- Extract the pinned client builder from `HttpArticleSource.create` into a package-private
  `CheckedHttpClients.create(EgressPolicy, Duration connectTimeout)` in `infrastructure/web/` (or copy the ~20 lines if
  the extraction risks Phase 17 tests); keep `disableRedirectHandling`, no retries/cookies/proxy.
- Host allowlist in the discord adapter (or the source): `Set.of("cdn.discordapp.com", "media.discordapp.net")`, scheme
  must be `https`, port default; checked before `egressPolicy.check`. Use `attachment.getUrl()`.
- Order in `/upload` handler: allowlist/identity/`requireOwner` -> `attachment.getSize() <= upload.maxSize.toBytes()`
  else fixed "file too large" reply -> host check -> `fetch(url, maxSize)` (deferReply first; download is blocking on a
  virtual thread) -> `IngestionService.ingest(new DocumentUpload(..., UploadSource.DISCORD, ...))`.
- Timeouts: reuse `mindforge.articles.connect-timeout`/`request-timeout` values or add `mindforge.discord.download-timeout`
  (prefer constants-free: one new Duration property under `AppProperties.Discord`).
- Tests: `OutboundHttpGuardTest.shouldHaveTheAttachmentSourceCallEgressPolicyCheck`; unit tests for host refusal (http,
  other host, userinfo), declared size over max refused with no fetch, body over cap fails not truncates, loopback-
  resolving name refused via the resolver seam.

## Reasoning
- A adds no state, no migration, no new command, and mirrors the existing pattern: web passes kbId in the path, CLI takes `--kb=<id>` (ADR 0019); Discord takes `kb:` with autocomplete so nobody types a UUID.
- B needs a migration, a fifth command (`/kb use`) the plan does not list (scope.md "the plan lists exactly four commands"), and stored state whose only purpose is UX; question constraint "No speculative state".
- C silently picks the wrong KB for a linked multi-KB user (Q02) - a write (`/upload`) into the wrong wiki is a correctness bug, not a UX nit.
- A2 is a nice-to-have default rule; it adds a branch and a second error path for little gain. Can be added later without breaking anything (making a required option optional is backward compatible).
- KB names are not unique per owner (V1__baseline.sql `knowledge_bases.name VARCHAR(255) NOT NULL`, no unique index), so the value must be the UUID, not the name.
- Discord does not enforce that a submitted value came from autocomplete: the handler must parse the UUID and call `KnowledgeBaseService.requireOwner` (KnowledgeBaseService.java:45) - which is the rule anyway; a bad UUID gets a fixed error text.
- Default KB: `KnowledgeBaseService.create(ownerId, "Discord", null)` already exists - one call, no new method. A first-contact user can `/upload` immediately.
- Reminder job (W10) has no selection to consult, so it counts every owned KB (Q10 option C1). Consistent and needs no extra state.

## What would change my mind
Evidence that JDA autocomplete cannot be wired with a thin, testable handler, or a human requirement that Discord commands need zero options.

## Implementation notes
- Slash commands: `/ask kb:<string, required, autocomplete> question:<string>`; `/quiz start kb:<…> [scope]`; `/quiz answer` - KB comes from the session record chosen in Q05 if it stores kbId, else `kb:` too; `/upload kb:<…> file:<attachment>`.
- Autocomplete handler (adapter, `dev.mindforge.discord`): on `CommandAutoCompleteInteractionEvent` for option `kb`, resolve user (D01 resolver), `knowledgeBases.list(userId)`, filter by name containing the typed text (case-insensitive), max 25 choices, `Choice(name truncated to 100, kbId.toString())`.
- Command handler: `UUID kbId = parse(option)` -> invalid -> fixed reply "Unknown knowledge base."; then `knowledgeBases.requireOwner(kbId, userId)`; map `NotFoundException`/`NotOwnerException` to the same fixed reply (no existence oracle).
- Default KB: in the identity resolution application service (D01 notes), when `createUserAndLink` actually provisioned a new user, call `knowledgeBaseService.create(userId, "Discord", null)`. Prefer the same transaction as user+link; if not, a user with zero KBs gets an autocomplete with no choices and a fixed reply telling them to upload - so put the create in the provisioning transaction, and only on the winning insert (not on the re-read after a unique violation).
- Test: first contact provisions user + exactly one KB named "Discord"; a command with another user's kbId -> NotOwnerException path -> fixed reply; a non-UUID kb value -> fixed reply, no service call.

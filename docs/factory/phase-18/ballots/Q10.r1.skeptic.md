## Reasoning
- D03 (decided): no stored KB selection, so C2 is unavailable; C1 (all owned KBs) is the only consistent scope. Assumption stated: D03 = A as recorded.
- A2 is wrong: fixed delay drifts with every restart, so time of day is random and a restart can repeat a DM within hours. A cron fires at most once per slot; a restart skips at worst one day and never repeats it. Matches existing `${...}` setting pattern (RunWorkerTriggers uses @Scheduled with property).
- B2 puts card fronts into DM history outside MindForge (retention, shared devices, screenshots) for no requirement; counts only leak nothing.
- D2 needs migration + a fifth command; scope.md fixes "exactly four commands". Blocking the bot is a working opt-out; a blocked DM fails and is logged. Add D2 later without breaking anything.
- Failure modes to test: per-user try/catch around both `due()` and the send (one bad user must not stop the loop); log only user id and exception class at WARN, never token or content; cap DM length (Discord 2000 chars) for users with many KBs; cheap-DM guard: skip when zero due; no model call (due() generates none).
- Operability: a blocked user fails every day -> a WARN per day per user; acceptable, note it. Invalid zone/cron fails at startup (fail-fast, good).
## What would change my mind
Evidence that users cannot practically stop DMs (then D2), or a requirement for multiple app instances (then need a lock).
## Implementation notes
`DiscordReminderJob` (discord package) with `@Scheduled(cron="${mindforge.discord.reminder-cron:0 0 9 * * *}", zone="${mindforge.discord.reminder-zone:UTC}")` calling `runOnce()` (testable). Seam `ReminderSender.send(String discordUserId, String text)`. For each Discord identity: for each `knowledgeBases.list(userId)` call `flashcards.due(kbId, scope)`; build "You have N flashcards due in *Name*" lines, truncate name and total to 2000 chars; skip user if no lines; catch RuntimeException per user, log.warn with user id. Document settings in deployment.md and env.example.

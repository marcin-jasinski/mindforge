## Reasoning
- A is the least code that is still fail-closed: one `@AssertTrue` on `AppProperties.Discord` (same pattern as
  `isLimitsPositive()` in `infrastructure/config/AppProperties.java:91`, class is `@Validated` at line 21) and one
  pure predicate `admits(guildId, roleIds)` that tests can drive without JDA.
- Q08 already settles "validated at startup when the token is set", so the guard is `botToken blank || !allowedGuildIds.isEmpty()`.
- B: a DM has no guild and no roles, so the role check cannot run; a user removed from the guild or role would keep
  access via DMs. Revocation breaks silently. Extra branch, extra test, weaker boundary — no requirement asks for DM commands.
- C: an unset list = open bot with account auto-provisioning; contradicts validation.md "Allowlists Over Blocklists"
  and scope "fail closed". Hard objection.
- D: role snowflakes are globally unique (question context), so a flat set already gives per-guild precision; a map is
  speculative generality (`minimal-implementation.md`).
- E: leaving guilds is extra event handling for no security gain — a rejected command already provisions nothing.
  It can be added later without changing semantics. Ignore + fixed reply is enough.
- Check order: allowlist first, before identity resolution, so a rejected caller provisions nothing (Q04 constraint).

## What would change my mind
A human requirement for DM commands (then B with a fresh guild-membership check on each DM), or evidence that one
deployment needs different role sets per guild in a way a flat set cannot express (it cannot happen with unique ids).

## Implementation notes
- `AppProperties.Discord`: `String botToken`; `Set<String> allowedGuildIds = Set.of()`; `Set<String> allowedRoleIds = Set.of()`
  (snowflakes as strings, env `MINDFORGE_DISCORD_ALLOWED_GUILD_IDS` comma list).
  `@AssertTrue(message = "mindforge.discord.allowed-guild-ids must not be empty when the bot token is set") public boolean isGuildAllowlistSet()`
  returning `botToken == null || botToken.isBlank() || !allowedGuildIds.isEmpty()`.
- `dev.mindforge.discord.DiscordAllowlist` (record built from properties): `boolean admits(String guildIdOrNull, Collection<String> memberRoleIds)`
  — null guild -> false; guild not in set -> false; role set empty -> true; else any overlap.
- Command listener: on `SlashCommandInteractionEvent`, call `admits(event.getGuild()==null?null:guild.getId(), member role ids)`
  before identity resolution; on false reply ephemeral fixed text e.g. "This bot is not available here." and log at
  debug the guild id only. Never echo the configured lists.
- Tests (18.4): non-allowed guild rejected and `ExternalIdentityRepository` never touched; DM rejected; role required
  and missing -> rejected; role list empty -> any member admitted; properties validation fails with token + empty guild list.
- deployment.md: document both settings and that an empty guild list with a token stops startup.

## Reasoning
- The attachment URL is not "taken from content or a user" (web-security.md:75 wording): Discord issues it in the interaction payload that arrives over the bot's authenticated gateway connection, which JDA already opens over OkHttp to an operator-configured platform with the operator's token. The CDN is the same trust tier as that gateway; ADR 0023 trusts exactly this class ("Endpoints that the operator sets in configuration ... are trusted").
- ADR 0023 § Consequences ("bot links ... must go through EgressPolicy. That change needs a new decision") is about URLs a user can choose (e.g. a pasted link). Q07 demands either fit or a new ADR; A writes that ADR (0027, format of 0026) and names the line it narrows, so no accepted ADR is silently contradicted. D does not, so D is out (fails the Q07 constraint; a soft blocker).
- B/C reuse the Phase 17 SSRF control, but `HttpArticleSource` (infrastructure/web, 219 lines) is shaped around `ArticleSource.fetch -> FetchedArticle` and HTML conversion; making it a generic byte fetcher means a new domain port and a refactor of an accepted security adapter (ADR 0025) whose guard test pins `HttpArticleSource.java` by path. That is more surface for no threat that A leaves open.
- B alone is weaker than it looks: ADR 0022 has no host list, so B accepts any public URL and never asserts the file is from Discord. A's fixed host list (`cdn.discordapp.com`, `media.discordapp.net`, https only) is the property that actually matters here; ADR 0022's objection to host lists ("an allowed host can ... redirect to an internal address") does not apply to a platform-owned CDN the operator already trusts.
- A year out: Phase 19 Slack files (`url_private`) need the bot token in the request; sending a platform token through a generic egress client to a URL that is not host-pinned would be wrong. A's rule "platform files come through the platform's client, host-pinned" carries over; B's does not.
- Size: `UploadPolicy.admit(filename, mime, attachment.getSize())` before any byte is read (Q15), then read at most max-size+1 bytes and fail (never truncate) if more arrive - the Phase 17 precedent.
- Guard test stays a real tripwire: add markers for JDA/OkHttp download (`okhttp3`, `.getProxy()`, `.download(`; none occur in src/main today, checked by grep) and allow only the exact downloader file, documented as a platform endpoint per ADR 0027.

## What would change my mind
Evidence that a user can influence the attachment URL in the interaction payload (e.g. a non-Discord host reaches `Attachment.getUrl()`), or that JDA's client follows redirects off the CDN in practice; then C.

## Implementation notes
- `dev.mindforge.discord.DiscordAttachments` (single file, exact path in the guard test): `byte[] read(Message.Attachment a, long maxBytes)`; rejects unless `URI.create(a.getUrl())` has scheme `https` and host in `Set.of("cdn.discordapp.com", "media.discordapp.net")` (fail closed, typed exception -> fixed reply text); checks `a.getSize() <= maxBytes` before download; `a.getProxy().download().join()` on the virtual thread (CompletableFuture, no Reactor); `in.readNBytes((int) maxBytes + 1)` and throws if length > maxBytes.
- The bot handler calls `UploadPolicy`/`UploadSanitizer` with filename, content type, declared size first, then `DiscordAttachments.read`, then `IngestionService.ingest(new DocumentUpload(..., UploadSource.DISCORD, ...))`.
- `OutboundHttpGuardTest`: add markers `okhttp3`, `.getProxy()`, `.download(`; add `PLATFORM_ENDPOINT_FILES = Set.of("dev/mindforge/discord/DiscordAttachments.java")` (or extend `OPERATOR_ENDPOINT_FILES` with a comment citing ADR 0027); add a test case that a discord file other than the allowed one with `.download(` is reported.
- New `docs/adr/0027-discord-attachments-downloaded-by-the-platform-client-host-pinned.md`: amends ADR 0023 § Consequences "bot links" to mean user-chosen URLs; Discord-issued attachment URLs are platform endpoints; considered B and C.

## Options
| id | option | correct | fit | simple | risk | reversible |
|----|--------|---------|-----|--------|------|------------|
| A  | Synthetic non-deliverable email `discord-<snowflake>@users.invalid`, no password, no schema change; `register` refuses the reserved domain | 4 | 4 | 5 | 4 | 5 |
| A' | A with a random local part (`discord-<uuid>@users.invalid`) instead of the snowflake | 4 | 3 | 4 | 4 | 4 |
| B  | `users.email` nullable (V8), optional email through `AccountService`, DTO, OAuth handler, JWT, SPA | 4 | 3 | 2 | 3 | 2 |
| C  | No provisioning; first contact only says "link your account" | 1 | 2 | 3 | 4 | 4 |

## Reasoning
- A adds zero schema, zero DTO and zero frontend change. `User` (domain/model/User.java) stays as is; `users.email NOT NULL`
  + `idx_users_email` (V1__baseline.sql:3-14) stays valid; `password_hash` is already nullable, so the account simply has
  no password sign-in. `AccountService.byEmail` (ADR 0019 `--user <email>`) names it with no new code path.
- Web sign-in is closed by design: `authenticate` filters `passwordHash() != null`; `OAuthLoginSuccessHandler` needs a
  provider-shared email, and no provider can verify an address under the RFC 2606 `.invalid` TLD. Linking is Q02's job.
- B touches `AccountService.normalise` (NPE on null), `UserResponse`, `OAuthLoginSuccessHandler`, `CliUsageRunner`,
  the SPA profile, and a V8 migration — wide change for data nobody reads now; hard to reverse once rows have NULL.
- C contradicts the plan's 18.2/18.4 (hard objection above).
- One real failure mode in A: the snowflake is public, so someone can `POST /register` with
  `discord-<id>@users.invalid` first (RegisterRequest has only `@Email`). If provisioning matched by email that is an
  account takeover; if it inserts, it is a unique-key failure (denial). Fix: `createUserAndLink` always inserts, never
  matches by email; `AccountService.register` (and `signInWithProvider`) refuse the reserved domain with
  `AccountException`. One check, unit-testable. This keeps A simpler than A' (random local part loses the
  human-derivable CLI name).
- UI shows the synthetic address as the profile email: acceptable — it is honest (`.invalid` cannot receive mail) and
  the bot users do not sign in to the web.

## What would change my mind
Evidence that Phase 18/19 needs Discord accounts to sign in to the web or receive mail without linking, or that the
SPA/JWT already treats email as optional (then B's cost falls).

## Implementation notes
- Domain: `dev.mindforge.domain.model.SyntheticEmail` (or a static in a small record/utility, JDK only):
  `static String forExternal(String platform, String externalId)` -> `platform.toLowerCase(Locale.ROOT) + "-" + externalId + "@users.invalid"`;
  `static boolean isReserved(String email)` -> `email.endsWith("@users.invalid")`. Name not Discord-only (Phase 19 reuses).
- Application: new `ExternalIdentityService.resolve(platform, externalId, displayName)` -> `findUserId` else
  `createUserAndLink(platform, externalId, new User(UUID.randomUUID(), TextRules.singleLine(displayName or externalId),
  SyntheticEmail.forExternal(...), null, null, null, null))`; on unique-key race re-read `findUserId`.
- `AccountService.register` / `signInWithProvider`: `if (SyntheticEmail.isReserved(normalised)) throw AccountException...`
  (new factory e.g. `AccountException.emailReserved()`).
- Adapter `createUserAndLink` in one `@Transactional`: insert user + insert `external_identities` row; unique
  `(platform, external_id)` is the backstop.
- Tests: first contact provisions with `discord-<id>@users.invalid` and null password; second contact returns the same
  user; register with a reserved address is refused.
- Record in the identity/account ADR: synthetic `.invalid` email, no web sign-in until linked (Q02).

## Reasoning
- Failure mode of A as written: on first contact the user opens `/upload`, Discord fires an autocomplete event for the
  required `kb` option BEFORE any command runs. The user is not provisioned, so autocomplete must either write (provision
  on a keystroke event, many per second) or show nothing (the new user cannot submit at all). E removes this: autocomplete
  is read-only (unknown user -> empty list), and the first `/upload` with no `kb` provisions and uses the default KB.
- Discord does not enforce autocomplete choices: the value is free text the client sends. So the value is untrusted:
  parse as UUID (fail -> fixed reply), then `KnowledgeBaseService.requireOwner` (KnowledgeBaseService.java:46). Never
  resolve by name: `knowledge_bases.name` has no unique constraint (V1__baseline.sql:16-23), so name lookup is ambiguous.
- Implicit default only when unambiguous (exactly one owned KB): no silent wrong-KB write, unlike C "oldest".
- Atomicity: if the default KB is created in a second step after `createUserAndLink`, a crash or a lost race leaves a user
  with zero KBs (every command fails forever; D01 says a bot user cannot reach the web to fix it, AccountService.java:42-44)
  or two "Discord" KBs (concurrent first contacts). Create it only on the winning provisioning path, in the same
  transaction. A cheap backstop: zero owned KBs at command time -> create the default (covers rows provisioned before this).
- No migration, no new command, no stored state (B is out of scope and adds a stale-selection failure when the KB is deleted).
- Reminders (W10): no selected KB exists, so count due cards over every owned KB (`list(ownerId)` + `FlashcardService.due`).
- Testable without Discord: a pure resolver `(Optional<String> kbOption, List<KnowledgeBase> owned) -> kbId | error`.

## What would change my mind
Evidence that JDA/Discord cannot leave a command option optional with autocomplete (then A with provisioning on
autocomplete), or a decision (Q13/Q01) that forbids KB creation inside the provisioning transaction.

## Implementation notes
- Commands: `/ask question:<str> kb:<str, optional, autocomplete>`, `/quiz start kb:<optional>`, `/upload file:<attachment> kb:<optional>`.
  `/quiz answer` takes no `kb`: the session (Q05) remembers its kbId.
- Autocomplete handler: allowlist (D04) first; `findUserId` only (never provision); unknown -> empty; else
  `list(ownerId)` filtered by case-insensitive contains on the typed text, max 25 choices, name truncated to 100 chars,
  value = `kbId.toString()`.
- Application (e.g. `application/service/BotIdentityService`, name per Q13): `UUID resolveOrProvision(String platform, String externalId, String displayName)`;
  on miss, in one `@Transactional` (org.springframework.transaction is allowed in application): `createUserAndLink(...)` then
  `knowledgeBases.insert(new KnowledgeBase(randomUUID(), userId, "Discord", null, null, 0, 0))`. On unique violation re-read
  `findUserId` (D01) — the loser creates no KB.
- Adapter helper (JDA-free, unit-tested): `record KbChoice(...)` / `UUID pickKnowledgeBase(Optional<String> option, UUID userId)`:
  option present -> `UUID.fromString` (IllegalArgumentException -> fixed reply "Unknown knowledge base.") then
  `requireOwner` (NotFound/NotOwner -> same fixed reply, no echo); absent -> `list(userId)`: size 1 -> it; size 0 ->
  `create(userId, "Discord", null)` backstop; size > 1 -> fixed reply "You have several knowledge bases; choose one with the kb option."
- Tests: first contact creates exactly one user and one KB; concurrent first contacts -> one KB; foreign kbId -> rejected,
  no service call; malformed value -> rejected; omitted with two KBs -> error; autocomplete never provisions.

## Reasoning
- Every surface already names the knowledge base per request: web in the path, CLI with required `--kb=<id>`
  (CliUsageRunner.java:17-18, ADR 0019). A adds a third surface with the same shape: kbId per command, then
  `KnowledgeBaseService.requireOwner(kbId, userId)` (KnowledgeBaseService.java:46-48). No new concept, no state.
- B adds a new domain concept ("current knowledge base"), a migration, a fifth command (`/kb use`) outside the plan's
  four (scope.md § Out of scope: "the plan lists exactly four commands"), and a stale-pointer case when that knowledge
  base is deleted (`knowledge_bases ... ON DELETE CASCADE`, V1__baseline.sql:16-23). Least reversible.
- C silently picks a tenant for multi-KB users (a web user later linked per Q02 owns several); choosing "oldest" is a
  hidden rule a maintainer will not expect. A2 keeps that ambiguity on the error path for a small UX gain.
- D: hard objection above.
- Autocomplete solves "a UUID is unusable to type": Discord shows the name and sends the id. Names are not unique per
  owner (no unique index on `knowledge_bases.name`), so the value must be the id, never the name.
- Default knowledge base at provisioning is required for correctness: a new user owns none, so without it `/upload`
  has nothing to target and there is no `/kb create` in the plan. It reuses `KnowledgeBaseService.create`.
- W10 fits cleanly: with no stored selection, the reminder counts every owned knowledge base (Q10 C1); no extra state.

## What would change my mind
Evidence that JDA autocomplete cannot run identity resolution within Discord's autocomplete deadline, or a human ruling
that a fifth command (`/kb use`) is in scope.

## Implementation notes
- Command option: `OptionData(OptionType.STRING, "kb", "Knowledge base", true, true)` on `/ask`, `/quiz start`,
  `/upload`. `/quiz answer` takes no `kb`: it uses the kbId stored with the session in the Q05 choice.
- Autocomplete handler (`CommandAutoCompleteInteractionEvent`, in `dev.mindforge.discord`): pass the same guild/role
  allowlist (D04/ADR 0028), resolve-or-provision the caller, then `knowledgeBases.list(userId)` filtered by
  case-insensitive name prefix, max 25 choices, `Command.Choice(name truncated to 100, kbId.toString())`.
  Resolution must run here too, or a first-contact user sees no choices.
- Command handler: parse the option as UUID (a user can type free text — invalid UUID is a fixed-text error), then
  `requireOwner(kbId, userId)` before any work; `NotFoundException`/`NotOwnerException` map to one fixed message
  ("Knowledge base not found") so ids of others are not probed.
- Default knowledge base: in the identity-resolution application service (e.g. `ExternalIdentityService.resolve(platform,
  externalId, displayName)`), only on the provisioning branch: `knowledgeBaseService.create(userId, "Discord", null)`.
  Make user + identity + knowledge base one transaction (wrap `createUserAndLink` and the KB insert in a
  `TransactionTemplate` per attempt so the D01 unique-violation retry re-reads in a fresh transaction). Name it from a
  constant, e.g. `DEFAULT_KNOWLEDGE_BASE_NAME = "Discord"`; platform-neutral parameter so Phase 19 passes "Slack".
- Tests: first contact creates exactly one knowledge base owned by the new user; a second contact creates none;
  a command with another user's kbId fails through the real `requireOwner`; autocomplete lists only the caller's
  knowledge bases.

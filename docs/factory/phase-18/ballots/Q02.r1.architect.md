## Reasoning
- The plan's task list never calls `link`: 18.2 has exactly four commands and 18.4 tests only auto-provisioning, allowlist
  and ownership (implementation-plan.md:1577-1589). scope.md "Out of scope" says "Other commands ... the plan lists
  exactly four commands". B, C and D each add a fifth entry point plus a web endpoint and SPA work: that is a new feature,
  not an implementation of 18.1.
- minimal-implementation.md "Build What You Need" / "No Future Stubs": `link` without a caller is dead code. A keeps the
  port honest; Q13's settled shape already says "`link` only if Q02 gives it a caller".
- A link credential is a new trust boundary that needs its own ADR, and its rate limiting is Phase 20 scope ("Rate
  limiting of auth endpoints ... (Phase 20)", scope.md). Shipping a credential endpoint before its hardening phase is the
  wrong order; a careful maintainer would want the flow designed once for Discord and Slack (plan 19 reuses the port,
  implementation-plan.md:1610,1616), not shaped by Discord alone.
- A is consistent with D01/ADR 0027: bot accounts are separate, cannot reach the web, and the synthetic email is a
  clean marker (`WHERE email LIKE '%@users.invalid'`) that a later linking/merge migration can find. Adding `link` later
  is purely additive (one port method, one adapter method, no schema change: the PK `(platform, external_id)` already
  allows re-pointing `user_id`).
- Cost accepted: an existing web user gets a second, empty account in Discord (vision.md:64 "ambient learning" is only
  half met). This is a product gap, not a correctness defect, and must be stated in "As built" and as a GitHub issue.
- If the panel wants linking now, D (OAuth "Connect Discord") is the architecturally strongest: verification by the
  platform, no new credential type to store/hash/rate limit, reuses the existing OAuth2 client machinery
  (application.yml:38-44 google/github). B/C invent a bespoke credential.

## What would change my mind
Evidence that the human expects existing web users to use their wiki from Discord in this phase (e.g. a roadmap or
vision line that makes linking a Phase 18 deliverable); then I would choose D over B/C.

  constraints for the future design: verified ownership on both sides (prefer platform OAuth), never by email claim;

  rules from web-security.md; shared by Discord and Slack.

  future note.

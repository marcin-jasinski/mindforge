## Reasoning
- validation.md:15 "Allowlists Over Blocklists" and scope.md "Allowlists over blocklists and fail closed" make A the only option that matches the standard; C is open by default (hard objection).
- Precedent: ADR 0022 rejected "an optional operator host allowlist (... empty = all public hosts)" for weakening the boundary; same reasoning applies to "empty = all guilds".
- Fail fast matches AppProperties: `@Validated` root with `@AssertTrue` cross-field checks (`Articles.isLimitsPositive`, AppProperties.java:91). Q08 says the bot is built only when the token is set, so the check is "token blank OR guild list non-empty".
- B makes membership a one-time check: a user removed from the guild or role keeps access through DMs. Role revocation must take effect, and in a DM there is no Member to read roles from. B also couples the access check to identity resolution, while the question requires the check BEFORE identity resolution (Q04 Constraints). That contradicts the constraint, so B is weaker by design.
- D is speculative generality (minimal-implementation.md): role snowflakes are globally unique, so a flat list already says the same thing.
- E adds an event handler and a second behaviour for no gain over rejection; it can be added later. A says "ignore" — keep it at rejection.
- The check is an adapter auth check (CLAUDE.md: thin controllers = "input validation + auth check + delegate"), so it lives in `dev.mindforge.discord`, not in an application service.

## What would change my mind
A human statement that the deployment is a single private guild where DM use is a key need (then B with a live per-command membership lookup, not a cached link).

## Implementation notes
- `AppProperties.Discord`: `String botToken`; `Set<Long> allowedGuildIds = Set.of()`; `Set<Long> allowedRoleIds = Set.of()`; `@AssertTrue(message = "allowed-guild-ids must not be empty when bot-token is set") boolean isGuildAllowlistSetWhenEnabled()` returns `botToken == null || botToken.isBlank() || !allowedGuildIds.isEmpty()`. Binding to `Long` rejects non-numeric ids at startup. Env: `DISCORD_ALLOWED_GUILD_IDS`, `DISCORD_ALLOWED_ROLE_IDS` (comma-separated) in deployment.md and env.example.
- Pure, JDA-free value in the adapter: `record DiscordAllowlist(Set<Long> guildIds, Set<Long> roleIds) { boolean admits(Long guildIdOrNull, Set<Long> memberRoleIds) }` — null guild -> false; guild not in set -> false; roleIds empty -> true; else `!Collections.disjoint(roleIds, memberRoleIds)`. Unit test it directly (18.4 "non-allowed guild rejected" also driven through the command handler fake).
- The handler calls `admits(...)` first, before `DiscordIdentityService`/identity resolution; on false it replies ephemeral fixed text, e.g. "This bot is not available here." — never names guilds/roles; log at DEBUG with guild id only, never the token.
- Register commands as guild-only (JDA `setContexts(InteractionContextType.GUILD)` or per-guild registration on allowed guilds) so DMs do not offer them; keep the `admits` check anyway as the real boundary.
- Record in the Discord ADR / deployment.md: DMs are outbound only (reminders); a reminder text tells the user to run commands in the server.

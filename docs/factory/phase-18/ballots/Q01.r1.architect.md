## Reasoning
- Email is the account's natural key across every surface today: `idx_users_email` UNIQUE NOT NULL (V1__baseline.sql:6,14), `signInWithProvider` matches by email (AccountService.java), and ADR 0019 names the acting user by email (`--user <email>`, CliUsageRunner.java:17-18). A keeps that invariant; B breaks it and leaves a Discord account that the CLI cannot name, which weakens ADR 0019's operator path (no CLI `--user` for a Discord user's KB).
- B ripples into `UserResponse.email` (api/dto/response/UserResponse.java:13), `OAuthLoginSuccessHandler`, the SPA profile and every future reader for an account that, without Q02, can never reach the web anyway. A Discord-only account never signs in to the web (no password, `.invalid` is never a provider-verified email), so the "synthetic address in the UI" risk does not arise in Phase 18.
- RFC 2606 `.invalid` is reserved and never deliverable, so no mail goes to a real person. Phase 19 reuses the same pattern (`slack-<id>@users.invalid`) through the same `createUserAndLink`, with no Discord-only names in the port.
- Gap in plain A (A0): `RegisterRequest` uses `@Email` (api/dto/request/RegisterRequest.java:10), which accepts `x@users.invalid`. An attacker could pre-register `discord-<victim snowflake>@users.invalid` with a password, so the victim's first contact fails on the unique index (lock-out), or, worse, a find-by-email provisioning would hand the attacker the victim's Discord data. Code must own the rule: `AccountService.register`/`signInWithProvider` refuse the reserved domain, and `createUserAndLink` inserts (never finds-by-email).
- A is the most reversible: a later migration can null or replace synthetic addresses with one `WHERE email LIKE '%@users.invalid'`; B's nullable column is hard to undo once NULL rows exist.
- Record the account model in a new ADR (scope requires one for the account model).

## What would change my mind
A requirement that a Discord-provisioned account must sign in to the web or show its profile in Phase 18, or evidence that a non-email user key is already planned (then B with a real `username` key).

## Implementation notes
- Domain: `dev.mindforge.domain.model.ExternalAccounts` (or a static on the identity record) with `String RESERVED_EMAIL_DOMAIN = "users.invalid"` and `static String syntheticEmail(String platform, String externalId)` → `platform.toLowerCase(Locale.ROOT) + "-" + externalId + "@users.invalid"`; validate `externalId` is digits/[A-Za-z0-9] only so the address stays well formed and <= 255.
- Application: `IdentityService.resolve(String platform, String externalId, String displayName)` → `UUID userId`: `findUserId` → else `createUserAndLink(platform, externalId, new User(UUID.randomUUID(), TextRules.singleLine(displayName), syntheticEmail(...), null, null, null, null))`; on a unique-key race (`(platform, external_id)` or email) re-read `findUserId` once.
- `AccountService.register` and `signInWithProvider`: throw `AccountException` (fixed text, e.g. "This email cannot be used") when the normalised email ends with `.invalid`. Unit test for both.
- Display name: Discord global name, else username, through `TextRules.singleLine`, truncated to 255.
- ADR 0027 "A bot user is provisioned with a reserved .invalid email" following the format of docs/adr/0026-*.md; note that Q02 linking re-points the identity and does not merge.

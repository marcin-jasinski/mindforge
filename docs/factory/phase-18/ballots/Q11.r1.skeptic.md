## Reasoning
- RateLimitInterceptor.java holds the window logic with servlet types only at the edges; the counter is about 10 lines (atomic Caffeine compute). Copying it into the Discord adapter keeps the bot free of servlet types and leaves tested web code untouched.
- C leaves a real cost-amplification hole: any allowed-guild member can loop /ask. The allowlist (Q04) bounds who, not how much.
- B gives one shared allowance only for linked accounts (Q02); bot-provisioned users (ADR 0027) have no web session, so sharing buys little. It refactors working web code and invites a generic limiter, which minimal-implementation forbids.
- Failure modes for A: counter is in-process (same as web; single instance, accepted); web and bot allowances add up for a linked user (bounded 2x, acceptable).
- Key by the Discord external id and check BEFORE provisioning, so a flood of first contacts cannot create accounts or call services; a rejected command must call no application service.
- Test: a plain Mockito test with a fake clock or small window, asserting the rejected command calls no service and the message shows N s.
## What would change my mind
Evidence that bot and web users are routinely linked and spend must be one shared cap (then B).

- id: S1
  severity: major
  confidence: 0.8
  location: src/main/java/dev/mindforge/infrastructure/web/HttpArticleSource.java:88
  claim: The 15 s total per URL (D06, ticket "one deadline per fetch across all hops") is not enforced while the client connects or reads response headers, so a hostile server can hold a fetch open for an unlimited time.
  evidence: The deadline is checked only before each hop (timeLeft at line 88) and after each 8 KB body read (line 174). Between those points, the only limits are per-operation socket timeouts. A response timeout in HC5 is SO_TIMEOUT, so it restarts on every read. A server that sends one header byte every 10 s (with request-timeout 15s) never trips SO_TIMEOUT, and Http1Config has no header deadline, so executeOpen (line 90) blocks for as long as the server goes on sending. The connect phase is not bounded by the deadline either: the 5 s connect timeout applies to each resolved address in turn (a name with 4 blackholed public A records takes 20 s before the first byte). There is also a third gap: when less than 1 ms is left, Timeout.of(left, NANOSECONDS) becomes 0 ms as a socket timeout, which means "infinite". The URL comes from a user-uploaded document, so an uploader controls the server. The test (300 ms timeout, handler sleeps 2 s before it sends anything) does not cover a slow trickle.
  fix: Enforce the deadline from outside the blocking call. When the hop starts, schedule request.cancel() at the deadline (for example with a shared ScheduledExecutorService or CompletableFuture.delayedExecutor) and cancel the scheduled task when the hop ends. Map the failure that follows the cancel (HC5 RequestFailedException, or an IOException when System.nanoTime() is past the deadline) to TIMEOUT. Also clamp the response timeout to at least 1 ms. Add a test with a handler that sends header bytes slowly.

- id: S2
  severity: major
  confidence: 0.75
  location: src/main/java/dev/mindforge/infrastructure/web/HttpArticleSource.java:68
  claim: The client keeps the HC5 default of unlimited header line length and header count, so a hostile server can send a header that never ends. The 2 MB cap from D06 does not apply to headers, and the client buffers the header in memory until the JVM runs out of heap.
  evidence: The pooling connection manager uses ManagedHttpClientConnectionFactory with Http1Config.DEFAULT. In httpcore5 5.4.2, Http1Config.Builder sets maxLineLength = -1 and maxHeaderCount = -1 (checked with javap). With -1, SessionInputBufferImpl.readLine adds to its CharArrayBuffer and never stops. Example: a linked server sends "HTTP/1.1 200 OK\r\nX: " and then endless bytes. readCapped never runs, because the client is still parsing the headers. The JVM is the whole MindForge server, so one URL in an uploaded document can stop the application. S1 makes this worse, because no deadline stops the read.
  fix: Build the connection manager with a ManagedHttpClientConnectionFactory that uses Http1Config.custom().setMaxLineLength(8192).setMaxHeaderCount(100) (or similar fixed limits), through PoolingHttpClientConnectionManagerBuilder.setConnectionFactory. Map the MessageConstraintException that results (an IOException) to a fixed reason. Add a test with an oversized header.

- id: S3
  severity: major
  confidence: 0.7
  location: src/main/resources/application.yml:61
  claim: The property pin does not keep the OAuth2 login client on the JDK transport. With httpclient5 on the classpath, the authorization-code token exchange now goes through Apache HttpClient 5. This contradicts D04 ("Keep every other Spring HTTP client on the JDK transport") and AC13.
  evidence: SecurityConfig uses .oauth2Login(...) with the default token client. In spring-security-oauth2-client 7.1.0, AbstractRestClientOAuth2AccessTokenResponseClient builds its client with RestClient.builder(). That is the plain Spring Framework builder, not Boot's auto-configured builder, so spring.http.clients.imperative.factory does not apply to it. In spring-web 7.0.8, DefaultRestClientBuilder.initRequestFactory checks HTTP_COMPONENTS_CLIENT_PRESENT first and returns new HttpComponentsClientHttpRequestFactory(), which uses HttpClients.createSystem(), a system-properties client. Boot 4.1 spring-boot-security-oauth2-client does not register a token response client that would override this. The gate's integration tests do not run a token exchange, so they cannot catch it.
  fix: Choose one of these. (a) In SecurityConfig, set .oauth2Login(l -> l.tokenEndpoint(t -> t.accessTokenResponseClient(...))) with a RestClientAuthorizationCodeTokenResponseClient whose RestClient has a JdkClientHttpRequestFactory. Keep that client's message converters and error handler. (b) Record a decision that the OAuth2 token exchange runs on HC5, and correct AC13, D04 and the application.yml comment.

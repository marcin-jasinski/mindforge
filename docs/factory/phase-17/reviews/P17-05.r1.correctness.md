- id: C1
  severity: major
  confidence: 0.8
  location: src/main/java/dev/mindforge/infrastructure/web/HttpArticleSource.java:63
  claim: Response headers are unbounded in size and count, so a hostile article server can make the fetcher buffer headers until the JVM runs out of memory; the 2 MB body cap does not cover them.
  evidence: The client is built with the default connection factory, so it uses `Http1Config.DEFAULT`. In httpcore5 5.4.2, `Http1Config$Builder()` sets `maxLineLength = -1` and `maxHeaderCount = -1` (javap shows `iconst_m1` for both), which means no limit. HC5 parses all headers inside `client.executeOpen(...)` (line 90) before `article(...)` or `readCapped` can apply the cap or the deadline. Scenario: an uploaded document links to `https://evil.example/`. The server sends `HTTP/1.1 200 OK\r\nX: ` and then streams `a` bytes with no CRLF at full line speed. The response timeout is a socket inactivity timeout, so it never fires. The header line buffer keeps growing until OutOfMemoryError, which affects the whole process and every tenant.
  fix: Build the connection manager with `.setConnectionFactory(ManagedHttpClientConnectionFactory.builder().http1Config(Http1Config.custom().setMaxLineLength(8192).setMaxHeaderCount(100).build()).build())`. Add a test where the server sends one header line longer than the limit.

- id: C2
  severity: major
  confidence: 0.75
  location: src/main/java/dev/mindforge/infrastructure/web/HttpArticleSource.java:88
  claim: The "15 s total per URL" deadline is not enforced while HC5 is inside one blocking call (connect to each resolved address, status line and headers, a chunk-size line), so a slow-trickling server can keep one fetch running indefinitely.
  evidence: The only deadline controls are `responseTimeout = timeLeft(deadline)`, which is an SO_TIMEOUT that every received byte resets, and `timeLeft(deadline)` after each 8 KB `read` in `readCapped`. Scenario: the server sends one header byte every (timeout - 1) seconds. Each socket read returns before SO_TIMEOUT, and `executeOpen` does not return until the headers end, so `fetch` never throws TIMEOUT. The chunked-body case behaves the same way (a trickled chunk-extension line stays inside one `body.read`). The connect phase is not tied to the deadline either: `ConnectionConfig.connectTimeout` (5 s) applies to each resolved address. A hop that starts with 0.1 s left, to a host whose N addresses do not answer, therefore runs about N x 5 s past the deadline. Ticket D06 and Notes require one deadline that covers all hops, and exceeding it must give TIMEOUT.
  fix: Before each `executeOpen`, schedule a hard abort at the deadline, for example `ScheduledFuture<?> abort = scheduler.schedule(request::cancel, timeLeft, NANOSECONDS)` from a single daemon scheduler that the source owns and closes in `close()`. Cancel the future in the `finally`. Map the resulting `InterruptedIOException`/`RequestFailedException` to TIMEOUT, as the code already does. Also cap the connect timeout at `min(connectTimeout, timeLeft)`.

- id: C3
  severity: minor
  confidence: 0.6
  location: src/main/java/dev/mindforge/infrastructure/web/HttpArticleSource.java:88
  claim: When less than 1 ms is left on the deadline at the start of a hop, the response timeout becomes 0 ms, which HC5 and the socket treat as "no timeout", so that hop can block with no limit.
  evidence: `timeLeft` only rejects `left <= 0` nanoseconds. `Timeout.of(500_000, NANOSECONDS)` becomes 0 when HC5 converts it to the int milliseconds it passes to `Socket.setSoTimeout`, and `setSoTimeout(0)` means wait forever. Scenario: a redirect chain whose fifth hop starts 0.5 ms before the deadline, to a server that never answers. The fetch hangs instead of failing with TIMEOUT.
  fix: In `timeLeft`, treat less than 1 ms as expired (`if (left < 1_000_000) throw TIMEOUT`), or round up to at least 1 ms. The C2 abort also covers this case.

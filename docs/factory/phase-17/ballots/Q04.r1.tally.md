## Options merged
- Architect "D" (Apache HttpClient 5 + custom `DnsResolver`) is renamed D-HC5. Skeptic "D" (OkHttp + custom `okhttp3.Dns`) is renamed D-OKHTTP.
- D-HC5 and D-OKHTTP are NOT merged. They use the same mechanism (a resolver hook that returns only checked addresses, TLS stays by name, manual redirects re-checked per hop). But the question asks "which HTTP client does it use", and the two differ in substance on that half: D-HC5 adds a new runtime artifact and changes Spring Boot's `ClientHttpRequestFactory` auto-detection for every `RestClient.Builder` (Spring AI included), so it needs a `spring.http.client.factory=jdk` pin; D-OKHTTP adds no jar (already shipped transitively) but carries an okhttp 4.12 / okhttp-jvm 5.3.2 split-package risk. Different dependency and risk profile = different options.
- Pragmatist "D" (Apache HC5 `DnsResolver`) = D-HC5. Pragmatist/skeptic "E" (JVM-wide `InetAddressResolverProvider`) kept as E.
- All three ballots agree on the redirect half: client redirects off, code follows 301/302/303/307/308, `EgressPolicy` re-check per hop, max 5, address check on resolved `InetAddress` values (not the host string). This part is settled in substance for round 2.

## Eliminated
- A: verified hard objection (architect; skeptic concurs) — on the only no-dependency client (JDK HttpClient), connecting to the checked IP needs the global restricted-header flag and a global hostname-verification disable, a JVM-wide TLS downgrade for Spring AI and OAuth2 calls too.
- C: verified hard objection (pragmatist; architect and skeptic concur) — http->https and short-link redirects are the normal case for article URLs (question Context says so), so a 3xx-as-failure defeats plan 17.2's purpose with no security gain over per-hop re-checks.
- E: verified hard objection (skeptic; pragmatist concurs) — a JVM-wide resolver filter also resolves the datasource, OTLP and dev model provider (`application-dev.yml:29`, localhost) and cannot tell an article lookup from those.

## Options
| id | option | correct | fit | simple | risk | reversible |
|----|--------|---------|-----|--------|------|------------|
| A  | Resolve + check, connect to the checked IP (Host header / SNI by hand), manual redirects re-checked per hop | 4 | 2 | 1 | 2 | 3 |
| B  | Resolve + check all addresses, JDK HttpClient connects by name (redirect NEVER), manual redirects (max 5) re-checked per hop | 4 | 5 | 4 | 4 | 5 |
| C  | B but a 3xx is a failed fetch | 2 | 4 | 5 | 4 | 5 |

## Reasoning
- No HTTP client exists in `src/main` (scope.md "Existing state"); JDK `java.net.http.HttpClient` adds no dependency, which `docs/standards/global/conventions.md` (minimal dependencies) favours.
- A is not clean with the JDK client: `Host` is a restricted header (needs the JVM-wide `jdk.httpclient.allowRestrictedHeaders`), and an HTTPS connect to an IP literal breaks hostname verification and SNI unless we hand-build `SSLParameters` and override endpoint identification. That is security-sensitive custom TLS code — more risk, not less.
- D is the strong form but adds Apache HttpClient 5 (new dependency, tech-stack.md entry) for a narrow window. E changes DNS for the whole JVM (Postgres, OTLP, provider on localhost) — breaks dev profile (scope.md disagreement 2).
- B's rebinding window is small in practice: the JDK HttpClient resolves through `InetAddress`, which shares the JVM positive DNS cache (`networkaddress.cache.ttl`, 30 s by default without a security manager). The check's `getAllByName` and the connect, milliseconds later, normally read the same cached answer; an attacker's TTL-0 answer does not bypass that cache.
- Redirects: `HttpClient.Redirect.NEVER`, and code follows 301/302/303/307/308 up to 5 hops, resolving `Location` against the current URI and passing every hop through `EgressPolicy.check` (meets "every hop passes EgressPolicy"). This is ~20 lines.
- C fails real article links (http->https, short links), so it does not meet 17.2's purpose.
- B fits Q13 option A: the policy takes an injected resolver function, so tests map a public-looking name to loopback without a production switch.

## What would change my mind
Evidence that the JDK HttpClient connect bypasses the InetAddress cache, or a project rule that a residual rebinding window is unacceptable (then D, with the dependency documented).

## Implementation notes
- `infrastructure/security/EgressPolicy`: `URI check(String url)` -> validates scheme (`http`/`https`), port, host; resolves via injected `Function<String, InetAddress[]> resolver` (prod: `InetAddress::getAllByName`); rejects if ANY address is loopback/site-local/link-local/any-local/multicast/CGNAT 100.64/10/IPv6 ULA fc00::/7/IPv4-mapped private. Parse odd IP spellings by trusting the resolved `InetAddress` bytes, not the host string. Throws a domain-meaningful `EgressDeniedException`.
- `infrastructure/article/HttpArticleClient` (or inside the fetcher adapter): one `HttpClient` bean built in `@Configuration` with `followRedirects(Redirect.NEVER)`, `connectTimeout`; per-request `timeout`. Loop: `uri = policy.check(url)`; send GET; if 3xx and hops < 5 -> `url = uri.resolve(location)`, repeat; else fail with fixed text "too many redirects".
- Cap body size while reading (`BodyHandlers.ofInputStream` + limit, per Q06).

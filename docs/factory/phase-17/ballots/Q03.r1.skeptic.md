## Reasoning
- SSRF needs an attacker-controlled URL. The only such source after Phase 17 is article URLs in uploaded blocks. Model,
  OTLP and OAuth2 endpoints come from env/config only; no API endpoint sets a base URL (grep of `src/main/java/dev/mindforge/api` finds none).
- `web-security.md:73` scopes the rule: "external URLs, and image URLs are **untrusted**" and forbids
  `restTemplate.getForObject(userProvidedUrl, ...)`. `architecture.md:276` says the same: "external URLs are validated via ... `EgressPolicy`".
- B: an exemption list for localhost on the model endpoint is the same trust decision as A, plus a wrapper around three
  framework HTTP stacks. More code means more ways to break login, tracing or every model call, with zero SSRF gain.
- C: Phase 20.1 already is a checklist pass against `web-security.md` (implementation-plan.md:1604). A recorded "B later"
  is a speculative future item (minimal-implementation.md) for work that has no threat to remove.
- D fails silently: the real risk with A is a later class (e.g. image fetch, webhook) opening HTTP to a content URL
  without the policy. Docs do not catch that; a test does. So the guard test in A is the load-bearing part.
- Failure modes A must still close inside the fetcher (else "goes through EgressPolicy" is a lie): redirects (each hop
  must be re-checked; use `HttpClient.Redirect.NEVER` and follow manually), DNS rebinding / names that resolve to private
  addresses (check the resolved `InetAddress`, connect to that address), IPv6 loopback/link-local/ULA and IPv4-mapped
  IPv6, and non-http(s) schemes.

## What would change my mind
Evidence that any endpoint URL (model base URL, OTLP host, OAuth issuer) can be set by a user through the API or a
knowledge-base setting; then it is untrusted input and must go through the policy.

## Implementation notes
- Doc: `docs/project/architecture.md` § "Security & Trust Model": "`EgressPolicy` guards every URL that comes from
  content or a user. Operator-configured endpoints (`OPENROUTER_BASE_URL`, `LANGFUSE_HOST`, OAuth2 providers) are trusted
  configuration and are not checked." Same line in the checklist evidence and in `web-security.md` § Untrusted Input.
- Guard test (no ArchUnit in `pom.xml`; do not add it for one rule): plain JUnit `OutboundHttpGuardTest` under
  `src/test/java/dev/mindforge/unit/infrastructure/security/` that walks `src/main/java` and asserts that only the
  article fetch adapter (e.g. `infrastructure/article/HttpArticleSource.java`) imports `java.net.http`, `java.net.URL`
  `openConnection`, `HttpURLConnection`, `RestClient`, `RestTemplate` or `WebClient`. Fail with the offending file name.
- In the fetcher: `EgressPolicy.check(URI)` before every request and every redirect hop; resolve host, reject
  loopback/site-local/link-local/any-local/multicast/ULA/IPv4-mapped; allow only `http`/`https`.
- Consider an ADR only if Q01 also produces one; otherwise the architecture.md line is enough.

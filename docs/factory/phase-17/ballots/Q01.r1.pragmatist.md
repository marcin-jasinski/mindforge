## Options
| id | option | correct | fit | simple | risk | reversible |
|----|--------|---------|-----|--------|------|------------|
| A  | Synchronous in `IngestionService.ingest` after the upload commit, only for a newly inserted non-ARTICLE document; each article via `ingest(...)` in its own transaction | 4 | 4 | 5 | 3 | 5 |
| B  | New `DocumentAccepted` domain event + `AFTER_COMMIT` listener fetches on a virtual thread | 4 | 3 | 3 | 4 | 4 |
| C  | After the parent's INGEST run completes (hook in `RunWorker` or run-completed event) | 4 | 2 | 2 | 3 | 3 |
| D  | Fetch as a step inside `IngestPipeline` | 2 | 1 | 3 | 1 | 2 |
| E  | (new) Same trigger point as A, but `IngestionService` hands the fetch to the existing injected `Executor` (`runExecutor`) after commit; no new event | 4 | 4 | 5 | 4 | 5 |

## Reasoning
- `IngestionService.ingest` already knows after its transaction whether a document was inserted (`accepted.run() != null`), so the trigger needs no new event: that is the smallest correct hook. A and E share it.
- Ordering is not a reason for C: the parent's run is enqueued in the upload transaction, so every article run is queued later and the worker takes runs oldest first per knowledge base (ADR 0015 amendment "claims the oldest per knowledge base"). Articles land after the parent anyway.
- B adds a domain event type and a listener for one caller; the ADR 0015 amendment keeps `IngestRunQueued` as the only run event. The missed-event and crash failure mode is the same as A/E, so B buys nothing extra.
- C adds a `RunWorker` dependency or a run-completed event, and a retry/sweep of the parent would re-trigger the fetch unless guarded. More code, more state.
- D: hard objection; ADR 0013 closed pipeline and the lease would be held across HTTP timeouts.
- A vs E: the only difference is one constructor argument. `RunWorker` already takes an `Executor` (`PipelineConfig.runExecutor()`, line 65), and `java.util.concurrent.Executor` is JDK, so the application layer may use it. E keeps the upload/CLI response fast (N URLs x timeout can take tens of seconds) and tests stay deterministic with `Runnable::run`. If others prefer A, A is acceptable; it differs from E in one line.
- Retry and sweep do not fetch again (they call `enqueue`, not `ingest`): good, a fetch is a one-time effect of an accepted upload.
- Off by default: the check `settings.fetchExternalArticles()` happens before any URL extraction.

## What would change my mind
Evidence that a background task outside a request breaks a project rule (e.g. auth context needed by `ingest`), or that the upload response must report the articles queued (then A).

## Implementation notes
- `IngestionService` constructor gains `ArticleSource articles` (domain port, name per Q09), `boolean fetchExternalArticles` (or `ProcessingSettings`), and `Executor executor`; wired in the existing `@Configuration` with `runExecutor`.
- In `ingest`, after `progress.notify(...)`: `if (accepted.run() != null && fetchExternalArticles && upload.source() != UploadSource.ARTICLE) executor.execute(() -> queueArticles(kbId, upload.uploadedBy(), parsed.blocks()));`
- `private void queueArticles(UUID kbId, UUID userId, List<ContentBlock> blocks)`: for each fetched article call `ingest(new DocumentUpload(kbId, userId, UploadSource.ARTICLE, ...))` (own transaction each; dedup and lesson rule reused); catch `LessonAlreadyExistsException` -> `log.info` skip (T18); catch `UploadRejectedException`/`LessonIdentityException` and the fetcher's domain exception -> `log.warn` with fixed text; catch-all around the whole task so a failure never escapes the executor silently.
- The `source != ARTICLE` guard also enforces "no recursion" (Q11).
- Tests: unit test with a direct executor (`Runnable::run`) and a mocked port; one asserting nothing is extracted when the flag is false.

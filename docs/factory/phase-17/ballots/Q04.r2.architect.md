## Reasoning
- New evidence since round 1: ADR 0022 is Accepted (status line 3) and its Consequences (lines 26-27) say "The fetcher must connect to the checked address (no second resolution)". B performs a second resolution by design, so B now has a hard objection. Both D options meet the ADR.
- D-HC5 vs D-OKHTTP is a dependency-hygiene question. HC5: version managed by the Boot 4.1.0 BOM (`spring-boot-dependencies-4.1.0.pom:77` `httpclient5.version 5.6.1`), one artifact, one version, one source of `org.apache.hc` classes.
- OkHttp: Boot 4.1 BOM does not manage it (no okhttp entry in that pom), so the direct declaration must hard-code 4.12.0. The jar ships BOTH `okhttp-4.12.0.jar` and `okhttp-jvm-5.3.2.jar` (different artifactIds, so Maven does not dedupe). Both define `okhttp3.*`; which `OkHttpClient`/`Dns` path runs is decided by classpath order, not by the pom. A security control whose implementation is chosen by jar order is the thing a maintainer will not agree with in a year; a later Spring AI or OTel upgrade can silently swap it.
- HC5 cost: Spring's RestClient default factory detection prefers HC5 when present, so other `RestClient` users (OAuth2 token calls) change transport. This is a visible, documented behaviour with a one-line pin (Boot `spring.http.client(s)...factory: jdk`) or simply accepted; it does not weaken the SSRF control. conventions.md:15-16 only asks to document why a major dependency is added (tech-stack.md entry).
- Redirect half is settled across all ballots: client redirects off, code follows 301/302/303/307/308, `EgressPolicy.check` per hop, max 5.
## Round 2
- Pragmatist (B): the JVM-cache argument is sound in practice, but ADR 0022 (accepted after round 1 framing) forbids a second resolution; B is out on fit, not on taste.
- Skeptic (D-OKHTTP): agree on the mechanism and on its caveats (IP literals skip `Dns`, force NO_PROXY). "No new jar" is real, but the okhttp 4/5 split is unresolved and the version is unmanaged by the BOM; I hold D-HC5. D-OKHTTP is my clear second choice and I have no hard objection to it.
## What would change my mind
Evidence that the okhttp 4.12/okhttp-jvm 5.3.2 duplication is resolved (one okhttp on the classpath) - then D-OKHTTP; or evidence that HC5 auto-detection breaks Spring AI/OAuth2 in a way the factory pin cannot undo.
## Implementation notes
- `pom.xml`: `org.apache.httpcomponents.client5:httpclient5` (no version, Boot BOM), comment "SSRF: DnsResolver pins the checked address (ADR 0022, Q04)"; `docs/project/tech-stack.md` Key Dependencies entry. Optional pin of Spring's default request factory to JDK so other RestClients keep their transport.
- `dev.mindforge.infrastructure.security.EgressPolicy`: `URI check(String url)` and `List<InetAddress> resolve(String host)` (reject if ANY address fails `isPublicUnicast`; IP-literal hosts checked in `check`).
- `dev.mindforge.infrastructure.article.CheckedDnsResolver implements org.apache.hc.client5.http.DnsResolver` -> `egressPolicy.resolve(host)`; `resolveCanonicalHostname` returns host unchanged.
- `@Configuration` builds `CloseableHttpClient` via `PoolingHttpClientConnectionManagerBuilder.setDnsResolver(...)`, connect/response timeouts, `disableRedirectHandling()`, no system proxy (`useSystemProperties()` not called).
- `HttpArticleFetcher`: loop max 5 hops, `uri.resolve(location)`, `egressPolicy.check(next)` before each request, body size cap, fixed failure text. Tests: redirect to 127.0.0.1 refused, name resolving to loopback refused via the resolver seam (Q13).

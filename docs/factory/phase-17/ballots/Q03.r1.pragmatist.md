## Reasoning
- The governing standard already scopes the rule to untrusted URLs: `web-security.md:73` "All uploaded filenames,
  external URLs, and image URLs are **untrusted** ... `egressPolicy.check(externalUrl)`", and its NEVER example is
  `restTemplate.getForObject(userProvidedUrl, ...)` (SSRF). `architecture.md:275-276` (Trust Model) says the same:
  "external URLs are validated via ... `EgressPolicy`". The checklist line is a summary of that rule, not a wider one.
- Operator-set endpoints (`OPENROUTER_BASE_URL`, `LANGFUSE_HOST`, OAuth2 issuers) carry no SSRF risk: no user controls
  them. Checking them adds no security and B must then add an exemption list that re-allows exactly what it checks.
- B breaks local dev unless that exemption exists (dev model endpoint is localhost) and needs wrappers around HTTP
  clients that Spring builds (Spring AI, Spring Security OAuth2 client, OTel exporter): large, framework-coupled code.
- C adds nothing to A except a planned item; Phase 20.1 already "verif[ies] each requirement in web-security.md"
  (implementation-plan.md:1604-1607), which is where B would be reconsidered anyway. Recording a future stub is what
  minimal-implementation discourages. No harm if a one-line note is added, but it is not needed.
- The guard test can be a plain JUnit test (no new dependency; no ArchUnit in pom.xml today) that scans `src/main/java`
  for HTTP-opening APIs and allows them only in the article HTTP adapter. That makes the scope claim checkable.

## What would change my mind
Evidence that some operator endpoint can be set by a non-operator (e.g. a per-KB or per-user configurable URL), or an
ADR/standard that requires all egress be policed regardless of source.

## Implementation notes
- Docs: `docs/project/architecture.md` § "Security & Trust Model" — add: "`EgressPolicy` governs every URL that comes
  from content or a user (article URLs today). Operator-configured endpoints (model provider base URL, Langfuse OTLP
  host, OAuth2 providers) are trusted configuration and are not checked; the dev profile's localhost model endpoint
  depends on this." Cite in the Phase 17 checklist evidence; implementation-plan checklist line reworded to
  "All outbound HTTP to content-derived URLs goes through `EgressPolicy`".
- Test: `src/test/java/dev/mindforge/unit/infrastructure/security/OutboundHttpScopeTest.java` — plain JUnit, walks
  `src/main/java`, fails if `java.net.http.HttpClient`, `HttpURLConnection`, `URL#openConnection`/`openStream`,
  `RestClient`, `RestTemplate`, `WebClient` or `Jsoup.connect` appear outside the single article HTTP adapter
  (e.g. `infrastructure/article/HttpArticleSource.java`), and asserts that adapter calls `egressPolicy.check(`.
- No ADR needed unless the panel wants one; if written, a short ADR "Egress policy scope: untrusted URLs only".

## Reasoning
- Impact is full-read SSRF: the fetched body becomes a Document and wiki pages the uploader reads, so a hit on 169.254.169.254 or a loopback admin port leaks its response. The check must hold at connect time, not only at check time.
- A breaks in the TLS layer: the JDK client derives SNI and endpoint identification from the URI host; connecting to `https://<ip>` sends no SNI and fails hostname verification unless one turns on `jdk.internal.httpclient.disableHostnameVerification` (a global security downgrade) and re-implements verification. `Host` is a restricted header (needs the global `jdk.httpclient.allowRestrictedHeaders`). Many hand-made parts, each a silent bypass if wrong.
- B's window is real but narrow: check and connect share the JVM positive DNS cache (default 30 s), so a rebinding answer wins only if the cache entry expires in the ms between them (attacker can prime the entry with an earlier URL in the same document and retry many uploads). It also depends on an operator not setting `networkaddress.cache.ttl=0`. The guarantee is probabilistic and untestable.
- D closes rebinding by construction: OkHttp calls `Dns.lookup` and connects only to the returned addresses; certificate checks remain by name. Evidence it is in reach: `target/mindforge-1.1.0-SNAPSHOT.jar` ships `BOOT-INF/lib/okhttp-4.12.0.jar` (compile scope via `spring-ai-openai-2.0.0.pom` line 99-102) and `okhttp-jvm-5.3.2.jar` (runtime via `opentelemetry-exporter-sender-okhttp`). Declaring it directly adds no jar; conventions.md:16 only asks to "document why".
- D risks and how we find out: (1) OkHttp skips `Dns` for IP-literal hosts - so `EgressPolicy.check(url)` must parse and reject literals before every hop (test: `http://2130706433/`, `0x7f.1`, `[::ffff:127.0.0.1]`); (2) a system proxy bypasses `Dns` - force `Proxy.NO_PROXY` (test asserts it); (3) okhttp 4.12 and okhttp-jvm 5.3.2 share package `okhttp3` today - pin the direct dependency to the version the OpenAI client already uses and use only API common to both (`Dns`, `Builder.dns/proxy/followRedirects/callTimeout`); `mvn verify` catches a linkage error.
- C fails common http->https and short-link articles; a 3xx-as-failure is a correctness loss with no security gain over manual per-hop checks.
- Redirects in every option: never let a client follow automatically; each `Location` is resolved against the current URL and passes the same `EgressPolicy` (scheme, port, host, addresses), cap 5 hops, then a fixed failure reason.

## What would change my mind
Evidence that the okhttp 4/5 split breaks at runtime or that the team refuses to declare it (then B, with the cache caveat recorded in architecture.md "Security & Trust Model"); or a clean JDK way to pin the address while keeping SNI and hostname verification by name.

## Implementation notes
- `dev.mindforge.infrastructure.security.EgressPolicy`: `URI check(String url)` (scheme http/https, port 80/443 or none, no userinfo, IP-literal hosts parsed and checked) and `List<InetAddress> resolve(String host)` (getAllByName; throw `EgressDeniedException` if ANY address is not public unicast; unwrap IPv4-mapped/compat/NAT64/6to4).
- `dev.mindforge.infrastructure.article.PolicyDns implements okhttp3.Dns` -> `egressPolicy.resolve(host)`.
- `HttpArticleFetcher` (infrastructure, behind the Q09 port): one `OkHttpClient` bean in a `@Configuration` with `.dns(policyDns).proxy(Proxy.NO_PROXY).followRedirects(false).followSslRedirects(false).callTimeout(...)`; loop max 5 hops, `egressPolicy.check(next)` before each call, body size cap, fixed failure text.
- Test seam (Q13): the "is public" predicate is a constructor argument so `ArticleFetcherTest` can admit the loopback mock server; one test keeps the real predicate and asserts the loopback server is refused, and one asserts a redirect to `127.0.0.1` is refused.
- pom: declare `com.squareup.okhttp3:okhttp` explicitly with a comment; add it to tech-stack.md "Key Dependencies Summary".

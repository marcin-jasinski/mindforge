## Reasoning
- The governing standard already scopes the rule: `web-security.md:73` "All uploaded filenames, external URLs, and image
  URLs are **untrusted**"; the anti-example (`:82`) is `restTemplate.getForObject(userProvidedUrl, ...)  // SSRF risk`.
  The checklist line is a restatement of this rule, so its scope is untrusted URLs, not operator config.
- `architecture.md` § "Security & Trust Model" (line ~276) says "filenames and external URLs are validated via
  `UploadSanitizer` and `EgressPolicy`" — same untrusted-input framing. A is the reading that matches both documents.
- B contradicts the dev constraint (LM Studio on localhost) unless an exemption list exists, and an exemption list for
  the very endpoints that would be checked makes the check a no-op with large surface: it wraps HTTP clients built by
  Spring AI, the OTLP exporter and Spring Security OAuth2, none of which MindForge code constructs. That is the
  speculative generality `minimal-implementation.md` forbids, and adds no SSRF protection (operator sets these URLs).
- C records future work that has no threat behind it; Phase 20.1 already re-verifies `web-security.md`, which carries
  the untrusted scope, so a separate "B later" item is a stub plan item. Not wrong, but adds nothing a maintainer needs.
- D vs A: scope.md says "an ADR if Q01/Q03 make a load-bearing decision". The trust boundary is load-bearing (it is what
  later phases — bots in 18–19 that may take user URLs — will rely on), but the decision is a clarification of an
  existing standard, not a new one. I prefer A with an explicit paragraph in architecture.md's trust model; a short ADR
  is acceptable if the orchestrator wants one. I vote A.

## What would change my mind
Evidence that a non-operator (user, tenant, or content) can influence the model base URL, OTLP host or OAuth2 issuer
URIs at runtime (e.g. per-KB provider settings) — then those become untrusted and B-style coverage is needed.

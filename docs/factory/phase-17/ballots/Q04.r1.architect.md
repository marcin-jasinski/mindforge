## Options
| id | option | correct | fit | simple | risk | reversible |
|----|--------|---------|-----|--------|------|------------|
| A  | Resolve+check, JDK HttpClient connects to the checked IP literal, Host/SNI by hand, manual redirects | 2 | 2 | 2 | 2 | 3 |
| B  | Resolve+check all addresses, JDK HttpClient connects by name (JVM DNS cache narrows the window), redirects NEVER + manual follow with re-check per hop, max 5 | 4 | 4 | 4 | 3 | 5 |
| C  | B with 3xx = failed fetch | 3 | 3 | 5 | 4 | 5 |
| D  | Apache HttpClient 5 (Boot-managed version) with a custom `DnsResolver` that resolves, runs every address through `EgressPolicy`, and returns only checked addresses - the client connects to exactly what was checked, TLS SNI and hostname verification stay on the name; redirects disabled and followed by code, each hop re-checked, max 5 | 5 | 4 | 3 | 4 | 4 |

## Reasoning
- The question is "keep the check true at connect time". Only a resolver hook gives that structurally: check and connect use the same answer. Apache HC5 `DnsResolver` is that hook; the JDK client has none (JEP 418 `InetAddressResolverProvider` is JVM-wide and would also hit the dev model provider at `localhost:1234`, scope.md Plan/code disagreement 2).
- A on the JDK client needs JVM-wide flags that weaken TLS for every outbound call (Spring AI, OAuth2) - hard objection. D is A's intent done without that cost.
- B is the honest no-dependency fallback: `InetAddress` positive cache (30 s default) means the client's own lookup usually reuses the checked answer, but that is an implicit JVM setting, not a design guarantee a maintainer can see in code.
- C fails http->https and short links, which most article URLs use; it trades correctness of the feature for simplicity.
- Fit: `docs/standards/global/conventions.md` "Minimal Dependencies ... document why major ones are included" - one Boot-managed artifact with a stated SSRF reason, added to `tech-stack.md` "Key Dependencies Summary", meets that. `httpclient5` 5.6.1 is already in the local Maven repo, so the offline `fast` gate still works.
- Redirects manual in every option (B/D): `EgressPolicy.check(url)` on each `Location`, scheme still http/https only, so "every hop passes EgressPolicy" (Q04 Constraints) holds by construction.
- Odd IP spellings (`2130706433`, `0x7f.1`, `[::ffff:127.0.0.1]`) are handled by checking resolved `InetAddress` values, never the string; Java maps IPv4-mapped IPv6 to `Inet4Address`.
- Side effect to manage: with HC5 on the classpath, Spring Boot's `ClientHttpRequestFactory` detection prefers it for every `RestClient.Builder`, including Spring AI's. Pin the others with `spring.http.client.factory=jdk` (or build the fetcher's client explicitly and leave the global builder untouched) so the dependency changes only the fetcher.

## What would change my mind
Evidence that adding httpclient5 changes Spring AI transport behaviour in a way the property pin cannot undo, or a project decision that no new runtime dependency is allowed this phase - then B.

## Implementation notes
- `pom.xml`: `org.apache.httpcomponents.client5:httpclient5` (no version; Boot BOM). `application.yml`: `spring.http.client.factory: jdk` to keep Spring AI on the JDK client. Document in `docs/project/tech-stack.md`.
- `infrastructure/security/EgressPolicy`: `void check(URI url)` (scheme http/https, allowlist per Q02) and `boolean isPublic(InetAddress a)` (reject loopback, any-local, link-local incl. 169.254/16, site-local, multicast, 100.64/10, 0/8, 255.255.255.255, fc00::/7, fe80::/10); throws `EgressDeniedException` (domain-meaningful, fixed message).
- `infrastructure/article/CheckedDnsResolver implements org.apache.hc.client5.http.DnsResolver`: delegates to an injected `Function<String, InetAddress[]>` (production `InetAddress::getAllByName`; the Q13 test seam), rejects if any address fails `isPublic`.
- `HttpArticleClient` (infrastructure adapter behind the Q09 port): `CloseableHttpClient` built in an `@Configuration` with `PoolingHttpClientConnectionManagerBuilder.setDnsResolver(...)`, connect/response timeouts, `disableRedirectHandling()`, max body size; loop up to 5 hops on 301/302/303/307/308, resolve `Location` against the current URI, `egressPolicy.check(next)` before each hop.

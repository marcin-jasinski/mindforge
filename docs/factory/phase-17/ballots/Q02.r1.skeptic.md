## Reasoning
- The SSRF risk is the address, not the host name. All real failures (169.254.169.254 metadata, loopback admin ports, RFC1918, DNS rebinding, redirect to an internal address, IPv4-mapped/NAT64 forms) are closed by the address check in A. A host list does not close any of them: an allowed host can resolve to 10.0.0.5 or redirect to 127.0.0.1. So B and C add config, not SSRF protection.
- A satisfies "Allowlists Over Blocklists" (docs/standards/global/validation.md:15) if the address rule is written as an allowlist: accept only global unicast (IPv4 not in any special-purpose range; IPv6 only in 2000::/3 minus special ranges, unwrap mapped/compat/NAT64/6to4 to the embedded IPv4), reject everything else by default. Unknown forms fail closed.
- B's failure modes: suffix match without a dot boundary ("example.com" admits "evilexample.com"); trailing-dot, uppercase and IDN/punycode hosts; an empty-vs-unset ambiguity in Spring binding. Each needs code and tests for a knob that no requirement asks for (minimal-implementation.md; scope "no speculative abstractions"). The operator's incident lever already exists: turn fetchExternalArticles off.
- C: an operator who sets the flag true sees no articles and no error - a silent, hard-to-diagnose failure; it contradicts plan 17.2's single switch and the question's own note ("a second off switch").
- How we find out A breaks: EgressPolicyTest enumerates each rejected range (incl. ::ffff:127.0.0.1, 64:ff9b::a00:1, 0.0.0.0, [::], decimal/octal IPv4 literals like http://2130706433/), rejected schemes (file, data, ftp, jar, gopher), userinfo URLs, non-default ports; plus a redirect-to-loopback case in ArticleFetcherTest. A rejection is logged with the URL host and reason enum, never the remote body.
- Reversible: B can be added later as a pure narrowing filter without changing A's contract.

## What would change my mind
A deployment requirement (e.g. a hardened/air-gapped operator) that needs per-host narrowing in Phase 17, or evidence that Q03 routes the model provider through the same policy and needs a host exception list anyway (then B's list could be shared).

## Implementation notes
- `dev.mindforge.infrastructure.security.EgressPolicy` (final class, built in a `@Configuration`): `URI check(String url)` returns the normalized URI or throws `EgressDeniedException(Reason)` (domain-meaningful exception; `Reason` enum: SCHEME, PORT, USERINFO, HOST, ADDRESS, UNRESOLVABLE). Add `List<InetAddress> resolve(URI)` that resolves all A/AAAA records and rejects if ANY is not public.
- Fetch must connect to a validated address, not re-resolve: either a custom resolver/`DnsResolver` in the HTTP client that calls `EgressPolicy`, or connect to the pinned IP with the Host header/SNI set. Disable automatic redirects; follow up to N (e.g. 3) manually, calling `check` on each `Location`.
- Constants, not properties: schemes `{http, https}`, ports `{-1→default, 80, 443}`. No new egress env var for A; only the article switch/timeouts (Q10/Q01) go in AppProperties and deployment.md.
- Test seam for the loopback mock server (Q13): inject the address predicate or resolver into EgressPolicy's constructor; production wiring uses the strict one.

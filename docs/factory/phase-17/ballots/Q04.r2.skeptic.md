## Options
| id | option | correct | fit | simple | risk | reversible |
|----|--------|---------|-----|--------|------|------------|
| B  | JDK HttpClient, resolve+check, connect by name (window narrowed only by JVM DNS cache); manual redirects re-checked per hop, max 5 | 3 | 3 | 4 | 3 | 5 |
| D-HC5 | Apache HttpClient 5 (Boot BOM) with a `DnsResolver` that returns only checked addresses; TLS SNI/hostname verification by name; redirects disabled, followed in code, re-checked per hop, max 5 | 5 | 4 | 3 | 4 | 4 |
| D-OKHTTP | OkHttp (transitively shipped) with a custom `okhttp3.Dns`; `Proxy.NO_PROXY`; same redirect loop | 5 | 3 | 3 | 2 | 4 |

## Reasoning
- B vs D: the sink is full-read SSRF (fetched body becomes wiki pages). B's guarantee rests on `networkaddress.cache.ttl`, an operator-changeable JVM setting, and cannot be tested. The accepted decisions already ask for the stronger form: D02 notes "Expose the resolved, vetted addresses ... so the fetcher connects to them"; D03 notes "check the resolved `InetAddress` ... and connect to that address". B does not meet that; D does by construction. Not a hard objection (no ADR text forbids B), but B is the weaker fit to decided notes.
- D-OKHTTP (my round-1 choice) is worse than I scored it. `unzip -l target/mindforge-*.jar` shows BOTH `okhttp-4.12.0.jar` (from spring-ai-openai) and `okhttp-jvm-5.3.2.jar` (from opentelemetry-exporter-sender-okhttp) in `BOOT-INF/lib`, both with package `okhttp3`, plus `okio-3.6.0` and `okio-jvm-3.16.4`. Which `OkHttpClient` class loads depends on jar order; a mixed load (4.x public class, 5.x internals) fails only at runtime with `NoSuchMethodError`. Our SSRF control would depend on a duplicate-class state owned by two other libraries, and a Spring AI or OTel upgrade can flip it silently. Pinning a direct version does not remove the other jar.
- D-HC5: one explicit, Boot-managed artifact, no duplicate classes; `httpclient5` 5.6.1 is in `~/.m2` (offline gate works, tally confirmed). Its default `HttpClients.custom()` ignores system proxy properties unless `useSystemProperties()` is called, so the proxy bypass of the resolver hook is closed by default (OkHttp needed `Proxy.NO_PROXY`).
- D-HC5 failure modes and detection: (1) Spring's `RestClient.builder()` / Boot builder auto-detect HC5 and switch transport for any other RestClient (OAuth2 token calls, Spring AI if it uses RestClient). No `RestClient` in `src/main` today (grep empty); pin `spring.http.client.factory`/Boot-4 equivalent to `jdk` and cover with the existing integration tests. (2) HC5 5.4+ `DnsResolver` has `resolve(String)` and `resolve(String,int)` default methods; override both (or delegate) so no path skips the check - a unit test asserts a name mapped to 127.0.0.1 is refused through the real client. (3) IP-literal hosts: `EgressPolicy.check` validates them before every hop regardless of client.
- Redirect half settled by all ballots: client redirects off, 301/302/303/307/308 followed in code, `Location` resolved against current URI, full `EgressPolicy.check` per hop, max 5, fixed failure text.

## Round 2
Changed D-OKHTTP -> D-HC5. Convinced by the architect's claim that HC5's `DnsResolver` is the same structural pin, combined with my own re-check of the shipped jar: the okhttp 4.12 / okhttp-jvm 5.3.2 split-package is a live duplicate-class hazard, not a hypothetical, and "no new jar" does not offset a runtime linkage risk inside the SSRF control. I hold against B: pragmatist's DNS-cache argument is correct but probabilistic, operator-dependent and untestable, and D02/D03 notes ask the fetcher to connect to the checked address.

## What would change my mind
Evidence that adding httpclient5 changes Spring AI or OAuth2 transport in a way the factory pin cannot undo (then B with the cache caveat in architecture.md); or the okhttp duplicate removed upstream.

## Implementation notes
- `pom.xml`: `org.apache.httpcomponents.client5:httpclient5` (no version, Boot BOM) with a comment "SSRF: DnsResolver pins checked addresses (ADR 0022/Q04)"; add to `docs/project/tech-stack.md` Key Dependencies; pin the global RestClient request factory to `jdk` in `application.yml`.
- `dev.mindforge.infrastructure.article.CheckedDnsResolver implements org.apache.hc.client5.http.DnsResolver`: `resolve(host)` -> `egressPolicy.resolve(host)` (throws `EgressDeniedException` if ANY address is not public unicast); override `resolve(host, port)` too; `resolveCanonicalHostname` returns host unchanged.
- `HttpArticleFetcher`: `CloseableHttpClient` built in a `@Configuration` with `PoolingHttpClientConnectionManagerBuilder.create().setDnsResolver(checkedDnsResolver)`, connect/response timeouts, `disableRedirectHandling()`, no `useSystemProperties()`; loop max 5 hops with `egressPolicy.check(next)` before each; body size cap.
- Tests: resolver seam (Q13) maps a public-looking name to loopback -> refused through the real client; redirect to `127.0.0.1` refused; 6th hop fails; OutboundHttpGuardTest (D03) also lists `org.apache.hc.client5` as an HTTP-client marker allowed only in the fetcher.

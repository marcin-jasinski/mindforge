## Options
| id | option | correct | fit | simple | risk | reversible |
|----|--------|---------|-----|--------|------|------------|
| A  | Synchronous in `IngestionService.ingest` after the upload commit, only for a new document | 4 | 3 | 5 | 2 | 5 |
| B  | New `DomainEvent.DocumentAccepted` in the upload transaction; `AFTER_COMMIT` listener runs the fetch on `runExecutor` | 4 | 4 | 4 | 4 | 4 |
| B' | Reuse `IngestRunQueued`; listener filters to first INGEST run of a non-ARTICLE, non-CONVERSATION document | 3 | 3 | 3 | 3 | 4 |
| C  | After the parent's INGEST run completes (hook in `RunWorker` or a run-completed event) | 4 | 2 | 2 | 3 | 3 |
| D  | A fetch step inside `IngestPipeline` | 2 | 1 | 2 | 1 | 2 |
| E  | Durable "articles pending" column on `documents`, drained by the sweep | 5 | 2 | 1 | 4 | 2 |

## Reasoning
- Ordering is not a reason for C: in A and B the parent's run is queued in the upload transaction, before any article run, and the worker claims the oldest QUEUED run per knowledge base (ADR 0015 amendment "the worker claims the oldest per knowledge base"). So the parent ingests first in A and B too. C adds a run-completed hook in `RunWorker` and in the sweep's WRITTEN→COMPLETED path, which means two places to forget. If the fetch runs inline, it also blocks the drain loop.
- A's failure mode is bad. The fetch runs after the upload has committed, so any uncaught fetch exception turns a successful upload into a 500. The client then retries, gets the identical-document path, and no fetch happens. N URLs × timeout also holds a 202 open for tens of seconds behind proxies. A hostile or slow external host can directly control how long our request takes.
- B isolates that failure. It uses the existing pattern (`RunWorkerTriggers.onRunQueued`: `@TransactionalEventListener(AFTER_COMMIT)` + `executor.execute`), so the upload latency and status do not change. If a fetch bug happens, it is logged and nothing else breaks.
- Loss window: A and B lose articles in the same case, which is a crash or shutdown during the fetch. B also loses them if the executor rejects the task. Nothing repairs either case. ADR 0015 accepts a missed event only because consumers are "derived or best-effort". This feature is off by default and best-effort, so the loss is acceptable. E fixes the loss, but it needs a migration and a new queue concept. That is speculative for an optional feature (minimal-implementation.md).
- B' fires again on `retry` and on every sweep re-queue (up to three attempts). The lesson rule makes a repeat harmless (the article lesson exists, so it is skipped), but it repeats outbound HTTP to third parties and needs a "first run" query. A dedicated event is clearer and easier to test.
- Re-fetch safety in every option: `IngestionService.ingest` for an article gives dedup by content hash and `LessonAlreadyExistsException` → skip+log. Duplicate triggers do not corrupt data.
- Testability: the listener delegates to an application service `ArticleIngestion.fetchFor(kbId, documentId)`. Unit-test it with Mockito and a direct executor. The listener itself is one line, the same as `RunWorkerTriggers`.
- Watch item: the CLI waits only for the parent run and then exits, so in B a background fetch can be cut off. Document it, or accept it, because the feature is off by default.

## What would change my mind
Evidence that a fetch failure must be visible to the uploader (A then wins on observability). Or a requirement that no article may be lost, which needs E.

## Implementation notes
- `DomainEvent`: add `record DocumentAccepted(UUID documentId, UUID knowledgeBaseId, UUID uploadedBy, Instant occurredAt)` to the `permits` clause. Publish it in `IngestionService.ingest` only in the new-document branch and only when `upload.source()` is not `ARTICLE` (no recursion) and not `CONVERSATION`. Do not publish it in `submitEdit` or `retry`.
- Application: `ArticleIngestion` (application/service). `fetchFor(kbId, documentId)` returns at once if `!settings.fetchExternalArticles()`. Otherwise it loads the document, extracts URLs from its blocks, and calls the `ArticleSource` port (infrastructure: `EgressPolicy` + HTTP + HTML→text) per URL outside any transaction. Then it calls `ingestion.ingest(DocumentUpload(kbId, uploadedBy, UploadSource.ARTICLE, ...))` per article, so each article commits in its own transaction. Catch `LessonAlreadyExistsException`, `UploadRejectedException`, `LessonIdentityException` and fetch failures per URL, and log them. One bad URL must not stop the others.
- Infrastructure: `infrastructure/event/ArticleFetchTriggers` with `@TransactionalEventListener(phase = AFTER_COMMIT) onDocumentAccepted(e) { executor.execute(() -> articles.fetchFor(...)); }`. Wire it in `PipelineConfig` with `runExecutor`. Catch and log all exceptions inside the task.
- Cap the URL count per document and the per-URL timeout in `AppProperties` (bounded total time). Record the cap in deployment.md.
- Tests: `ArticleIngestionTest`: flag off → no port call; lesson exists → skipped and logged, others continue. `IngestionServiceTest`: the event is published only for a new non-article document.

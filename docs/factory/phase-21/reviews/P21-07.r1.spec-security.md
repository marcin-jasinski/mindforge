- id: S1
  severity: minor
  confidence: 0.5
  location: .github/workflows/dependency-check.yml:8
  claim: The new workflow declares no `permissions:` block, so its `GITHUB_TOKEN` gets the repository default scope (write on repos with the legacy permissive default) while it runs third-party Maven plugin code that the job downloads.
  evidence: The file has no top-level or job-level `permissions:` key (`grep -rn permissions .github/workflows/` returns nothing). `actions/checkout@v4` persists the token in `.git/config` by default, so the `mvn -B dependency-check:check` step can read it. The job only needs to read the repository contents and upload an artifact (upload-artifact v4 does not need the `GITHUB_TOKEN` scope). Triggers are `schedule` and `workflow_dispatch` only, so there is no untrusted PR input. The secret goes in through `env:` (not interpolated into `run:`), so it is not exposed. The risk is limited to hardening.
  fix: Add `permissions: { contents: read }` at the top level of dependency-check.yml.

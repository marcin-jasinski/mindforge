- id: C1
  severity: minor
  confidence: 0.8
  location: .github/workflows/dependency-check.yml:20
  claim: The NVD cache is not saved when the check fails, so a known finding stops the weekly NVD data from being kept until the finding is fixed or suppressed.
  evidence: The `actions/cache@v4` post step saves only when the job succeeds (its `post-if` is `success()`). `failBuildOnCVSS=7` (pom.xml:472) makes `mvn -B dependency-check:check` exit non-zero on a finding. When a finding stays open for several weeks, every run restores the last good cache and downloads a longer NVD update each time, and the updated data is never saved.
  fix: Use `actions/cache/restore@v4` before the Maven step and `actions/cache/save@v4` with `if: always()` (same path, key `nvd-${{ github.run_id }}`) after it.
- id: C2
  severity: minor
  confidence: 0.6
  location: .github/workflows/dependency-check.yml:18
  claim: `setup-java` `cache: maven` caches all of `~/.m2/repository`, so it also stores the NVD data, under the same key that the `ci.yml` jobs use.
  evidence: The setup-java maven cache path is `~/.m2/repository` and its key is `setup-java-<os>-maven-<hash of **/pom.xml>`, the same in both workflows. The dependency-check plugin's default data directory is `${settings.localRepository}/org/owasp/dependency-check-data` (no `dataDirectory` set in pom.xml:471-489). When the scheduled run is the first to save a cache for a pom hash (for example after a cache eviction), that cache includes the NVD database, and every later `linux` CI run restores it as well.
  fix: Remove `cache: maven` from this workflow (it resolves few dependencies), or set the plugin `dataDirectory` outside `~/.m2/repository` and point the `actions/cache` path there.

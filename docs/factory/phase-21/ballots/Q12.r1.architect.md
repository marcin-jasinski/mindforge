## Reasoning
- T26 targets page-body syntax: "nobody writes a second regex" for heading, section and link in wiki pages. The validator checks the OKF bundle file grammar of generated index.md and log.md (class javadoc: "OKF section 9 ... a pure function over what the renderers produced"). That is a different grammar: whole-line `* [t](u) - d` items and `## YYYY-MM-DD` headings. MarkdownStructure knows level-1 sections and inline links only.
- The validator is the exporter tests' oracle ("every exported bundle passes", plan 9b). If it used MarkdownStructure, and the renderers or the lint used the same parser, one parser bug would pass both sides. An independent strict grammar is the point of an oracle. Option A weakens that and makes the domain parser grow bundle-file concepts (heading level, index-entry line shape) that no page-body consumer needs.
- Option C leaves a silent hole: any future export-side regex escapes the guard. Option B keeps the guard global, and the exception is one named file with a written reason. This is the existing pattern in OutboundHttpGuardTest (src/test/java/dev/mindforge/unit/infrastructure/security/OutboundHttpGuardTest.java), which allowlists by exact path.
- Make the allowlist narrow: exact path, plus a test that fails if the allowlisted file stops containing an offending pattern (no stale exceptions). Record the reason in T26 follow-up or a short note in the plan 21.3 text.
- Guard mechanism: source scan of Pattern.compile string literals (as OutboundHttpGuardTest does), because ArchUnit cannot see the literals.

## What would change my mind
Evidence that the renderers and validator already drift, or that MarkdownStructure can cheaply expose heading level without a circular-oracle problem (for example the validator keeps its own grammar but delegates only link parsing). Also a human reading of T26 that says "no exceptions".

## Reasoning
- B is the only option that leaves `src/main` unchanged and still meets the plan text: `implementation-plan.md:1785` "Against `docker compose up` with a stub-provider profile". The "profile" can be a compose override (`compose.e2e.yml`, like the existing `compose.override.yml`), not a Spring profile.
- The seam already exists: `application.yml:49` `base-url: ${OPENROUTER_BASE_URL:https://openrouter.ai/api/v1}`. Point it at the fake; no new Java config.
- B exercises the real `AIGatewayAdapter` (Resilience4j retry/circuit breaker, `TracingGateway`, `PermitGateway`, `CostObservationFilter`) and the real Docker image. That is the point of an E2E over `ApiFlowTest`, which already covers the stubbed-gateway path.
- A puts a fake model in the product JAR. It conflicts with the spirit of `minimal-implementation.md` ("Build what you need... No future stubs") for production code, and creates a permanent security obligation (web-security: production must never answer with fake output by default) that needs a guard, a test of the guard, and an ADR forever. Not a hard objection (a guard can satisfy the rule), but a maintainer in a year will ask why `src/main` has a fake.
- C tests a different artifact (test classpath, not the image) and drops "docker compose up"; it duplicates `ApiFlowTest` with a browser. It also couples Playwright (Node) to the Maven test lifecycle.
- Routing is feasible in B: `support/Prompts.java` fragments are stable plain headings (`"# Task: claim extraction"`, etc.) with no JSON-escaped characters, so WireMock `bodyPatterns: [{contains: "# Task: ..."}]` matches the serialized request. `givenAnswers()` answers are static strings, so they map to static JSON mappings.
- Drift risk (mapping fragments duplicated from `Prompts.java`): an unmatched prompt gets WireMock's 404, the run fails, the E2E fails loudly. Acceptable; add a comment in each mapping naming the `Prompts` constant.
- CLAUDE.md "Use `StubAIGateway`" applies to unit/integration tests; B does not mock at `ChatClient` level, it fakes the remote provider, which is outside the hexagon.
- An ADR is needed either way (question constraint). B's ADR is small: "E2E fakes the provider over HTTP; the product has no fake model".

## What would change my mind
Evidence that some step needs a prompt-dependent answer (echoing ids/paths from the prompt) that WireMock templating cannot express cleanly, or that Spring AI's OpenAI client uses a streaming/endpoint shape WireMock mappings cannot serve; then B2 (script server) or C.

## Implementation notes
- `compose.e2e.yml` (repo root): adds service `model` (`image: wiremock/wiremock:3.x`, volume `./src/test/e2e/wiremock:/home/wiremock:ro`), and on `app`: `OPENROUTER_BASE_URL: http://model:8080/v1`, `OPENROUTER_API_KEY: e2e`, `AUTH_SECURE_COOKIES: "false"`, a throwaway `JWT_SECRET`, `depends_on: model`.

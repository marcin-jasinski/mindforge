## Reasoning
- A's main failure mode: one wrong `SPRING_PROFILES_ACTIVE` (for example `dev,stub`) makes prod write canned prose into real users' wikis. The output looks valid, so you only see it in the content. That is a data-integrity failure with no alarm. It also puts test-only code in the product JAR, which goes against `minimal-implementation.md` ("Build What You Need"). It does not run `AIGatewayAdapter` either. This is a soft objection: no accepted ADR forbids a profile, and I found no "fake model output" text in `web-security.md`.
- B adds no production code. The only change is the operator-configured `spring.ai.openai.base-url: ${OPENROUTER_BASE_URL:...}` (`application.yml:49`), which ADR 0023 / `web-security.md:83` treat as trusted config. It runs the real image, `compose.yml`, the Dockerfile and the SPA embedded in the JAR. It also runs `AIGatewayAdapter`: the deadline race, Resilience4j, permits, tracing and `costUsd`. C and A skip all of these.
- The adapter only does plain non-streaming text completions (`AIGatewayAdapter.complete`, no tools, no response_format). The fake therefore needs just one `/chat/completions` shape. The ingest answers in `ApiFlowTest.givenAnswers()` (lines 447-453) are static strings, so WireMock `bodyPatterns.contains` on the `# Task: ...` fragments is enough. No response templating is needed.
- B's failure modes, and how we would see them: (1) Mappings drift from the prompts. The run goes FAILED and the journey goes red, which is loud but not precise. Fix: a unit test that checks every mapping fragment against a `Prompts` constant or prompt resource. (2) An unmatched prompt. A lowest-priority catch-all returns 4xx. `AiConfig.java:51` retries only `TransientAiException`/`IOException`, so it fails fast, and WireMock's `/__admin/requests/unmatched` names the prompt. The CI job dumps this on failure.
- C's breakage: the `gate` runs `-DskipFrontend=true`, and failsafe already includes `**/e2e/**/*Test.java` (`pom.xml:332`). An in-JVM Playwright test would find no SPA on the classpath, so it would fail the gate or need conditional skipping. It also never tests the image or compose, and it departs from plan 21.2's "docker compose up".
- The `test-writing.md` rule "Use `StubAIGateway`… never mock at `ChatClient` level" bans mocks above the adapter. B fakes below it, at the wire, so it does not break the rule. The rule's spirit is to keep the real adapter, and B keeps it.

## What would change my mind
If Q07/Q08 settle on an in-JVM Java Playwright runner inside `mvn verify` with the SPA built, C becomes cheaper and I would accept it. The same goes for a journey step that needs prompt-dependent (templated) answers that WireMock JSON cannot express cleanly. In that case I would choose D.

## Implementation notes
- `compose.e2e.yml` (repo root, used as `docker compose -f compose.yml -f compose.e2e.yml up`, never auto-merged): service `model-stub` with image `wiremock/wiremock` (pinned tag) and volume `./src/test/e2e/model-stub:/home/wiremock:ro`. The `app` service gets `OPENROUTER_BASE_URL: http://model-stub:8080/v1`, `OPENROUTER_API_KEY: e2e-fake`, `AUTH_SECURE_COOKIES: "false"`, a dev `JWT_SECRET`, and `depends_on: model-stub`. Do not publish the stub's port.
- `src/test/e2e/model-stub/mappings/*.json`: one mapping per fragment in `Prompts.java` (GUARD, EXTRACT, WRITE, LINKS, SUPERSEDE, FLASHCARDS, QUIZ, GRADE). Each uses `POST /v1/chat/completions` (check the exact path the Spring AI client calls) with `bodyPatterns: [{contains: "# Task: ..."}]`. The response is an OpenAI chat completion (`id, object: chat.completion, created, model, choices[0].message{role, content}, finish_reason, usage`), and `content` is the JSON string from `givenAnswers()` plus the study answers. Add `zz-unmatched.json` with priority 10 that returns 400 with the body "no e2e stub answer for this prompt".
- `src/test/java/dev/mindforge/unit/e2e/ModelStubMappingsTest.java` (plain JUnit + AssertJ): checks that every mapping's `contains` fragment occurs in some `src/main/resources/prompts/en/*.md`. This catches drift before the E2E runs.
- ADR `docs/adr/0042-e2e-model-answers-come-from-a-fake-openai-compatible-server.md`: why no stub profile ships, and that the stub container exists only in `compose.e2e.yml`.

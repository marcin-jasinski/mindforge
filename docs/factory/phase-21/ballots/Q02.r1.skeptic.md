## Reasoning
- pom.xml has no SpotBugs plugin and no config/ dir exists, so this is a greenfield gate (grep found nothing). Plan line 1782 names only SpotBugs.
- B: High-only silently misses most real defects (null deref, resource leaks are often Medium), so the gate gives false assurance; skeptic cost is undetected bugs.
- A: noise is removed by narrow, reasoned excludes; everything else fails the build. EI_EXPOSE_REP on records and injected beans is a known false positive here. Keep the exclude to those two families, each with a comment reason, so new real bug types still trip.
- C: FindSecBugs is a new dependency (conventions.md Minimal Dependencies: document why). Plan does not name it. It adds new noise and could turn the factory gate red. Security is covered by Phase 20 tests and review. Defer it as a follow-up.
- Risk with A: the gate may fail on unknown existing findings. Mitigation: run once, triage, fix real ones, add per-finding excludes with a reason, never change behaviour for a false positive.
- Pin SpotBugs 4.8+ (Java 21 bytecode); exclude generated code only if needed.

## What would change my mind
Evidence that Medium produces a large volume of false positives beyond the two families (then add narrowly scoped excludes), or a decision that security scanning is in scope (then C).

## Implementation notes
Add spotbugs-maven-plugin (4.8+ engine) in pom.xml with threshold Medium, effort Max, excludeFilterFile config/spotbugs-exclude.xml, a `check` goal bound to verify. Create config/spotbugs-exclude.xml with a Match per bug pattern (EI_EXPOSE_REP, EI_EXPOSE_REP2, CT_CONSTRUCTOR_THROW), each preceded by an XML comment giving the reason. Document the plugin in docs per Minimal Dependencies.

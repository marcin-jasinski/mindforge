## Reasoning
- BundleConformanceValidator is the oracle for "every exported bundle passes" (plan 9b). If it parsed with MarkdownStructure, and the exporter/linter also does, one parser bug passes both sides (loss of independence): a shared misreading is never caught.
- Its patterns (INDEX_ENTRY, LOG_DATE at lines 35-37) check the fixed OKF grammar of index.md/log.md, not page-body syntax. T26 concerns heading/section/link meaning in page bodies.
- Whole-line index-entry shape and "##" level-2 log headings do not exist in MarkdownStructure (it has HEADING with levels, INLINE_LINK); adding them to a JDK-only domain class widens its API for one consumer, and risks regressions in BundleConformanceValidatorTest.
- C leaves a silent hole: new export/infrastructure code could add a second regex with no signal. B keeps the rule on everywhere, with one named, reasoned exception, as OutboundHttpGuardTest does.
- Guard failure modes to test: scan must be a source scan of Pattern.compile string literals containing "#" or "](" (and fixtures in @TempDir like OutboundHttpGuardTest); the allowlist must be exact path, so a second pattern added to the validator still needs a conscious decision; also test the guard flags a planted offender, so it cannot pass vacuously. Existing non-markdown hits (DocxParser "heading ([1-9])") must not trip it: match "#" or "](" literals only.

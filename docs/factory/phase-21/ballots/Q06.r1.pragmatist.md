## Reasoning
- The plan text is fixed: 21.2 "Against `docker compose up` with a stub-provider profile" (implementation-plan.md:1785). B and A keep compose; C drops it.
- B adds zero production code. The model URL is already an env var: `base-url: ${OPENROUTER_BASE_URL:https://openrouter.ai/api/v1}` (application.yml:49). One override file plus static JSON mappings; no new Java.
- The journey answers are static strings (ApiFlowTest.java:447-453 `givenAnswers()`: GUARD, EXTRACT, WRITE, LINKS, SUPERSEDE are fixed JSON). Flashcards, quiz and grading answers can be static too. The fragments in Prompts.java ("# Task: wiki page writing" ...) have no JSON-escaped characters, so a WireMock `bodyPatterns: contains` matches them in the request body.
- B exercises the real `AIGatewayAdapter` / `PermitGateway` / `TracingGateway` path, which no other test does. Unmatched prompts get WireMock's 404, which the adapter turns into a failed run - visible in the E2E.
- A ships a fake model in the product JAR. minimal-implementation.md: "Create only methods, classes, and functions that will actually be called" - production never calls it. web-security constraint needs an extra guard. More code, worse fit. Not hard-objected because a guard can make it safe, but it is the worst fit.
- C needs Playwright from Java (new dependency, browser install inside Maven) or orchestrating Node against a JVM-started server; `givenAnswers()` is private to ApiFlowTest so reuse is copy anyway. It also contradicts the plan wording.
- D is B with code we must own; WireMock JSON mappings are declarative and a standard image (`wiremock/wiremock`).
- Fully reversible: delete `compose.e2e.yml` and `src/test/e2e/wiremock/`.

## What would change my mind
If the adapter uses streaming or tool-call responses, or a step needs an answer derived from the prompt (e.g. echo a page path or block id unknown in advance), static mappings break and C (StubAIGateway responders) wins.

## Implementation notes
- `compose.e2e.yml` (repo root): service `model-stub` with image `wiremock/wiremock:3.x` (pinned), volume `./src/test/e2e/wiremock:/home/wiremock:ro`; `app` env `OPENROUTER_BASE_URL: http://model-stub:8080` (match the path Spring AI appends, `/v1/chat/completions` or `/chat/completions`), `OPENROUTER_API_KEY: e2e-not-a-key`, `JWT_SECRET` dev value, `AUTH_SECURE_COOKIES: false`; `app.depends_on: model-stub`.
- Start: `docker compose -f compose.yml -f compose.e2e.yml up -d --build`; Playwright in `src/test/e2e/` (own package.json) with `baseURL http://localhost:8080`.
- `src/test/e2e/wiremock/mappings/*.json`: one per task fragment (guard, extract, write, links, supersede, flashcards, quiz, grade, select, answer), `request: {method: POST, urlPathPattern: ".*/chat/completions", bodyPatterns: [{contains: "# Task: ..."}]}`, `response.jsonBody` = OpenAI chat completion (`id`, `model`, `choices[0].message.content` = the answer JSON as a string, `usage`). A catch-all low-priority mapping returning 500 with "unmatched prompt" body helps debugging.
- ADR `docs/adr/0042-e2e-uses-a-wiremock-model-provider.md`: no fake in the JAR; real adapter exercised; compose.yml default unchanged so production never gets fake output.
- Document the override in `docs/project/deployment.md`.

## Options
| id | option | correct | fit | simple | risk | reversible |
|----|--------|---------|-----|--------|------|------------|
| A  | `@playwright/test` in `src/test/e2e/` with its own package.json/lockfile, against compose | 4 | 2 | 2 | 3 | 4 |
| B  | `@playwright/test` in `frontend/` devDependencies, specs in `frontend/e2e/` | 4 | 3 | 3 | 3 | 4 |
| C  | Playwright for Java, JUnit 5 + AssertJ in `src/test/java/dev/mindforge/e2e/`, `@Tag("e2e")` | 4 | 5 | 4 | 3 | 4 |
| D  | C, but the browser points at a compose stack instead of a `@SpringBootTest` (Java binding, compose start) | 3 | 3 | 2 | 3 | 4 |

## Reasoning
- The repo already decided where e2e lives. `docs/standards/testing/test-writing.md` lines 31-37 list
  `src/test/java/.../e2e/ — full stack; @Tag("e2e")`. `pom.xml` lines 308-336 exclude `**/e2e/**` from surefire and
  include `**/e2e/**/*Test.java` in failsafe. `docs/project/tech-stack.md` line 56 says JUnit 5 is the runner for the
  "unit / integration / e2e structure". Only plan 21.2's path `src/test/e2e/` disagrees; that is one line to fix.
- C keeps one build tool, one test runner, one assertion style (AssertJ, CLAUDE.md § Testing) and lets the E2E reuse
  `StubAIGateway`, `support/Prompts.java` and `ApiFlowTest.givenAnswers()` (Q06 C) instead of a second answer router.
- The SPA is already copied into the classpath by `copy-frontend` (pom.xml line 384, `frontend/dist/frontend/browser`)
  when the frontend is built, so a `@SpringBootTest(RANDOM_PORT)` serves the real SPA; no new packaging.
- A adds a second npm project at the repo root next to `frontend/`: a second lockfile and Node toolchain outside Maven,
  against "Minimal Dependencies" (conventions.md line 15). B is smaller than A, but it puts a full-stack test inside the
  frontend module and moves a Java-server concern into the Angular tree; the frontend extra gate would also need care.
- D mixes both costs (Java binding plus compose orchestration) with no gain.
- The gate risk (`-DskipFrontend=true` builds no SPA) is real for C, but it is Q08's job: a Maven `-Pe2e` profile, or a
  failsafe `excludedGroups=e2e` by default, solves it without a different binding. I do not raise a hard objection on
  any option: none breaks an ADR; A/B only contradict a standard that can be edited.
- Playwright Test (Node) has better tooling (trace viewer, UI mode), which is the best argument for A/B; it does not
  outweigh fit with the existing test architecture for a single smoke journey.

## What would change my mind
Q06 resolving to a compose-only stack (A or B) where the backend is a black box: then a Node runner (B) is the
lighter fit. Evidence that Playwright for Java cannot install browsers on the CI linux runner would also change it.

## Implementation notes
- pom.xml: test dependency `com.microsoft.playwright:playwright` (current 1.5x, pin a version property
  `playwright.version`); document the reason in tech-stack.md (Minimal Dependencies).
- Test: `src/test/java/dev/mindforge/e2e/` (failsafe include needs `*Test.java`), name
  `SmokeJourneyTest.java`; `@Tag("e2e")`, `@Testcontainers`, `@SpringBootTest(webEnvironment = RANDOM_PORT)`,
  `StubAIGateway` as a `@TestConfiguration` bean, `@LocalServerPort`; Playwright `Browser` in `@BeforeAll`/`@AfterAll`
  (static, per class), Chromium headless only.
- Assertions with AssertJ plus Playwright `assertThat(page)` only where waiting is needed (import aliased via
  `PlaywrightAssertions`).
- Gate: keep e2e out of the default `verify` (failsafe `<excludedGroups>e2e</excludedGroups>` default, cleared by a
  `-Pe2e` profile that also sets `skipFrontend=false`) — final form per Q08.
- Browser install: `mvn exec:java -Dexec.mainClass=com.microsoft.playwright.CLI -Dexec.args="install --with-deps chromium"`
  in CI and in `docs/project/deployment.md`.
